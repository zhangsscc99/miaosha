# 18 缓存穿透和布隆过滤器

前 17 章测的是「东西存在、但被抢光了」。这一章测另一种流量：**请求的 id 根本不存在**。爬虫枚举商品 id、羊毛党试号码、下架商品的旧链接、竞争对手扫接口，都会打到这里。这类请求在缓存里永远查不到，`GET` 每次都落空，于是每一次都去查库。库存行锁、限流、售罄标记都拦不住它，因为它连商品都没有。

本章在本机跑了 5 种写法 × 2 种流量形状 × 3 轮，全部有原始 JSON。机器是那台 **8 核 / 16GB macOS**，Redis 8.10.3（256MB 上限）、MySQL 9.6.0、JDK 27，服务进程 512MB 堆、Hikari 池 16，客户端 64 并发。跑的时候机器负载在 **15 左右**（浏览器、IDE、其它 agent 都在抢核），所以**绝对值偏保守，比例比绝对值有用**，和前面几章一样。日期 2026-11-14。

面试口径和成本账在上一层的 [技术报告](../REPORT.md)，本章只讲这一件事。

## 一分钟看结论

同一份 5 万商品、90% 请求是不存在的 id、64 并发、每轮 10 秒：

| 写法 | 扫号（每次新 id） | 重放（同一批 1000 个 id） | 每请求落库 | 每次请求 Redis 命令 |
|---|---:|---:|---:|---:|
| 无防护，直接查库 | 9,587 | 10,103 | 100% | 0 |
| 空值占位（`__NULL__` 60 秒） | **8,591** | 14,366 | 90~100% / 4.3% | 1 |
| 进程内布隆 | 14,680 | **18,481** | **10.74%** | **0** |
| 共享布隆（Redis 位图） | 13,156 | 13,663 | 10.74% | 1 |
| 布隆 + 空值占位 | **17,186** | 17,526 | 0.94%（热）/ 10.75%（冷） | 0.11 |

（RPS 取 3 轮中位数，p50/p99 见下面的完整表。）

四句话：

1. **扫号场景下，空值占位是负优化。** 每个 id 都是新的，写进去的 `__NULL__` 一次都不会被读到，反而多了一次 `SETEX` 和一份内存。RPS 从 9,587 掉到 8,591（**-10%**），落库比例仍是 90~100%。
2. **布隆把落库从 100% 压到 10.74%，RPS 提高 1.53 倍。** 那 10.74% 里，10% 是真实存在的商品，**0.74% 是布隆的误判**（10 位/元素、7 个哈希，理论 0.82%，打到 90% 的不存在流量上就是 0.74%）。
3. **布隆在进程内查一次是 21.85 纳秒**，8 线程合计 **2.24 亿次/秒**；放到 Redis 共享位置是 **15.7 万次/秒一个分片**。差 1,400 倍，这是后面成本账的分水岭。
4. **布隆 + 空值占位是最终形态**：布隆挡住 90% 的扫号，漏过来的 0.74% 误判写一次空值，下一次重放就是缓存命中。代价是热路径偶尔多一次 `GET`（实测 0.11 次/请求）。

## 和现有代码的关系

`GoodsController.detail2` 的写法是：`GET` 详情 → 未命中 → `getGoodsVoByGoodsId` 查库 → `SET`。第 5 章已经量过这条路径的击穿。这一章不动那段代码，只换一个前提：**库里根本没有这个 id**，所以 `SET` 什么也写不进去（`StringUtils.isEmpty` 还会把空字符串当未命中，负缓存不能写 `""`）。

`GoodsKey` 的详情 TTL 是 60 秒，所以空值占位也用 60 秒。布隆的 id 空间是商品 id，真实商品是 `1..N`，扫号落在 `1e9` 以后。

## 规则

- **布隆参数**：`m/n = 10` 位/元素，`k = round(ln2 × 10) = 7`。理论误判率 `(1-e^{-kn/m})^k = 0.819%`。
- **哈希**：两个 64 位 `fmix64`，第 i 个位置用 `h1 + i×h2`（Kirsch-Mitzenmacher 双哈希）。偏移在**客户端**算，Lua 里只做 `GETBIT`/`SETBIT`——Lua 5.1 的 number 是 double，在脚本里做 64 位乘法会掉精度。
- **共享布隆**：位图 key 是 `bf:goods`，一次 `EVALSHA` 问完 k 个位，命中任何一个 0 就返回 0。
- **误判的方向**：布隆只会「说有」，不会「说没有」。说没有的一定不存在，所以**误判只会多查一次库，不会把不存在的商品卖出去**，也不会少卖。
- **不删除**：布隆不能删单个元素。商品下架后旧 id 仍然「可能存在」，会一直多查这一次库。处理办法见下面「不能删怎么办」。

## 布隆自己的物理参数

纯进程内，不碰 Redis 和 MySQL。每档插 n 个 key，再拿 100 万个**不存在**的 key 去问：

| 元素数 n | 位/元素 | 哈希 k | 内存 | 插入 | 实测误判 | 理论误判 |
|---:|---:|---:|---:|---:|---:|---:|
| 10 万 | 7 | 5 | 87,504 B | 3.9 ms | 3.477% | 3.466% |
| 10 万 | 10 | 7 | 125,000 B | 2.7 ms | 0.829% | 0.819% |
| 10 万 | 14 | 10 | 175,000 B | 2.3 ms | 0.121% | 0.120% |
| 100 万 | 7 | 5 | 875,000 B | 13.8 ms | 3.452% | 3.466% |
| 100 万 | 10 | 7 | 1,250,000 B | 13.7 ms | 0.812% | 0.819% |
| 100 万 | 14 | 10 | 1,750,000 B | 20.7 ms | 0.115% | 0.120% |
| **1000 万** | 10 | 7 | **12,500,000 B** | 213.9 ms | 0.829% | 0.819% |

- 实测和理论差在 **1% 以内**（相对误差），说明双哈希没有把分布搞坏。
- **1.25 字节/key** 是 10 位/元素的固定开销，和 key 本身多长无关——布隆不存元素。
- 1000 万商品的全量布隆 **12.5MB**，从零重建 **168 毫秒**。
- 单线程查一次 **21.85 纳秒**（5,000,000 次），8 线程 **2.24 亿次/秒**。它就是几次内存随机读，和 key 的字节数、Redis 的网络都无关。

位图放大到 **1 亿位**时，Redis 里 `STRLEN` 是 **12,500,001 字节**（12.5MB）——正好等于 m/8，没有额外结构。这一点很关键：布隆的容量是「位」，不是「key」。

## 共享布隆：一次 EVALSHA 还是七次往返

位图放在 Redis，20 万个 key、10 位/元素，构建用 pipeline 每批 5000 条 `SETBIT`：

| 项 | 数值 |
|---|---:|
| 构建 | 140 万次 `SETBIT`，0.638 秒，**219 万次/秒** |
| 位图大小 | 250,000 字节（200 万位） |
| 构建后自检 2,000 个已写入的 id | 漏判 **0** |
| 一次 `EVALSHA` 查 7 个位，16 连接 | **156,736 ops/s**，p50 96 µs，p99 231 µs |
| 同样 7 个位，客户端发 7 次 `GETBIT`，16 连接 | 33,020 ops/s，p50 469 µs |
| 同样 7 个位，1 条连接 | 8,834 ops/s |
| pipeline 100 个查询（700 条 `GETBIT`） | **423,700 次查询/秒**，每批 3.8 ms |
| 新增一个元素（一次 `EVALSHA` 写 7 位） | 133,624 ops/s |

两件事值得记住：

1. **7 次往返不是 1/7 的性能，是 1/4.7**（33,020 vs 156,736）。因为 16 条连接可以并发，往返被摊掉了；真正的差距是 Redis 解析 7 条独立命令 vs Lua 里 7 次 `redis.call` 的内部调用。
2. **pipeline 能把共享布隆的吞吐抬到 42 万/秒**，但那是「客户端攒 100 个请求一起问」的形态，只在网关/批处理里成立，普通 REST 接口用不上。所以后面按 **15.7 万/秒一个分片** 算容量，不按 42 万。

## 端到端：5 种写法，2 种流量

`scan` 是扫号：每次一个**新的**不存在 id（落在 1e9 之后），另有 10% 的请求打真实商品 `1..50000`。`replay` 是重放：同一批 1000 个不存在 id 反复打。两种都有 10% 真实商品。3 轮，每轮 10 秒，64 并发，中位数：

| 写法 | 流量 | RPS | p50 | p99 | 落库/请求 | Redis/请求 |
|---|---|---:|---:|---:|---:|---:|
| 无防护 | scan | 9,587 | 4.85 ms | 34.9 ms | **100%** | 0 |
| 无防护 | replay | 10,103 | 4.60 ms | 31.7 ms | **100%** | 0 |
| 空值占位 | scan | **8,591** | 5.35 ms | 44.0 ms | **90~100%** | 1.00 |
| 空值占位 | replay | 14,366 | 3.10 ms | 25.4 ms | 4.33% | 1.00 |
| 进程内布隆 | scan | 14,680 | 2.79 ms | 23.9 ms | **10.74%** | **0** |
| 进程内布隆 | replay | 18,481 | 2.54 ms | 17.8 ms | **10.90%** | **0** |
| 共享布隆 | scan | 13,156 | 3.62 ms | 25.0 ms | 10.74% | 1.00 |
| 共享布隆 | replay | 13,663 | 3.55 ms | 24.1 ms | 10.90% | 1.00 |
| 布隆 + 空值 | scan | **17,186** | **2.49 ms** | **18.4 ms** | 0.94%（热） | 0.11 |
| 布隆 + 空值 | replay | 17,526 | 2.58 ms | 20.6 ms | 5.09% | 0.11 |

### 扫号：空值占位为什么更慢

扫号每次的 id 都是新的，所以：

1. `GET gn:<新id>` 必然未命中（1 次往返）；
2. 未命中就查库（1 次 SQL，和 `none` 完全一样）；
3. 查到空，再 `SETEX __NULL__`（第 2 次往返，还有一次写）。

比 `none` 多了 **2 次 Redis 命令和一次写**，落库一次没少。实测 RPS 9,587 → 8,591，**-10.4%**，p99 从 34.9 ms 涨到 44.0 ms。第 2、3 轮落库是 90% 而不是 100%，只是因为 10% 真实商品的详情被上一轮缓存了——和防穿透无关。

这就是面试里最容易被追问的点：**负缓存只对「同一批不存在的 id 被重复请求」有效**。扫号是唯一 id，负缓存等于把攻击流量抄进了自己的内存。反过来，如果是某个下架商品被反复刷（广告落地页、App 缓存没清），负缓存非常有效。

### 布隆：10.74% 是怎么来的

90% 的扫号流量在布隆这一层就被判死，一次 Redis、一次 SQL 都不发。剩下的：

- **10%** 是真实商品，必须查（缓存未命中时）；
- **0.74%** 是布隆误判：0.819% × 90% ≈ 0.74%。实测 10.74% − 10% = 0.74%，对得上。

`bloom` 的 RPS 是 `none` 的 **1.53 倍**，p50 从 4.85 ms 降到 2.79 ms，p99 从 34.9 ms 降到 23.9 ms。瓶颈从 MySQL 变成了 JVM 自己的 HTTP + 那 10% 的真实查询。

### 共享布隆为什么慢一截

`bloomredis` 每个请求多一次 EVALSHA 往返（p50 从 2.79 ms 涨到 3.62 ms），RPS 从 14,680 掉到 13,156（**-10%**）。但它换来的是**所有 Pod 共用一份位图**：新商品上架只写一次 Redis，不用通知 800 个 Pod。

反过来，进程内布隆每个 Pod 各有一份 12.5MB（1000 万商品），新商品上架要么广播失效、要么等下一次重建。这个取舍在下面「不能删怎么办」里展开。

### 布隆 + 空值：热路径 0.11 次 Redis

`bloomnull` 只在布隆说「可能存在」时才查 Redis：10% 真实 + 0.74% 误判 ≈ 0.11 次/请求。所以它既拿到了布隆的 90% 拦截，又用负缓存把误判的重复请求收掉：

- 扫号：落库 **0.94%**（热）——比 `bloom` 的 10.74% 少了整整一个数量级，因为 10% 的真实商品详情已经在 Redis 里了；
- 重放：落库 **5.09%**，因为 1000 个不存在 id 的空值在 60 秒 TTL 内，第一轮写完，后面直接命中；
- 冷启动落库是 **10.75%**，和 `bloom` 一样——第一轮没有缓存，该查的还得查。

RPS 17,186，比 `bloom` 高 17%，因为绝大多数真实商品走了 Redis 而不是 MySQL。注意这是**稳态**：商品的详情缓存命中率高的时候才是这个数。

## 不能删怎么办

布隆没有删除。商品下架、活动结束、id 回收，旧 id 会永远「可能存在」，每次都要多查一次库。真实系统里有四种处理：

| 办法 | 代价 | 什么时候用 |
|---|---|---|
| 全量重建 | 1000 万商品 **168 ms**（进程内）；共享布隆 7 亿次 `SETBIT` ÷ 219 万/秒 ≈ **5.3 分钟** | 商品数不大、能接受短暂误判 |
| 计数布隆（每个位改成 4 位计数器） | 内存 **×4**（1000 万件 12.5MB → 50MB），仍然会漏计 | 删除很少、内存不紧张 |
| 分代布隆（新旧两张，定期轮换） | 内存 ×2，查询两次 | 删除量大、要求低延迟 |
| 只对「绝对不存在」的 id 建布隆 | 0 额外内存 | id 有单调性/发号器，能用上下界先判掉 |

还有一条工程上的做法：**布隆只挡「一定不存在」**，把「可能不存在」交给负缓存。这也是 `bloomnull` 比 `bloom` 更好的原因——布隆是粗筛，负缓存是精筛，两层的错误方向不一样。

- **注意这是「加钱能解决」的那一类问题**，和抢库存的热行不一样：穿透的分库分表真能拆开，因为每个 id 是独立的行。所以这张表是可信的，不像第 17 章 `v0` 的 3,750 台那样「加钱也跑不了」。

**误判率就是钱**（1000 万 QPS、扫号占比 90% 的极端假设）：

| 误判率 | 漏进存储的 QPS | MySQL 主库 | 月成本 |
|---:|---:|---:|---:|
| 1.00% | 100,000 | 38 | ¥114,000 |
| 0.81%（本章实测） | 81,250 | 31 | ¥93,000 |
| 0.10%（14 位/元素） | 10,000 | 4 | ¥12,000 |

从 10 位/元素加到 14 位/元素，内存从 1.25 字节/key 涨到 1.75 字节/key（+40%），误判降 8 倍，1000 万 QPS 下省 **¥81,000/月**。这是布隆最划算的一次调参。

## 面试时可以主动讲的取舍

1. **先说方向**：布隆只会假阳性，不会假阴性。所以它放在「防穿透」的入口，不能放在「判断用户有没有资格」这种不能误判的地方。
2. **扫号 vs 重放要分开讲**。空值占位在扫号下是负优化（本章实测 -10%，还写脏内存），在重放下有效（落库 4.33%）。面试官问「为什么不用负缓存」时，这就是答案。
3. **布隆不该单独用**。`bloom + 负缓存` 才是稳态：布隆粗筛 90%，负缓存收掉 0.74% 的误判。实测落库从 10.74% 降到 0.94%（热）。
4. **进程内 vs 共享是「内存换核」**：进程内 21.85 ns/次、2.24 亿/秒，但每个 Pod 一份、更新要广播；共享 15.7 万/秒一个分片，多 96 个分片才 ¥48,000/月，但多一个网络往返，p50 从 2.79 ms 涨到 3.62 ms。
5. **容量按位算，不按 key 算**：1000 万商品 12.5MB，1 亿 119MB，10 亿 1.16GB。这个数字要能当场算出来：`n × 10 bit ÷ 8`。
6. **重建成本要敢说**：1000 万 168ms（进程内），共享位图 5.3 分钟（219 万 SETBIT/秒）。所以共享布隆一般做成「双写 + 定时全量」，而不是每次上架都重建。
7. **知道它不解决什么**：布隆不挡「存在但被抢光」的流量（那是第 1、4、17 章的售罄标记），不挡热点 key（第 5 章），不挡 DDoS（那是边缘和限流，第 10 章）。
8. **误判率的公式**：`(1 - e^{-kn/m})^k`，最优 `k = ln2 × m/n`。本章 10 位/元素对应 k=7，实测 0.812%~0.829%，理论 0.819%，误差 1% 以内。

## 边界

- 客户端和服务端在同一台 8 核机器上，压测时系统负载 15 左右。绝对值偏保守，**只用比例**。这台机器同时还有浏览器、IDE 和其它 agent。
- 没有第二台机器，没有真实网关，没有 TLS。共享布隆的 96 个分片是**除法**，没有跑起来。
- 布隆的 id 用商品 id，真实系统里更常见的是「用户 id + 商品 id」拼起来；key 变长不影响 1.25 字节/id 的结论，因为布隆不存 key。
- 没有测 Redis Cluster 下的位图分片。按 id 取模分片时，一次查询仍然只落一个分片（k 个位都在同一张位图里），所以 15.7 万/秒可以横向乘分片数——但这条是推论，不是本章实测。
- `bloomnull` 的 0.94% 是**热**的稳态（商品详情都缓存过）。冷启动是 10.75%，两个数都在表里。
- 没有测布谷鸟过滤器（Cuckoo Filter）和 Ribbon Filter。前者支持删除、空间效率略高，后者更省内存但实现复杂，都属于后续。

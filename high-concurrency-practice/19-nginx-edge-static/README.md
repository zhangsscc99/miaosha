# 19 nginx 边缘层：静态化、gzip、keepalive、缓存锁、限流

前 18 章都在应用进程、Redis、数据库和消息队列里。这一章换到最外面一层：**nginx 边缘**。秒杀页面 90% 的字节是商品详情 HTML，只有「还剩几件」是实时数据。如果每个点击都让 Java 拼一遍 8KB 页面、查一次 Redis，应用和 Redis 都要按点击 QPS 扩容；把页面静态化、把压缩和限流放在边缘，应用只需要处理真正要决策的那一小部分请求。

这一章在**同一台机器**上把 9 种边缘写法逐个跑了一遍，原始 JSON 在 [`results`](results/README.md)。nginx 是 1.31.8，2 个 worker；静态页 1000 个、每个 8,106 字节；上游是第 17 章那个 Java 商详服务的一个简化版（一次 Redis `GET` 再拼 8KB HTML）；Redis 8.10.3，256MB。日期 2026-11-14。

面试口径和成本账在上一层的 [技术报告](../REPORT.md)，本章只讲边缘这一层。

## 一分钟看结论

64 连接、每项 3 秒、同一轮跑完（这台 8 核 macOS，负载见下面的边界）：

| 写法 | RPS | p50 | p99 | nginx CPU | 每请求 CPU | 说明 |
|---|---:|---:|---:|---:|---:|---|
| 静态页，keep-alive | **38,555** | 1.31 ms | 5.7 ms | 107.7% | **27.9 µs** | 基线：nginx 直接发 8,106 字节 |
| 静态页 + gzip | 31,541 | 1.70 ms | 6.4 ms | 187.0% | 59.3 µs | 字节从 8,106 降到 **1,906**（4.25 倍） |
| 静态页，关 keep-alive | **13,608** | 3.06 ms | 18.0 ms | 56.0% | 41.2 µs | 每请求一次 TCP，RPS **-64.7%** |
| 静态页 + open_file_cache | 37,251 | 1.40 ms | 5.4 ms | **50.4%** | **13.5 µs** | 同样的 RPS，CPU 减半 |
| 静态页，关 sendfile | 41,477 | 1.29 ms | 6.7 ms | 102.4% | 24.7 µs | 这台 macOS 上没有稳定收益，见正文 |
| 动态页，经 nginx 反代 | 16,239 | 2.74 ms | 24.8 ms | 49.6% + 上游 166.7% | **133 µs** | 一次 Redis `GET` + 拼 8KB |
| 动态页，直连上游 | 24,601 | 2.34 ms | 9.2 ms | 上游 152.5% | 62 µs | 少了 nginx 这一跳，也少了它的排队 |
| 详情 API（2.3KB JSON） | 27,272 | 2.09 ms | 9.4 ms | 66.6% + 上游 131.9% | 73 µs | 字节少 3.5 倍，CPU 没少多少 |
| 边缘缓存命中，TTL 2 秒 | 25,758 | 1.61 ms | 16.8 ms | 95.5% + 上游 8.5% | 40.4 µs | 回源从 1.6 万/秒降到 **约 400~770/秒** |

五句话：

1. **静态化把这一个请求的 CPU 从约 97~133 µs 降到 28~30 µs**，RPS 提高 2.0~2.4 倍，Redis 从 1 次/请求降到 0。省的不是带宽，是应用进程和 Redis 的命令数。
2. **keepalive 是最便宜的优化**：关掉之后 RPS 掉 55%~65%，p99 从 5.7 ms 涨到 18 ms。生产上不要在这一层关它。
3. **gzip 是 CPU 换带宽**：字节少 4.25 倍，nginx CPU 从 27.9 µs 涨到 59.3 µs（2.1 倍）。在 1000 万 QPS 这一档，压缩后的带宽从 648 Gbps 降到 152 Gbps，这是「能不能装下」的问题，不只是钱。
4. **边缘缓存的命中率不是重点，回源 QPS 才是**：1000 个商品、2 秒 TTL，回源被钉在 **500/秒**，和点击是 10 万还是 1000 万无关。命中时 nginx 仍是 40 µs/请求，RPS 不会因为「命中」变成无限。
5. **`proxy_cache_lock` 只保护「新元素」的冷启动，不保护 TTL 过期**。冷启动 256 并发被收成 1 次回源，但等待者要等约 **500 ms**（nginx 每 500 ms 轮询一次）；TTL 过期时 256 个请求**全部**回源。过期场景用 `proxy_cache_use_stale updating` + 后台更新，1 次回源、p50 38~40 ms，两个指标都更好。

## 这一层在秒杀里到底管什么

一个商详页 8KB，里面 95% 是标题、价格、参数、评价、样式，只有「剩余 N 件」和倒计时是变的。第 5 章已经把「详情缓存 + singleflight」放在应用里做了；这一章把同一件事往前推一层：

```
浏览器 → CDN / nginx（静态页、gzip、缓存、限流） → 应用（库存决策、下单） → Redis / MQ / DB
```

- **静态页**：活动开始前生成，内容是快照；库存由页面上的 AJAX 或点击「立即抢购」时再问。8KB 不再经过 Java，也不再查 Redis。
- **gzip**：在边缘压，压完再出网。CPU 花在边缘，省的是用户带宽和 CDN 账单。
- **keepalive**：边缘和浏览器之间复用 TCP。秒杀流量是突发短连接，如果不复用，握手和端口耗尽会先于 CPU 成为瓶颈。
- **边缘缓存**：页面必须动态渲染、又不想每个请求都回源时，让 nginx 按 URL 缓存 1~2 秒；回源量由「商品数 / TTL」决定，不由点击决定。
- **限流**：在离用户最近的一层把超量请求打成 503，别让它们进到应用和 Redis。第 10 章测的是 Redis 里的限流算法，这一层测的是 nginx 的 `limit_req`。

Kubernetes 里这一层通常是 Ingress Controller（nginx-ingress / Envoy）或云 CDN，不是业务 Pod。这台机器没有 dockerd，也没有 kubelet，所以本章跑的是**宿主机上的 nginx 进程**，不假装跑过 K8s。Ingress 的 `nginx.ingress.kubernetes.io/*` 注解最终落到的就是下面这些指令。

## 复现

依赖本机 nginx 1.31.8（Homebrew）、JDK 21+、Maven（Jedis 3.7.0 已在 `~/.m2`）、Redis 8.10.3。

```bash
cd high-concurrency-practice/19-nginx-edge-static
bash run.sh              # 起 Redis 6390、生成 1000 个静态页、起 Java 上游和 nginx
bash run.sh matrix       # 9 项主对照，3 轮
bash run.sh scale        # 32/64/128/256 连接
bash run.sh cache        # 冷启动 256 并发，lock on/off × 3 轮
bash run.sh stale        # TTL 过期，lock vs stale-while-revalidate × 3 轮
bash run.sh limits       # 限流三种 burst × 2 轮
python3 scripts/cost_model.py
```

`run.sh` 会在结束时停掉自己起的进程。手工起服务：

```bash
redis-server --port 6390 --maxmemory 256mb --save '' --appendonly no --daemonize yes
python3 scripts/gen_data.py                      # 生成 runtime/static/p1..p1000.html 和 seed.resp
redis-cli -p 6390 --pipe < runtime/seed.resp
java -Xmx512m -cp "target/classes:$(cat target/cp.txt)" com.geekq.lab.edge.EdgeServer \
  --port 18090 --redisPort 6390
ulimit -n 32768
nginx -p "$PWD/runtime/" -c "$PWD/nginx/nginx.conf"
```

单跑一组：

```bash
java -Xmx2g -cp "target/classes:$(cat target/cp.txt)" com.geekq.lab.edge.LoadGen \
  --url http://127.0.0.1:18080 --prefix /p --suffix .html \
  --seconds 5 --warmup 2 --concurrency 64 --goods 1000 --label static
```

## 静态化：把 8KB 从 Java 搬到 nginx

`GoodsController.detail2` 现在的写法是：`GET` 详情 → 未命中查库 → 渲染 → `SET`。第 5 章量过这条路径的缓存击穿。这一章不动业务代码，只把「渲染完的整页」提前生成成文件，让 nginx 用 `sendfile` 发出去；动态路径则保留为对照。

| | 静态页 | 动态页（经 nginx） | 动态页（直连） | 详情 API |
|---|---:|---:|---:|---:|
| RPS | **38,555** | 16,239 | 24,601 | 27,272 |
| p50 | 1.31 ms | 2.74 ms | 2.34 ms | 2.09 ms |
| p99 | 5.7 ms | 24.8 ms | 9.2 ms | 9.4 ms |
| nginx CPU | 107.7% | 49.6% | 0 | 66.6% |
| 上游 CPU | 0 | 166.7% | 152.5% | 131.9% |
| Redis 命令/请求 | **0** | 1 | 1 | 1 |
| 响应字节 | 8,106 | 8,106 | 8,106 | 2,334 |

静态页相对动态页是 **2.0~2.4 倍 RPS**，p50 从 2.3~2.7 ms 降到 1.3 ms，p99 从 9~25 ms 降到 5.7 ms。按 CPU 归一化：静态页 **27.9 µs/请求**，动态页 **97~133 µs/请求**，差 3.5~4.8 倍。Redis 那一次 `GET` 只是其中一部分，更多的是 Java 拼 8KB 字符串、字符集编码和 HTTP 写回。

**反直觉的一点：2.3KB 的 JSON API 并不比 8KB 的 HTML 便宜。** 同一轮里 API 是 27,272 RPS，p50 2.09 ms，每请求 CPU 约 73 µs；HTML 动态页是 16,239 RPS、133 µs。字节少 3.5 倍，CPU 只少 1.8 倍，因为 JSON 那一段 `StringBuilder` 拼 SKU、优惠券、服务标签的循环并不比 HTML 少。**不要因为「返回小」就把它放在热路径上。**

**直连上游比经 nginx 快**：24,601 对 16,239（1.51 倍），因为 nginx 反代多一次连接、一次拷贝和一份 CPU。边缘层的价值不是「让单个请求更快」，是「让不该进来的请求不进来」：静态页把 Redis 命令降到 0，gzip 把字节降下来，缓存把回源降下来，限流把超量挡在外面。

### 连接数不是越多越好

`scale` 跑了 32/64/128/256：

| 连接 | 静态页 RPS | p50 | p99 | nginx CPU | 客户端 CPU |
|---:|---:|---:|---:|---:|---:|
| 32 | **44,507** | 0.64 ms | 2.1 ms | 90.7~107.7% | 342~352% |
| 64 | 42,002 | 1.30 ms | 4.2~4.6 ms | 105.0~117.1% | 371~381% |
| 128 | 34,598 | 2.7~2.9 ms | 11~16 ms | 82.1~99.2% | 328~395% |
| 256 | 6,377（另一轮客户端超时） | 33.0 ms | 78.2 ms | 19.4% | 451% |

32 连接最快，64 就开始变慢，256 直接塌掉。不是 nginx 不行，是**同一台机器上的客户端先撑不住**：256 个虚拟线程 + 8KB 响应体 + JVM GC，客户端自己占了 4.5 个核，服务端反而闲着。生产上连接数和机器数是两件事，不要用「压测客户端能开多少连接」去推服务端容量。

## gzip：4.25 倍字节，2.1 倍 CPU

同一个静态页，18081 打开 `gzip on`、`gzip_comp_level 5`，客户端带 `Accept-Encoding: gzip`：

| | 不压缩 | gzip | 变化 |
|---|---:|---:|---:|
| RPS | 38,555 | 31,541 | **-18.2%** |
| p50 | 1.31 ms | 1.70 ms | +30% |
| nginx CPU | 107.7% | 187.0% | +73.6% |
| 每请求 CPU | 27.9 µs | **59.3 µs** | 2.1 倍 |
| 响应体 | 8,106 B | **1,906 B** | **4.25 倍** |
| Content-Length | 8,106 | 0（chunked） | gzip 动态压，长度未知 |

`content-length` 变成 0 是因为 gzip 边压边发，走 chunked。客户端读到的字节是 1,906，不是 8,106。

gzip 的取舍不是「快不快」，是「CPU 和带宽哪个先不够」：

- 1000 万 QPS、8KB/请求 = **81.1 GB/s = 648 Gbps**。这个量级不是加机器能解决的，必须先压。
- gzip 后 19.1 GB/s = **152 Gbps**，仍然很大，但已经是另一个数量级。
- 代价是每请求 59.3 µs，1000 万 QPS 要 149 台 4c8g，不压是 74 台，多 75 台、**70,500 元/月**；按 CDN 0.2 元/GB 算，1 小时省 **44,640 元**。活动超过 **1.6 小时**才回本（见 `results/cost-model.md`）。

**秒杀活动通常只有几分钟。** 如果只为一次 10 分钟的活动买机器，gzip 的 CPU 钱回不来；但 648 Gbps 的出口带宽根本买不到，所以 gzip 仍然要开。**先算带宽，再算 CPU。**

## keepalive：关掉就掉一半

18082 把 `keepalive_timeout` 设成 0，每个请求一次 TCP：

| | keep-alive | 关 keep-alive | 变化 |
|---|---:|---:|---:|
| RPS | 38,555 | **13,608** | **-64.7%** |
| p50 | 1.31 ms | 3.06 ms | 2.3 倍 |
| p99 | 5.7 ms | 18.0 ms | 3.2 倍 |
| nginx CPU | 107.7% | 56.0% | 每个请求更便宜，但总量少 |

另一轮（32 连接）是 40,538 对 18,018，**-55.6%**。两次都掉一半以上。TCP 三次握手、慢启动、TIME_WAIT 占用端口，都会在突发流量里先爆。nginx 默认 65 秒，不要改小；上游 `upstream { keepalive 256; }` 也要开，否则 nginx 到 Java 之间还是短连接。

## open_file_cache 和 sendfile：一个真省，一个不背锅

| | 基线 | open_file_cache | sendfile off |
|---|---:|---:|---:|
| RPS | 38,555 | 37,251 | 41,477（另一轮 30,916） |
| p50 | 1.31 ms | 1.40 ms | 1.29 ms |
| nginx CPU | 107.7% | **50.4%** | 102.4% |
| 每请求 CPU | 27.9 µs | **13.5 µs** | 24.7 µs |

`open_file_cache` 把 `open(2)`、`stat(2)` 的结果缓存在 worker 里，命中时不用再进内核。同样的 RPS，nginx CPU 从 107.7% 降到 50.4%，**归一化后约 2 倍容量**。RPS 没涨是因为客户端先到瓶颈（客户端 365%），不是它没用。

`sendfile off` 在这台 macOS 上没有稳定收益：一次 41,477（比基线快 7.6%），另一次 30,916（比基线慢 24%）。**不把它写成优化项。** Linux 上 `sendfile` 省一次用户态拷贝，通常更快；这台机器的结果不能拿去讲 Linux。

## 边缘缓存：命中、冷启动、过期，是三件不同的事

nginx 的 `proxy_cache` 把上游的 8KB 响应存到磁盘，命中时直接发。配置是 `proxy_cache_valid 200 2s`，缓存键 `$host:$server_port$request_uri`，缓存区 128MB。

### 稳态：回源被钉在商品数 / TTL

1000 个商品、2 秒 TTL，预热后跑 5 秒：

| | 动态页（不缓存） | 边缘缓存 |
|---|---:|---:|
| RPS | 16,239~18,016 | 19,445~25,758 |
| p50 | 2.74 ms | 1.61 ms |
| p99 | 24.8 ms | 16.8 ms |
| nginx CPU | 49.6% | 95.5% |
| 上游 CPU | 166.7% | 8.5% |
| 每请求 CPU | 97~133 µs | 40.4 µs |
| 回源 | 16,239~18,016/秒 | **约 413~767/秒** |
| 缓存状态 | - | HIT 96,435 / EXPIRED 2,065 / MISS 1 |

缓存命中把上游从 1.6~1.8 万/秒降到 400~770/秒，**少 21~44 倍**。但 nginx 自己的 RPS 只从 1.6 万涨到 2.6 万（1.6 倍），因为命中仍要查缓存、读磁盘、发 8KB，每请求 40.4 µs，只比静态页的 29.6 µs 多 36%。**边缘缓存的收益在回源，不在命中 RPS。**

回源量的公式是：

```
回源 QPS ≈ 商品数 / TTL      （每个商品每个 TTL 至少回源一次）
```

1000 个商品、2 秒 TTL = **500/秒**，和点击是 10 万还是 1000 万无关。这是这一章最值钱的一条：**它把「按点击扩容」变成了「按商品数扩容」。**

### 冷启动：cache lock 省回源，但等待者要等 500 ms

256 个并发同时打一个**不存在的缓存键**（URL 带随机 `b=`），上游注入 20 ms 渲染耗时：

| | lock on | lock off |
|---|---:|---:|
| 回源次数 | **1** | 233~256 |
| 200 响应 | 256 | 256 |
| MISS / HIT | 1 / 255 | 233~256 / 0~23 |
| p50 | **549 ms** | 72~91 ms |
| p99 | 570~576 ms | 115~127 ms |
| 墙钟 | 578~591 ms | 124~142 ms |

`proxy_cache_lock on` 把回源从 250 次收成 1 次，代价是 255 个请求等 **约 550 ms**。这个 550 ms 不是 20 ms 的回源，也不是 2 秒的 `proxy_cache_lock_timeout`，而是 nginx 的等待轮询：

- 注入 0 ms：等待 **507~510 ms**
- 注入 5 ms：**510~513 ms**
- 注入 100 ms：**513~515 ms**
- 注入 500 ms：**1,010~1,011 ms**

回源多快都不影响那 500 ms 的台阶，回源超过 500 ms 才叠加。用 18079 的 debug 日志能看到 `http file cache lock u:0` 之后请求被挂起，缓存写入后由 500 ms 的轮询唤醒。**结论：cache lock 保护上游，不保护尾延迟。** 秒杀页面的 p99 如果是 100 ms，这个 550 ms 不能接受。

### TTL 过期：cache lock 收不住，stale 才收得住

先预热一个页面，等 6 秒（TTL 2 秒，nginx 的秒级粒度会多给最多 1 秒，6 秒保证过期），再 256 并发打同一个 URL：

| | cache lock（18084） | stale + 后台更新（18076） |
|---|---:|---:|
| 回源 | **256** | **1** |
| 缓存状态 | EXPIRED 256 | STALE 1 / UPDATING 255 |
| p50 | 67~95 ms | **38~40 ms** |
| p99 | 103~133 ms | 51~63 ms |
| 200 响应 | 256 | 256 |

`proxy_cache_lock` 的文档写的是「populate a **new** cache element」，过期元素不是 new，所以 256 个请求**全部**回源，一次都没收住。这是冷启动和过期最容易被混为一谈的地方。

`proxy_cache_use_stale updating` + `proxy_cache_background_update on` 的语义是：缓存过期后先把旧页发给所有人（`STALE`），只放一个请求在后台更新（`UPDATING`）。结果是回源 1 次、p50 38 ms，**回源和延迟同时优于 cache lock**。代价是用户可能看到 2 秒前的库存，所以页面上的库存必须由 API 再确认，不能把静态页当真相。

### 三种策略怎么选

| 场景 | 策略 | 代价 |
| --- | --- | --- |
| 页面可以接受 1~2 秒快照 | 静态页 + CDN，长 TTL | 库存要 API 确认 |
| 页面必须每次渲染，但可缓存 1~2 秒 | `proxy_cache` + `use_stale updating` + `background_update` | 最多旧 2 秒；回源 500/秒 |
| 页面绝对不能旧，且回源很贵 | `proxy_cache_lock` | 冷启动 p50 约 550 ms；TTL 过期仍会穿透 |
| 页面绝对不能旧，回源便宜 | 不缓存，直接反代 | 上游按点击扩容 |

**秒杀详情页的正确答案通常是第一行或第二行**：页面壳静态化，库存用 API；或者边缘缓存 1~2 秒 + stale。不要用 cache lock 去保 p99。

## 限流放在边缘：burst 的大小也是排队并发

`limit_req_zone $binary_remote_addr zone=rl:10m rate=5000r/s`，`limit_req_status 503`。三个端口分别是 `burst=1`、`burst=1000 nodelay`、`burst=1000`（排队）。64 连接、3 秒、动态页：

| | burst=1 | burst=1000 nodelay | burst=1000 排队 |
|---|---:|---:|---:|
| 客户端发出的请求 | 53,287 | 22,739 | 15,134 |
| 200 放行 | **4,224（7.9%）** | 15,825（69.6%） | **15,134（100%）** |
| 503 | 49,063 | 6,914 | **0** |
| 放行速率 | **1,446/秒** | 5,258/秒 | 5,130/秒 |
| p50 | 3.16 ms | 5.09 ms | **12.82 ms** |
| p99 | 58.6 ms | 93.4 ms | 16.1~48.6 ms |
| 上游收到 | 4,785 | 16,353 | 16,923 |
| nginx CPU | 35.3% | 26.5% | 27.8% |

三件事：

1. **`burst=1000 nodelay` 和排队的放行速率都贴着 5,000/秒**，和配置的 `rate=5000r/s` 对得上（5,258 和 5,130）。区别是 nodelay 把超出的 6,914 个立刻打成 503，排队把超出的放进队列，p50 从 5.1 ms 涨到 12.8 ms，p99 反而更低（16~49 ms 对 71~93 ms），因为没有 503 的快速重试把客户端打爆。
2. **`burst=1` 的放行只有 1,446/秒，不是 5,000/秒**（另一轮 load 更高时是 1,119/秒）。因为 `burst` 同时是「能排队的请求数」：只有 1 个槽位，放行的请求实际上被串行化，速率被上游延迟（约 0.67 ms）卡住。**burst 不只是「允许多少突发」，它还是「允许多少并发等待」。** 想按 5,000/秒放行，burst 要给到足够容纳一个 RTT 的量。
3. **503 不是 429。** nginx 的 `limit_req_status` 默认 503，客户端和监控要按 503 处理；如果要 429，显式改。

限流放在边缘的代价是 nginx 自己要扛全部被拒绝的请求（这台机器上约 5.3 万次/3 秒，nginx 35.3% CPU），但上游只收到 4,785 次，Redis 也少了 4.9 万次。相比第 10 章把限流放进 Redis，边缘这一层省的是 Redis 的核和网络往返。

## 容量和钱

| 10 万 | 3 | 1 | ¥2,971 | 1 | ¥940 | **¥2,031** |

表的读法：1000 万点击/秒、每个点击都要 Java 拼 8KB、每次查一次 Redis，需要 243 台 4c8g 加 100 个 Redis 分片；静态化之后只要 74 台，Redis **0 个分片**，少 **17.4 万元/月**。这不是「静态页比 Java 快 3 倍」这么简单：它把 Redis 整层从按点击扩容里拿掉了。

|---:|---:|---:|---:|---:|---:|

边缘缓存的 101 台比静态页的 74 台多，因为命中仍要 40.4 µs/请求；但它保留了「页面是动态的」这个能力，且回源只有 500/秒。如果页面可以完全静态化，静态页更便宜。

`open_file_cache` 把静态页从 74 台降到 37 台（少 **¥34,780/月**）。这个数只在这台 macOS 上成立：Linux 的 `open`/`stat` 更便宜，收益会小；而且 RPS 没有涨（客户端瓶颈），只有 CPU 减半，所以它是「同一 RPS 下省核」，不是「同一台机器多一倍 QPS」。

### 一笔不要加错的账

- 静态化的 ¥173,980 是**机器 + Redis**，不是带宽；带宽在下一张表。
- 边缘缓存的 ¥95,091 和静态页的 ¥69,560 是**互斥方案**，不要相加。
- `open_file_cache` 的 ¥34,780 是静态页 74 台里的 37 台，不是额外省出来的。
- gzip 的 ¥70,500 和多省的钱不能直接相加：它只增加 CPU，不减少机器台数（压缩后的机器数更多）。
- CDN 的 ¥58,363/小时 是流量费，不含 HTTPS 请求数费用；1000 万 QPS = 360 亿请求/小时，按请求计费的产品会把这张表推翻，下单前要按实际计费项重算。
- 这些数和第 1 章的 14,969、第 17 章的 31 万不是同一笔，不要相加。

## 面试时可以主动讲的取舍

1. **先说这一层解决什么**：不是让单个请求更快，是让「不需要进应用的请求」不进应用。静态页把 Redis 命令降到 0，缓存把回源降到商品数/TTL，限流把超量挡在门外。
2. **静态化和 CDN 不是一回事**：静态化省应用 CPU，带宽仍要出；CDN 把带宽接过去，但按 GB 计费。10 万 QPS 的 8KB 页面就是 6 Gbps，先算这个数。
3. **cache lock 的 500 ms 是本章最容易被追问的细节**：它保护上游，不保护 p99；冷启动有效，TTL 过期无效；过期要用 `use_stale updating`。
4. **burst 同时是排队并发**：`burst=1` 不是「每秒 5000」，实测只有 1,486/秒；想按 rate 放行，burst 要能装下一个 RTT 的请求。
5. **keepalive 先于一切调优**：关掉掉 55%~65%，比任何 gzip/open_file_cache 的收益都大，而且不花 CPU。
6. **gzip 是 CPU 换带宽，先看带宽是不是瓶颈**：648 Gbps 装不下时，2.1 倍 CPU 也得压；只是几分钟的活动，回不了本。
7. **open_file_cache 只省 CPU，不涨 RPS**（在这台机器上）；不要把它讲成「QPS 翻倍」。
8. **K8s 里这一层是 Ingress/CDN，不是业务 Pod**：本章没跑 kubelet，不能讲成「已经在 K8s 验证过」。

## 和现有代码的关系

- `GoodsController.detail2` 是「每次请求查 Redis + 渲染」的写法，对应本章的 `/dyn`。静态化不是改这段代码，而是在活动前把渲染结果写成文件；库存由 `/api` 或下单接口再确认。
- `MiaoshaController` 的售罄标记和限流仍在应用里（第 1、4、10 章）。本章的 `limit_req` 是它们前面的一道粗筛：先按 IP 把超量打成 503，再让应用做「一人一单、售罄、令牌桶」。
- `MQSender`、`MQReceiver` 不在这一层；边缘只负责把页面和静态资源发出去，下单仍走原来的链路。
- 本章的静态页模板在 `scripts/gen_data.py`，和 `GoodsKey.getGoodsDetail` 的字段一一对应；改模板要同时改两边，否则页面和 API 会对不上。

## 边界

- 压测客户端、nginx、Java 上游、Redis 全在同一台 8 核 macOS 上。客户端自己占 300%~450% CPU，静态页的 3.8~4.5 万 RPS 是**客户端先到瓶颈**，不是 nginx 的上限；绝对值只能同轮比较。
- 本章没有第二台机器，没有真实 CDN，没有 TLS/HTTP2/HTTP3，没有内核参数调优，没有 DPDK/XDP。
- 没有 dockerd、没有 kubelet、没有 Ingress Controller。nginx 是宿主机进程；K8s 的对应物是 Ingress，不是本章实测。
- `proxy_cache_valid 2s` 是秒级粒度，实际过期可能多 1 秒；冷启动和过期的测试都等了 6 秒才打，避免边界。
- 缓存测试里的 20 ms 是 `EdgeServer --delayMs` 注入的 `Thread.sleep`，不是真实渲染；真实 Java 渲染在这台机器上是 97~133 µs CPU，不是 20 ms。20 ms 只用来让 256 并发的回源差异看得见。
- 1,000 个商品、8,106 字节是刻意选的量级；商品数变了，回源 QPS = 商品数/TTL 跟着变。
- 1,000 万 QPS 的机器数、带宽、CDN 费用都是除法，没有真的跑 1,000 万；100 万也只跑到 4.5 万/秒的客户端上限。
- gzip 只测了 `text/html`、level 5；Brotli、zstd、静态预压缩（`gzip_static`）没测。生产上静态文件应该预压缩，省掉运行时的 59.3 µs。
- `open_file_cache` 的 2 倍 CPU 收益只在 macOS 上测到；Linux 上要重测。
- `limit_req` 的 zone 是全局共享的，三个端口共用同一个 `rl`；测试之间停了 2.2 秒让令牌桶恢复，连续压测时前一组会影响后一组。
- 没有测 `proxy_cache` 的磁盘 IO 上限、缓存淘汰、缓存目录被清空后的回源风暴；128MB 缓存区只装了 1,000 个 8KB 页面。

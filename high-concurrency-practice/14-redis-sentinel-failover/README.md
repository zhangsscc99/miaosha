# 14 同机 Redis Sentinel 自动切换

库存还是一个热 key。Sentinel 做的是：主库进程不再应答以后，把从库提成新的主库，并让客户端有一个地方可以问「现在写哪一台」。它不把成功扣减拆成两个核，也不给这个键增加 QPS。

这一章在一台机器上起 1 个主库、1 个或 2 个从库、3 个 Sentinel。没有第二台机器，没有网络分区，没有 Redis Cluster，没有 RocketMQ 的 DLedger。`kill -9` 是杀进程，页还在，不是断电。2 毫秒是本机 TCP 代理里的 sleep，不是跨机房。

面试口径在上一层的 [技术报告](../REPORT.md)。原始数字在 `results/*.json`。`pass: true` 才算这组成立。延迟仍是直方图桶的上界。故障转移的时间从发出 `SIGKILL` 之前开始算，进程大约 20 毫秒后消失，这 20 毫秒不单独拿来当切换时间。

## 复现

依赖本机的 Go 1.22。Redis 不在仓库里。

```bash
bash run.sh
```

脚本会把 Redis **7.0.15** 装到 `/tmp/redis-7015`（已经有就直接用），清掉 `/tmp/miaosha-sentinel`，关掉 6379、6380、6381、26379、26380、26381 上的 Redis，测完再关掉。不要对已经有业务数据的实例运行。

## 资源

| 项目 | 这次的值 |
| --- | --- |
| 机器 | 4 vCPU，压测和 Redis 在同一台。`results/env.txt` |
| Redis | 7.0.15，jemalloc 5.2.1。主库 6379，从库 6380，需要时再加 6381。每个数据进程 `maxmemory 64mb`，没有 AOF |
| Sentinel | 26379、26380、26381。`sentinel monitor miaosha 127.0.0.1 6379 <quorum>`。`deny-scripts-reconfig yes` |
| 发现周期 | 进程起来之后执行 `SENTINEL DEBUG info-period 200 publish-period 200`。DEBUG 里的 `PING-PERIOD` 仍是 **1000**，`DEFAULT-DOWN-AFTER` 仍是 **30000**，`ELECTION-TIMEOUT` 是 **10000**。每个主库自己的 down-after 写在它的配置行里，不改这个全局默认 |
| 空进程 RSS | 主库 **6,372 KB**，`used_memory` **1,247,648**。从库 **6,284 KB**，**1,224,344**。三个哨兵 **6,164 / 6,124 / 6,052 KB**。哨兵的 INFO `used_memory` 读出来是 **0**，不拿 0 去规划 |

仓库里的 `RedissonAutoConfiguration` 把 Sentinel 地址注释掉了。这一章没有把这段配置打开，也没有把 Spring Boot 跑起来。

发送 PING 的间隔，在我们编的这份 7.0.15 里，是 down-after 和 `PING-PERIOD` 里较小的那个。down-after 写成 500 时，间隔是 500 毫秒；写成 30000 时，间隔仍是 1000 毫秒。down-after 从最近一次成功的 PONG 算起，不是从 `kill` 算起。

## 手动提升

没有哨兵。从库已经连上主库，再执行 `REPLICAOF NO ONE`。命令返回时 `ROLE` 已经是 master。五次命令耗时是 **88、169、107、86、373 微秒**。

这是提升命令本身。下面的 1.4 秒和 30 秒都不是这 373 微秒。

## down-after 500，三次 kill -9

一个从库，quorum 2，三个哨兵都在。先写入 `stock=100` 并等到从库读到 100，再 `kill -9` 主库。没有在切换窗口里继续写这个键。订阅的是 26379，所以 `+odown` 不一定出现在这一个哨兵的事件里。轮询间隔 5 毫秒。

| | +sdown | 从库 ROLE 变成 master | 第一个 get-master 改口 | 这个哨兵的 +switch-master |
| --- | --- | --- | --- | --- |
| 第 1 次 | 51.5 毫秒 | **1.406 秒** | 1.986 秒 | 2.061 秒 |
| 第 2 次 | 121.9 毫秒 | **1.452 秒** | 2.195 秒 | 2.254 秒 |
| 第 3 次 | 88.2 毫秒 | **1.514 秒** | 2.099 秒 | 2.156 秒 |

三次之后三个哨兵的地址都是 6380，`stock` 仍是 **100**。配置写的是 500 毫秒，`+sdown` 可以比 500 毫秒更短，因为上一次 PONG 可能已经过去了大半个发送间隔。

从库开始应答，比 get-master 改口早大约 **0.6 到 0.8 秒**。这段时间主库已经死了，问哨兵仍会拿到 6379。可用性要算到地址改口，不要只算到 `ROLE`。

三次切换后，6380 的配置文件里没有 `replicaof` 行。这次没有把 6380 重启一遍来确认它会按这个文件以主库身份起来。

## 把 down-after 写成 30000

同一种拓扑，只改这一行，只跑了一次。20.003 秒时，三个哨兵的地址仍是 **6379**，6380 的 `ROLE` 仍是 **slave**。

| 事件 | 距 kill |
| --- | --- |
| 这个哨兵的 +sdown | **30.485 秒** |
| 从库 ROLE 变成 master | **30.834 秒** |
| 这个哨兵的 +odown | 31.584 秒 |
| 第一个 get-master 改口 | 31.724 秒 |
| +switch-master | 31.778 秒 |

`stock` 仍是 100。三个哨兵最后都指向 6380。一次样本不能写成分布。它说明的是：默认那一档不会在 20 秒里切，这一次的主观下线落在 30.5 秒。

## quorum 和多数派

先等三个哨兵互相看见，再关掉其中几个，然后 `kill -9` 主库。没有提升的那两组看了 **15 秒**。

| 配置 | 关掉几个哨兵 | ckquorum | 15 秒里 |
| --- | --- | --- | --- |
| quorum 2 | 2 | `NOQUORUM 1 usable Sentinels`，句子里既有 specified quorum，也有 majority | 没有提升。+sdown 在 1.022 秒。从库 `ROLE` 仍是 slave，状态是 `connect` |
| quorum 1 | 2 | `NOQUORUM 1 usable Sentinels`，只有 majority 那一句 | 1.046 秒出现 +odown 和 +try-failover。**11.238 秒** `-failover-abort-not-elected`。从库仍是 slave |
| quorum 2 | 1 | 问的时候还是 `OK 3 usable Sentinels` | 提升了。从库 1.909 秒成为 master。结束时两个活着的哨兵都指向 6380，被关掉的那个 flags 是 `s_down,sentinel,disconnected` |

quorum 1 仍不够。已知哨兵是 3 个时，授权故障转移要多数派，这一次是 2 票。剩下的那一个投了自己，10 秒选举超时后放弃。DEBUG 里的 `ELECTION-TIMEOUT` 是 10000 毫秒，和 1.046 秒到 11.238 秒的间隔对得上。15 秒里没有第二次提升。

关掉一个之后马上问 ckquorum，文本还可以是 3 个可用，因为那个进程还没被标成 sdown。转移仍然完成了。不能把这句 OK 读成「关掉的哨兵一直算可用」。

没有做网络分区，所以没有看到两个哨兵各选一个主库。

## priority 0

两个从库。6380 的 `replica-priority` 是 100，6381 是 0。哨兵列表里能看到 `slave-priority` 分别是 100 和 0。`kill -9` 主库之后，新主库是 **6380**。6381 的 `ROLE` 是 slave，主库端口是 **6380**，状态 `connected`。从库成为 master 用了 **1.407 秒**。priority 0 没有被选中。

## 主库进程还活着

down-after 800。对主库写 `DEBUG SLEEP 4`，不杀进程。从库在 **1.664 秒**成为 master，当时 `SLEEP` 还没返回（返回在 **4.001 秒**）。旧的 pid 还在。

`SLEEP` 返回之后，两端的 `ROLE` 同时是 master 的观察窗口是 **0.893 秒**（第一次看到到最后一次看到，中间有 2 毫秒的 sleep 和 `ROLE` 的往返）。这段里 `SET ghost 1` 成功了 **374** 次。降级完成在 **4.907 秒**，新主库上的 `ghost` 不在了。`stock` 仍是 **7**。

这 374 次是轮询夹进去的写入，不是 4 秒压测的 QPS。它们说明的是：已经返回 OK 的写入，会在旧进程被改成从库、全量同步时丢掉。Sentinel 没有 fencing。`SLEEP` 期间主库不读命令，所以两端同时对外服务的窗口在它醒来之后，不在 1.664 秒那一下。

## 旧主库空目录重启

先正常切到 6380，新主库上的 `kept` 是 `from-new`。再把 6379 用原来的主库配置、空数据目录拉起来。一个连接不停 `SET kept from-zombie`，直到 6379 的 `ROLE` 变成 6380 的从库。三次：

| | 成功的 SET | 从拉起到变成从库 | 第一次 SET 成功 |
| --- | --- | --- | --- |
| 1 | **96,880** | 1.801 秒 | 4.9 毫秒 |
| 2 | **4,308** | 81.8 毫秒 | 4.8 毫秒 |
| 3 | **74,433** | 1.389 秒 | 3.3 毫秒 |

三次结束时，两边的 `kept` 都是 **from-new**。6379 的配置文件里是 `replicaof 127.0.0.1 6380`。

断开之后重连大约按 PING 的间隔来，所以三次差很多。不要把 1.801 秒和 81.8 毫秒平均成「固定 1 秒」，也不要拿 81.8 毫秒当承诺。三次丢掉的都是已经返回 OK 的写入。

## 切换时复制差多少

一条连接对主库 `INCR`，250 毫秒后 `kill -9`。`loopUs` 大约 250 毫秒，成功次数大约 1.1 万到 1.3 万。这是一条连接打到连接被重置，不是 4 秒窗口，不拿去除。订阅开在 kill 之后，这里的 1.2 秒左右不要拿去替换上面那张 1.406 秒的表。

差定义为最后一次读到的回复减去新主库上的值。

| | 三次的差 |
| --- | --- |
| 直连 | **-1、0、-1** |
| 代理每方向 2 毫秒 | **0、0、0** |

-1 表示从库上比客户端读到的回复多 1。那一次 `INCR` 已经复制过去，回复没读到，主库进程随后没了。不是从库比主库更新。直连这三次没有出现「回复已经返回、从库上没有」的缺口。

2 毫秒代理的 0 不能写成「延迟 2 毫秒也不会丢」。提升完成时，代理已经把读到的字节交出去了。这不是两台机器的 RTT。

把从库指到 `127.0.0.1:1`，`ROLE` 状态变成 `connect`，再对主库做 **2000** 次 `INCR`，然后 `kill -9`。三次新主库上的值都等于冻结时读到的值，差都是 **2000**。Sentinel 仍把这个从库提成了主库。down-after 500 时，源码里允许的断链时间是 down-after 的 10 倍再加主观下线之后的时间。2000 次一条连接的 `INCR` 没有碰到那条线。线本身这次没有量。

## 配置不落盘

down-after 500 的一次切换之后，三个哨兵的配置行都是：

```text
sentinel monitor miaosha 127.0.0.1 6380 2
```

用这三份已经改写的文件重新拉起哨兵，**158.8 毫秒**后三个都指向 6380，flags 里没有 s_down。

再换成全新的配置，监控的仍是已经死掉的 6379。接下来 8 秒，三个 get-master 都停在 **6379**，flags 是 `s_down,master,disconnected`，`num-slaves` 是 **0**。6380 一直是 master。哨兵不会把本机上另一个端口扫出来。

## 强制切换时，问一次和每次都问

主库进程不杀。`SENTINEL FAILOVER` 由一个哨兵发起，旧进程随后被改成从库。客户端在切换前已经写了大约 200 毫秒。这不是 4 秒容量测试，CPU 不引用。

差 = 得到整数回复的 `INCR` 次数 − 新主库上的最终值。

| 客户端 | 写在旧端口 | 写在新端口 | 最终值 | 差 | 两端同时是 master | 旧端口变成从库 |
| --- | --- | --- | --- | --- | --- | --- |
| 出错才重新问 | 122,369 | 67 | 17,606 | **104,830** | 1.885 秒 | 2.053 秒 |
| 每次 `INCR` 前都问 26379 | 24,615 | 26,246 | 36,720 | **14,141** | 1.508 秒 | 1.745 秒 |

122,369 + 67 − 17,606 = 104,830。24,615 + 26,246 − 36,720 = 14,141。

每次都问的那一组 **errors 是 0**，差仍是 14,141。回复成功，不表示这次写入还在最后的主库上。问地址的那一刻，哨兵还可以仍返回旧端口，旧端口也还接受写入。它被改成从库之后，这些写入不在新主库上。

两组的窗口不一样，不要把 104,830 和 14,141 相除当成稳定倍数。

## 问地址要多少核

预热 1 秒，测量 4 秒。没有管线。QPS 按成功次数除以实际窗口。哨兵 CPU 接近 100% 是用满了一个核。

| 做法 | 连接 | QPS | p50 桶 | p99 桶 | 最慢 | 目标 CPU | 客户端 CPU |
| --- | --- | --- | --- | --- | --- | --- | --- |
| get-master | 1 | 56,324 | 不超过 20 微秒 | 不超过 50 微秒 | 3.010 毫秒 | 46.3% | 55.8% |
| get-master | 16 | **223,444** | 不超过 100 微秒 | 不超过 200 微秒 | 5.655 毫秒 | **98.7%** | 188.7% |
| get-master | 64 | 224,040 | 不超过 500 微秒 | 不超过 1 毫秒 | 3.773 毫秒 | 97.2% | 175.5% |
| 主库 GET | 16 | **231,609** | 不超过 100 微秒 | 不超过 200 微秒 | 5.907 毫秒 | **98.8%** | 185.0% |

后面拿去除的是 **223,444**。64 连接是 224,040，1.003 倍，p99 从不超过 200 微秒变成不超过 1 毫秒。1 个连接的 56,324 只有 46.3%，不拿去除。

同一次跑完的主库 `GET` 是 231,609。16 连接的 get-master 是它的 **0.96** 倍。每次点击先问哨兵，大约再占一个核，不是进程内读一个地址。

4 秒空闲、INFO 周期和 hello 都已经缩短到 200 毫秒：主库命令增加 **127**，主库和三个哨兵的 CPU 都是 **0.2%**。默认 INFO 是 10 秒、hello 是 2 秒，这次没有单独量。0.2% 不拿去外推。

`SENTINEL SET miaosha client-reconfig-script /tmp/miaosha-evil.sh` 返回：

```text
ERR Reconfiguration of scripts path is denied for security reasons. Check the deny-scripts-reconfig configuration directive in your Sentinel configuration
```

字段没有写上。

## 扩到 10 万、100 万、1000 万

成功扣减仍是 1 个主库。三个哨兵不把 13.9 万变成 41.7 万。点击 QPS 上去之后，哨兵的个数只在「每个点击都问一次地址」时才跟着涨。

缓存地址、失败或 `+switch-master` 再问：10 万、100 万、1000 万都是这 **3** 个进程。这一章空闲时它们是 0.2% CPU。没有在 1000 万点击旁边再跑一遍。

每个点击都 `get-master`，按 223,444、一个进程一个核来除。64 连接没有更快。45 个进程没有同时跑。客户端当时和哨兵在同一台机器上。

| 点击都问地址 | 进程 | 按官方 10 万/进程去买 |
| --- | --- | --- |
| 10 万 | **1** | 1 |
| 100 万 | **5** | 10 |
| 1000 万 | **45** | 100 |

1 个连接的 56,324 不拿去除。拿去除的话，1000 万是 178 个进程。

## 钱

目录价仍是两套，不在这里改：Redis 社区版 1GB **151.2** 元/月，ECS 2 核 4G **470** 元/月。哨兵打满的是一个核。一个 2 核的机器上，这次没有再跑第二个打满的哨兵，所以不把台数除以 2。

每个点击都问地址，一台 2 核只放一个这样的进程：

| 点击 | 进程 | 月费 |
| --- | --- | --- |
| 10 万 | 1 | 470 |
| 100 万 | 5 | **2,350** |
| 1000 万 | 45 | **21,150** |

地址缓存、3 个哨兵和现有的主库、从库放在一起：按这次的 RSS，三个哨兵合计大约 18MB，额外的 2 核机器是 **0**。1000 万这行少出来的是 **21,150** 元/月。少的是「不要为查询地址去买核」，不是少买库存分片。第 1 章的 14,969 和第 13 章的 302.4 都不在这笔里。

如果把同样的 45 个进程买成社区版 1GB：45 × 151.2 = **6,804** 元/月。按官方 10 万去买是 100 个、**15,120**。哨兵的 INFO `used_memory` 是 0，RSS 大约 6MB，它不是那 1GB 的数据分片。6,804、15,120、21,150 不要相加。

1 个连接的 56,324 如果拿去除，1000 万是 178 个 2 核机器、**83,660** 元/月。当时 CPU 是 46.3%。不要和 21,150 相加。

21,150、6,804、15,120、453.6、83,660、470、2,350 不要相加，也不要和第 1 章的 14,969、第 8 章的 38,070、第 9 章的 71,070、第 11 章的 70,030、第 12 章的 156,040、第 13 章的 19,958.4 相加。

## 这次没有当成优化的事

- 把 373 微秒的 `REPLICAOF NO ONE` 说成故障转移时间。三次 kill 之后从库成为 master 是 1.406 到 1.514 秒，地址改口在 2.0 到 2.3 秒。
- 把 down-after 500 说成至少 500 毫秒才主观下线。三次 +sdown 是 51.5、121.9、88.2 毫秒。
- 把 30.485 秒写成多次测量的均值。30 秒那组只有一次。20 秒时还没切。
- 把 quorum 1 说成一个哨兵就能切。已知 3 个时，它试了一次，11.238 秒放弃，从库没变。
- 把「马上问到 OK 3 usable」说成被关掉的哨兵一直健康。结束时它的 flags 是 s_down。
- 把 2 毫秒代理的差 0 说成延迟下不丢数据，或说成跨机房。从库被指走之后，三次差都是 2000。
- 把直连的 -1 说成从库比主库新。那一次回复没读到，值已经在从库上。
- 把 374 次 `SET` 或 1.1 万次 `INCR` 当成容量。一个是 2 毫秒轮询，一个是大约 250 毫秒的一条连接。
- 把 96,880 和 4,308 平均。三次都丢掉了已经返回的写入，窗口差在重连时刻。
- 把 104,830 除以 14,141。两次强制切换的窗口不一样。每次都问的那一组 errors 是 0，差不是 0。
- 把 56,324 拿去除。CPU 46.3%。64 连接的 224,040 不替换 223,444。
- 把 0.2% 的空闲 CPU 放大。INFO 和 hello 被 DEBUG 缩短到 200 毫秒，而且只有 4 秒。
- 把哨兵的 `used_memory` 0 拿去规划。RSS 是 6,052 到 6,164 KB。
- 把 21,150、6,804、15,120、453.6 加在一起，或加进前面章节的账。热 key 的成功扣减仍然是 1 个主库。

## 面试时怎么说

先说切换时间不是提升命令。`REPLICAOF NO ONE` 五次都在 1 毫秒以内。down-after 500 的三次，从库 1.4 到 1.5 秒开始应答，哨兵地址 2.0 到 2.3 秒才改。写成 30000 的那一次，20 秒时还没动，主观下线在 30.485 秒。

再说 Sentinel 不是带 fencing 的共识。quorum 1、三个哨兵只活一个，会进入故障转移然后 11.238 秒放弃。旧进程被 `SLEEP` 挡住时，从库已经升上去；进程醒来后还有 0.893 秒两边都是 master，374 次已经返回的 `SET` 最后不在新主库上。空目录把旧端口重新拉起来，三次丢掉 96,880、4,308、74,433 次已经返回的 `SET`。从库被故意指走后再写入 2000 次，哨兵仍提升它，新值正好少 2000。

最后把钱说成一笔。库存键还是 1 个主库加第 13 章那个从库。哨兵要不要跟着点击买，只取决于每个请求是不是都 `get-master`。按打满的 223,444 去除，1000 万是 45 个核、21,150 元/月；地址留在进程里，这 45 台不用买。45 个 1GB 数据分片是另一笔 6,804，不要加进去。

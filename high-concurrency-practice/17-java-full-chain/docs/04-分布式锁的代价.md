# 04 分布式锁的代价：为什么秒杀热路径不能用它

> 结论：同一个热点库存 key、8 个线程、同样的扣减逻辑：
> **本地锁 540 万 ops/s，Redis 分布式锁 1.31 万 ops/s，Lua 原子扣减 14.34 万 ops/s。**
> 分布式锁比 Lua 慢 **11 倍**，p99 从 0.17 ms 涨到 **12 ms**，还多出 2.5 万次自旋重试。

## 1. 实验怎么做

`LockBench` 固定 8 个平台线程、每个线程 3,000 次扣减，三种策略：

| 策略 | 临界区 |
|---|---|
| `local` | `synchronized (monitor) { counter-- }`，单 JVM 内 |
| `redlock` | `SET lock token NX PX 3000` → `GET stock` → `DECR` → Lua 校验 token 后 `DEL` |
| `lua` | 一段 Lua：GET + 判断 + DECR |

锁获取失败时 `parkNanos(50µs)` 退避，模拟生产里带 backoff 的自旋（不是无脑忙等）。

## 2. 实测（8 线程 × 3,000 次）

| 策略 | QPS | p50 | p99 | 重试次数 | 说明 |
|---|---:|---:|---:|---:|---|
| 本地 `synchronized` | **5,397,959** | 0.2 µs | 34.3 µs | 0 | 无网络，单 JVM |
| Redis 分布式锁 | **13,078** | 67.5 µs | **12.0 ms** | 25,397 | 每单 4 次 Redis 往返 |
| Redis Lua | **143,428** | 48.0 µs | **0.175 ms** | 0 | 每单 1 次往返 |

三个数量级：本地锁 540 万 → Lua 14 万 → 分布式锁 1.3 万。

## 3. 为什么分布式锁这么慢

一次加锁扣减的完整链路：

```
SET lock NX PX 3000      → 1 RTT
GET stock                → 1 RTT
DECR stock               → 1 RTT
EVAL unlock (compare-del)→ 1 RTT
```

4 次 RTT，本机回环约 50~100 µs，跨机房 1~2 ms。更致命的是**锁竞争**：

- 8 个线程抢同一把锁，任意时刻只有 1 个能进临界区，其余 7 个在退避重试；
- 每次重试又是一次 `SET NX`，把 Redis 打得更满；
- 实测 2.4 万次操作产生 **2.5 万次重试**，等于一半流量在做无用功；
- 重试 + 排队让 p99 达到 12 ms，是 Lua 的 **68 倍**。

而 Lua 只有 1 次 RTT，没有锁、没有重试，Redis 单线程天然串行，反而更快。

## 4. 那分布式锁什么时候必须用

不是"禁用分布式锁"，而是"不要把它放在单 key 热路径上"。这些场景仍然需要：

| 场景 | 为什么需要锁 | 更好的做法 |
|---|---|---|
| 订单创建 + 优惠券核销 + 积分扣减 | 跨多个资源，需要整体互斥 | 本地事务 + 消息最终一致，或 TCC |
| 同一用户重复下单 | 用户维度串行，冲突低 | `SET user:order:{id} NX` 一次性占位，不用可重入锁 |
| 定时任务选主 | 同一时刻只能一个实例跑 | etcd/zk 选主，或 DB 行锁 |
| 库存对账/日切 | 跨 Pod 的批量操作 | 分布式锁 + fencing token，低频可接受 |
| 缓存重建（防击穿） | 只允许一个线程回源 | 本地 `singleflight` + Redis `SETNX` 短锁 |

**订单幂等**尤其要注意：不要用"锁 + 查 + 插"，而是直接用 DB 唯一索引
`UNIQUE(order_no)`，冲突就返回已存在。锁只能降低冲突概率，不能替代唯一约束。

## 5. 如果一定要用，怎么用对

1. **锁要带过期时间**，防止宕机死锁；Redisson 的 watchdog 默认 30 s 续期（每 10 s 续一次）。
2. **释放必须校验 token**，防止 A 的锁过期后被 B 拿到，A 醒来把 B 的锁删了：

```lua
if redis.call('get', KEYS[1]) == ARGV[1] then
  return redis.call('del', KEYS[1])
else
  return 0
end
```

3. **主从架构下锁不可靠**：主库加锁成功、未同步就宕机，从库升主后另一个线程也能加锁。
   要强一致用 RedLock（多数派）或 etcd/zk；但 RedLock 本身在时钟漂移下也有争议。
4. **加 fencing token**：每次加锁返回单调递增的版本号，下游存储校验版本号，
   旧持有者的写会被拒绝——这是比"锁本身"更可靠的防脑裂手段。
5. **锁粒度尽量小**：按 `goodsId`、`userId` 分锁，而不是一把全局锁。

## 6. 容量视角

单热点 key 的分布式锁上限约 **1.3 万 ops/s**（本机、8 线程），跨机房会更低。
这意味着：

- 10 万 QPS 的单商品秒杀，用分布式锁需要 8 个以上"锁分片"，而分片后又回到一致性问题；
- 100 万、1000 万 QPS 完全不可能用锁串行化，必须本地库存 + 批量批发 + 边缘拦截。

所以"分布式锁解决超卖"在低并发 CRUD 系统里成立，在秒杀热路径上是**反模式**。

**省了多少（按第 09 篇的假设）**：10 万 QPS 用分布式锁需要 8 个"锁分片"（每个 3 节点 HA，约 ¥12,000/月），
而且分片后库存总量又要在别处汇总，一致性更难；Lua 单分片 14.3 万 ops/s，10 万 QPS 一个分片（3 节点约 ¥1,500/月）就够。
100 万 QPS 用锁需要 77 个串行单元，已经不可能保证同一件商品的账一致——**这不是钱的问题，是方案不成立**。

## 7. 面试问答

**Q：分布式锁和 Lua 都能防超卖，为什么选 Lua？**
A：Lua 把"读-判断-写"合成一个原子操作，1 次 RTT、无锁竞争；
分布式锁是 4 次 RTT + 排队重试，实测慢 11 倍、p99 高 68 倍。
锁适合跨资源临界区，不适合单 key 扣减。

**Q：Redisson 的看门狗机制了解吗？**
A：加锁时不指定 leaseTime，Redisson 启动一个后台任务每 10 s 把锁续到 30 s，
防止业务没执行完锁就过期。代价是持有锁的进程崩溃后，最多 30 s 才释放；
所以要配合业务超时和 fencing token。

**Q：锁超时了但业务还在跑，怎么办？**
A：两个层面：① 业务侧幂等 + 唯一约束，重复执行不会产生副作用；
② fencing token，让存储层拒绝旧版本持有者的写。仅靠"锁没过期"是不可靠的。

**Q：本地锁 540 万 QPS 是不是说明单机就够了？**
A：不是。本地锁只在单 JVM 内有效，多 Pod 会各扣各的导致超卖；
而且 540 万是纯内存自增，不含 HTTP、DB、JSON。它只能说明"锁本身"不是瓶颈，
瓶颈在跨进程协调。

**Q：秒杀里完全不使用分布式锁吗？**
A：热路径不用。订单落库用唯一索引幂等；用户限购用 Redis `SET NX` 占位；
对账、日切、缓存重建这些低频操作可以用锁。工具要用在对的位置。

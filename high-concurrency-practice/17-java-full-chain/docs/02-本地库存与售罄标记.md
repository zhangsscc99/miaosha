# 02 本地库存缓存与售罄标记：把热点留在 JVM 里

> 结论：把库存扣减压进进程内的分段计数器，热路径 **Redis 调用从 1 次/单降到 0 次/单**；
> 售罄后靠一个 volatile 标记直接拒绝，拒绝能力从 **1.29 万 RPS 提到 4.38 万 RPS**，
> 同时 MySQL 写入从 6,198 条/s 降到 **0**。代价是要处理"多 Pod 分配、少卖、对账"。

## 1. 问题：Redis 也会成为热点

v2 每下一单要执行一次 `EVAL`（读库存 + 判断 + 扣减）。本机 Redis 单实例能跑 20.8 万 EVAL/s，
看起来 10 万 QPS 才用一半，为什么还要本地缓存？

三个原因：

1. **单分片上限**：一个商品一个 key，只能落在一个 Redis 分片；集群加机器并不能拆热 key。
2. **网络成本**：同机房一次 RTT 0.2~0.5 ms，跨可用区 1~2 ms；10 万 QPS 就是每秒 10 万次往返。
3. **售罄后仍然打 Redis**：库存为 0 后，每一个请求还要问一次 Redis"还有吗"，
   这是纯浪费——而秒杀 99% 的请求都发生在售罄之后。

## 2. 设计

### 2.1 分段计数器

进程内用 16 个 `AtomicInteger` 表示本地库存，请求按线程哈希到不同段，降低 CAS 竞争：

```java
int start = (int) (Thread.currentThread().threadId() & 0x7fffffff) % SEGMENTS;
for (int k = 0; k < SEGMENTS; k++) {
    AtomicInteger seg = segments[(start + k) % SEGMENTS];
    while (true) {
        int v = seg.get();
        if (v <= 0) break;
        if (seg.compareAndSet(v, v - 1)) return true;
    }
}
soldOut = true;   // 所有段都空了才置位
return false;
```

`soldOut` 是 `volatile boolean`。一旦为 true，后续请求在 JVM 内直接返回 410，
不碰 Redis、不碰 MQ、不碰 DB。**注意置位条件必须是"遍历完所有段都 ≤ 0"**，
因为只有扣减、没有增加，遍历到全 0 时不可能再有库存。

### 2.2 多 Pod 的库存分配：批发，而不是平分

单机实验里 `reset(stock)` 把全部库存放进本地；生产有 N 个 Pod，不能各拿全量。两种做法：

| 做法 | 问题 |
|---|---|
| 启动时平分 `stock/N` | 流量不均时有的 Pod 卖完、有的剩很多；扩缩容要重新分配 |
| **按 chunk 向 Redis 批发**（本项目 v5） | 一次领 2,000 件，卖完再领；Redis QPS = 订单 QPS / chunk |

批发用一段 Lua 保证"取多少、扣多少"原子完成，不会领超：

```lua
local s = tonumber(redis.call('get', KEYS[1])) or 0
local take = math.min(tonumber(ARGV[1]), s)
if take <= 0 then return 0 end
redis.call('decrby', KEYS[1], take)
return take
```

本地卖完后，只有一个线程拿锁去批发，其它线程短暂等待后继续卖，不会每个线程都打 Redis。

### 2.3 对账

活动结束后，DB 里的 `hc_stock` 并不是实时值（异步模式下没人扣它）。
`/admin/reconcile` 把 `Redis 余量 + 各 Pod 本地余量` 回写 DB，供财务/库存系统核对。
正确性测试就是等 MQ 消费完 → 对账 → 校验订单数 = 库存数、DB 库存 = 0。

## 3. 实测

### 3.1 v2（Redis 扣减）vs v3（本地库存）

| 指标 | v2 Redis | v3 本地 | 变化 |
|---|---:|---:|---|
| 成功 QPS（最佳轮） | 24,044 | **31,460** | +31% |
| p50 | 2.27 ms | **1.79 ms** | -21% |
| p99 | 8.71 ms | **6.31 ms** | -28% |
| Redis 调用/订单 | 1.0 | **0** | 热路径清零 |
| DB 写语句/订单 | 0.012 | 0.008 | 批量写 |
| 服务端 CPU（采样） | 112% | 92~126% | 基本持平 |

QPS 只涨 31%，是因为单机 HTTP 层和压测客户端先到瓶颈了；真正的收益在**下游成本**：
Redis 从"每单一次"变成"每 2,000 单一次"，10 万 QPS 时 Redis 只需 50 次/s。

### 3.2 售罄后的拒绝能力

库存 100 件，256 并发持续打 10 秒：

| 方案 | 总 RPS | 成功 | 售罄 | DB 写语句 |
|---|---:|---:|---:|---:|
| v0 DB 空转 | 5,850~12,932 | 100 | 8~15 万 | **6,198 条/s** |
| v3 本地标记 | **20,622~43,806** | 100 | 27 万 | **0** |

v0 在售罄后仍然每个请求打一次 DB（`UPDATE ... WHERE stock>0` 影响 0 行，但要走完事务），
10 秒白烧 6 万多次写；v3 在 JVM 内一个布尔判断就返回，DB 完全静默。

### 3.3 正确性

```
100 件库存 / 3,000 个不同用户 / 128 并发
v2: accepted=100, dbOrders=100, dbStock=0, redisStock=0, errors=0  ✅
v3: accepted=100, dbOrders=100, dbStock=0, localStock=0, errors=0 ✅
3 Pod（chunk=10）: accepted=100, dbOrders=100, errors=0           ✅
```

## 4. 扩容到 10 万 / 100 万 / 1000 万 QPS

以"回源到应用"的 QPS 计算（边缘拦截见第 06/09 篇）：

| 回源 QPS | 单 Pod 规划 | Pod 数（1.5 倍余量） | Redis 批发 QPS（chunk=2,000） | 备注 |
|---:|---:|---:|---:|---|
| 10 万 | 20,000 | 8 | 50 | Redis 几乎空闲 |
| 100 万 | 20,000 | 75 | 500 | 单 Redis 主从足够 |
| 1000 万 | 20,000 | 750 | 5,000 | 建议边缘挡掉 95%，回源 50 万 → 38 Pod |

**单 Pod 20,000 QPS 是怎么来的？** 实测 31,460 QPS 时服务端进程约 1.26 核
（`ps` 采样），即每请求约 40 µs CPU；4 核打满理论 10 万 QPS，按 50% CPU 余量取 2 万，
已经非常保守。真正的限制往往不是 CPU，而是：客户端连接数、网卡软中断、日志、GC。

**内存**：16 个 `AtomicInteger` + 一个布尔，不到 1 KB；库存百万级也只是一个 int。
所以本地缓存的资源成本可以忽略，收益是省掉整个 Redis 热路径。

## 5. 坑与边界

| 坑 | 现象 | 处理 |
|---|---|---|
| 售罄标记误置位 | 还有库存却全部 410 | 必须遍历完所有段再置位；回滚时 `soldOut=false` |
| Pod 崩溃丢库存 | 领了 2,000 件没卖完，Pod 挂了 → 少卖 | 优雅停机时把本地余量退回 Redis；或 chunk 设小 + 短租约 |
| 多 Pod 超卖 | 各 Pod 各拿全量 | 只能走 Redis 原子批发/配额，不能各自 `reset(stock)` |
| 本地与 Redis 不一致 | 对账对不上 | 活动结束停写 → 汇总本地+Redis → 回写 DB；不要在线逐单调和 |
| 滚动发布 | 新 Pod 从 0 开始，老 Pod 还握着库存 | 新 Pod 启动即批发；老 Pod 下线前退回；或按版本号隔离库存 key |
| 补偿导致负库存 | 入队失败回滚本地，但 Redis 已扣 | 回滚只加本地，活动后对账吸收差值；严格场景用 Redis 补偿脚本 |

**省了多少（按第 09 篇的假设）**：100 万 QPS 时，v2（Redis 扣减）需要 150 个应用 Pod + 30 个 Redis 节点，
约 ¥83,500/月；v3（本地库存）只需 75 个 Pod + 3 个 Redis 节点，约 ¥40,000/月，
**每月省 ¥43,500**，其中 Redis 省 ¥13,500、应用 Pod 省 ¥30,000。1000 万 QPS 时这个差距扩大到 **¥448,500/月**。

## 6. 面试问答

**Q：本地缓存库存，多个 Pod 怎么保证不超卖？**
A：库存的"总量"只在 Redis 里做一次原子批发，每个 Pod 只能卖自己领到的 chunk；
本地扣减不需要跨进程同步，所以不会超卖。可能少卖（Pod 挂了、chunk 没用完），
用优雅停机退回 + 活动结束对账解决，秒杀场景"少卖"比"超卖"可接受。

**Q：为什么用 16 段而不是一段 AtomicInteger？**
A：单段 CAS 在 3 万 QPS 下会有明显竞争（缓存行乒乓）。分段后每段独立缓存行，
冲突概率降到 1/16；实测 p99 从 v2 的 8.7 ms 降到 6.3 ms，有一部分就是这里的贡献。
段数不是越多越好，16~64 足够，太多会增加遍历空段的成本。

**Q：售罄标记会不会把后来的补库存挡住？**
A：会。所以补库存/回滚时必须显式 `soldOut=false`；生产上库存变更走统一入口，
不允许直接改 Redis key。更严谨的做法是带版本号，版本变化时重置本地缓存。

**Q：为什么不在网关层做本地库存？**
A：可以，而且 10 万以上 QPS 往往就这么做（边缘节点/网关持有配额）。
但网关通常多租户、内存受限、发布频繁，库存这种强业务状态放在应用层更好治理；
本项目把"批发 + 售罄标记"做成通用模式，放哪一层都成立。

**Q：本地缓存会不会导致 Redis 和 DB 的库存长期不一致？**
A：活动期间本来就不以 DB 为准，DB 是"冷存储"；活动结束停写后对账一次。
如果业务要求实时可查，可以异步把 Redis 余量同步到 DB（每秒一次），
但不要每单同步写 DB，否则又回到 v0 的瓶颈。

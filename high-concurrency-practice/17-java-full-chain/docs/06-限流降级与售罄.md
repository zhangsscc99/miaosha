# 06 限流、降级与售罄：让系统"优雅地拒绝"

> 结论：当入口被打到 3.15 万 RPS 时，5,000/s 的令牌桶让系统只放行 5,009/s，
> 其余 **40 万次请求在 47 ms 内拿到 429**，服务端 CPU 稳定在 93%、0 错误；
> 售罄后本地标记把拒绝能力从 1.29 万 RPS 提到 **4.38 万 RPS**，DB 写入归零。

## 1. 秒杀的真相：绝大多数请求注定失败

一场 1 万件库存、100 万人参与的秒杀：

- 99% 的用户抢不到；
- 流量在开抢后 1~3 秒内达到峰值；
- 其中相当一部分是脚本/黄牛，重复请求率极高。

如果每个"抢不到"的请求都要走完整链路（网关→应用→Redis→DB），系统会被无效流量打死。
所以高并发秒杀的第一原则不是"接住所有请求"，而是**用最便宜的方式拒绝掉 99%**。

## 2. 分层限流

```
CDN / 边缘节点      → 静态售罄页、活动未开始页、IP/UID 频控（挡 80~95%）
      ↓
API 网关（Nginx/Envoy）→ 全局限流、连接数限制、黑白名单
      ↓
应用入口（本实验）   → 单机令牌桶 5,000/s，超出 429
      ↓
用户级限流（Redis）  → 同一 userId 每秒最多 N 次（防脚本）
      ↓
业务层              → 一人一单、库存判断
```

每一层都只做自己最擅长的事：边缘挡静态流量，网关挡连接/全局速率，
应用挡突发，Redis 挡单用户刷接口。不要指望一层解决所有问题。

## 3. 令牌桶实现

```java
// 每 10ms 补充 rate/100 个令牌，桶容量 = burst
scheduler.scheduleAtFixedRate(this::refill, 10, 10, MILLISECONDS);

public boolean tryAcquire() {
    while (true) {
        int cur = tokens.get();
        if (cur <= 0) return false;
        if (tokens.compareAndSet(cur, cur - 1)) return true;
    }
}
```

为什么用令牌桶而不是固定窗口计数：

- 固定窗口在窗口切换瞬间可能放行 2 倍流量（临界问题）；
- 令牌桶允许一定突发（桶容量），又能控制长期速率；
- 漏桶更平滑，但会引入排队延迟，秒杀场景"快速失败"比"排队"体验更好。

## 4. 实测：过载保护

v4 = v3 + 5,000/s 令牌桶，256 并发，库存 500 万（保证不是售罄导致失败）：

| 指标 | 第 1 轮 | 第 2 轮 | 第 3 轮 |
|---|---:|---:|---:|
| 总 RPS（客户端尝试） | 31,521 | 19,304 | 13,432 |
| 成功（202） | 5,009 | 5,013 | 5,016 |
| 429 次数 | 408,398 | 230,377 | 134,730 |
| 成功请求 p99 | 47.1 ms | 88.5 ms | 132.3 ms |
| 错误（5xx） | 0 | 0 | 0 |
| 服务端 CPU | 93% | 93% | 93% |

看点：

1. **放行速率精确**：三轮都稳定在 5,009~5,016/s，误差 <0.4%；
2. **拒绝很便宜**：429 在应用入口返回，不碰 Redis/MQ/DB；
3. **p99 变差是正常的**：256 并发下，令牌桶每秒只放 5,000 个，其余请求要排队等令牌
   （我们的实现是立即失败，p99 仍受客户端调度影响），但**系统没有雪崩**；
4. **0 个 5xx**：说明限流把压力控制在了下游能力之内。

> 如果业务希望"排队"而不是"立即 429"，可以把令牌桶换成有界队列 + 排队页，
> 但队列长度必须有限，否则延迟无限增长，等价于雪崩。

## 5. 售罄标记：最便宜的拒绝

售罄后的请求不应该再查 Redis/DB。v3 用一个 `volatile boolean soldOut`：

```java
if (soldOut) return 410;   // 不进任何下游
```

| 方案 | 总 RPS | DB 写语句/s | 说明 |
|---|---:|---:|---|
| v0（DB 判断） | 5,850~12,932 | **6,198** | 每个请求一次无效 UPDATE |
| v3（本地标记） | **20,622~43,806** | **0** | JVM 内布尔判断 |

在 1000 万 QPS 的场景，这个标记就是"要不要动用边缘节点"的分界线：
如果每个边缘节点都能拿到"已售罄"，99% 的请求连回源都不需要。

## 6. 降级预案

| 级别 | 触发 | 动作 |
|---|---|---|
| L1 | 入口 QPS > 阈值 | 开启令牌桶，429 + `Retry-After` |
| L2 | Redis 超时/错误率 > 5% | 切换到本地配额模式，停止跨 Pod 扣减 |
| L3 | MQ 积压 > 10 万 | 降级为"排队中"，暂停非核心消费（积分、短信） |
| L4 | DB 主库不可用 | 只读模式：展示售罄/活动结束，停止下单 |
| L5 | 机房故障 | 切流到备用机房，活动延期公告 |

降级要**提前配置、提前演练**，不能等故障时改代码。每个降级开关都要有：
谁触发、影响面、恢复条件、监控指标。

## 7. 容量：限流器本身要多少资源

令牌桶是纯内存 CAS，单机 5,000/s 的限流器开销可以忽略（实测 CPU 93% 主要来自 HTTP 和 MQ）。
真正的成本在网关层：

| 层 | 单节点能力（4c8g） | 10 万 RPS | 100 万 RPS | 1000 万 RPS |
|---|---:|---|---|---|
| Nginx/Envoy 网关 | 5~10 万 RPS | 2 台 + HA | 20 台 | 200 台（必须边缘拦截） |
| 应用令牌桶 | 与业务同进程 | 5~10 Pod | 50~100 Pod | 500+ Pod |
| 边缘/CDN | 百万级 | 可选 | 建议 | **必须**，挡 95% |

限流阈值怎么定：**下游容量 × 0.7**。比如 MySQL 能扛 5,000 写/s、每单 0.01 条写，
那 DB 不是瓶颈；Redis 能扛 10 万 EVAL/s，应用单 Pod 能扛 2 万 QPS，
那单 Pod 限流就设 1.5 万，留 25% 余量给突发和 GC。

## 8. 坑

| 坑 | 现象 | 处理 |
|---|---|---|
| 限流粒度太粗 | 正常用户被误伤 | 按 userId/IP/商品多维度，白名单 |
| 集群限流用本地令牌桶 | 10 个 Pod 各放 5,000 → 实际 5 万 | 要么网关统一限，要么 Redis 集中计数（有成本） |
| 429 没有 Retry-After | 客户端立刻重试，流量翻倍 | 返回退避时间 + 前端倒计时 |
| 限流阈值拍脑袋 | 要么没保护，要么把业务限死 | 压测找拐点，按下游容量 × 0.7 |
| 售罄标记不同步 | 边缘还显示有货，回源全 410 | 活动状态用短 TTL 缓存 + 主动推送失效 |
| 降级开关没演练 | 真故障时开关无效 | 混沌工程/定期演练 |

## 9. 面试问答

**Q：限流和降级的区别？**
A：限流是"主动丢弃一部分流量，保住整体"；降级是"关掉非核心功能，把资源让给核心链路"。
限流通常在入口，降级在业务层；两者要配合，先限流再降级。

**Q：令牌桶的 rate 和 burst 怎么定？**
A：rate = 下游安全容量 × 0.7；burst 一般取 rate 的 1~2 秒量，允许短突发。
秒杀场景 burst 不宜太大，否则瞬时打穿下游；可以按"每秒放量"精确控制。

**Q：为什么 429 比排队好？**
A：排队的延迟不可控，用户等 30 秒最后还是失败，体验更差，还占着连接/线程。
快速失败 + 明确提示 + 稍后重试，对系统和对用户都更好。

**Q：边缘节点怎么知道已售罄？**
A：活动状态/售罄标记用短 TTL（1~5 秒）缓存在边缘，卖完后由服务端主动 purge；
允许几秒不一致，因为边缘只是"减少回源"，最终一致性由源站库存保证。

**Q：限流会不会把真实用户挡在外面？**
A：会，所以要分层：边缘按 IP/UID 频控挡脚本，应用按全局速率保系统，用户级限流防刷。
真实用户通常只发 1~2 个请求，被误伤概率低；黄牛才是主要目标。

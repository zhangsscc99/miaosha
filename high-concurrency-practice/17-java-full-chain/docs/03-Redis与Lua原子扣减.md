# 03 Redis + Lua 原子扣减：把串行点前移到内存

> 结论：用一段 Lua 把"读库存 + 判断 + 扣减"合成一个原子操作，
> 不需要分布式锁、不会超卖；单机实测 **208,116 次 EVAL/s**，
> 业务侧每单一次 EVAL 时 QPS 从 4,721 提到 **17,473~18,622**（约 3.9 倍），p50 从 12.8 ms 降到 2.7 ms。

## 1. 为什么必须是 Lua

错误写法一：先 `GET stock`，再 `DECR`。两个命令之间可能被其它请求插入，
两个线程都看到 1，都扣，库存变成 -1（超卖）。

错误写法二：`SETNX` 分布式锁包住 `GET + DECR`。能防超卖，但每单 3 次以上网络往返
（加锁、读、扣、解锁），热点 key 上锁竞争会把 p99 拉到十几毫秒（第 04 篇实测 1.3 万 ops/s）。

正确写法：Lua 脚本在 Redis 单线程里一次执行完，中间不会插入其它命令：

```lua
local s = tonumber(redis.call('get', KEYS[1]))
if (not s) or s <= 0 then return -1 end
return redis.call('decr', KEYS[1])
```

返回 `-1` 表示售罄，否则返回扣减后的余量。Java 侧：

```java
Object r = jedis.eval(DEDUCT_LUA, List.of("hc:stock:" + goodsId), List.of());
long left = (Long) r;
```

## 2. EVAL、EVALSHA 与集群

| 方式 | 每次传输 | 适用 |
|---|---|---|
| `EVAL` | 整个脚本（约 120 B）+ 参数 | 实验/低频，简单 |
| `EVALSHA` | 40 B 的 SHA1 | 生产，脚本启动时 `SCRIPT LOAD` |
| `EVALSHA` 失败回退 `EVAL` | 兜底 | Redis 重启后脚本缓存丢失 |

生产用 Lettuce/Redisson 时通常 `RScript` 自动处理 EVALSHA + 回退。
本项目为了少依赖直接 `EVAL`，对 20 万 QPS 的 Redis 来说，多传 80 字节不是瓶颈。

**Redis Cluster 注意**：脚本里的所有 key 必须在同一个 slot。
库存 key 建议带 hash tag：`hc:stock:{goodsId}`，保证 `stock`、`order:users` 等同一商品相关 key 同槽。
但热 key 本身无法靠集群拆分——一个商品再热也只在一个分片，这也是第 02 篇要做本地缓存的原因。

## 3. 实测

### 3.1 Redis 单机上限（redis-benchmark，64 客户端 / 20 万请求）

| 命令 | QPS | p50 |
|---|---:|---:|
| SET | 208,986 | 0.151 ms |
| GET | 210,305 | 0.151 ms |
| INCR | 217,155 | 0.151 ms |
| EVAL（`return redis.call('incr', KEYS[1])`） | 208,117 | 0.151 ms |

Redis 8.10 单实例在本机约 **21 万 ops/s**，这是"内存数据库"这一层的天花板。

### 3.2 业务链路

| 方案 | 成功 QPS（中位/最佳） | p50 | p99 | Redis 调用/订单 |
|---|---:|---:|---:|---:|
| v0 DB 扣减 | 4,721 / 4,784 | 12.8 ms | 24.9 ms | 0 |
| v1 Redis Lua + 同步 DB | 17,473 / 18,622 | 2.7 ms | 12.1 ms | 1 |
| v2 Redis Lua + MQ | 19,389 / 24,044 | 2.3 ms | 8.7 ms | 1 |

应用里一次 EVAL 的 Redis 服务端耗时约 **4.2~4.4 µs**（`INFO commandstats`），
也就是说 1 万 QPS 只占用 Redis 单核约 4%；真正的开销在客户端网络往返和 Java 侧序列化。

### 3.3 不超卖验证

库存 100，3,000 个不同用户并发：

```
accepted=100  dbOrders=100  dbStock=0  redisStock=0  errors=0  ✅
```

## 4. 容量换算：10 万 / 100 万 / 1000 万 QPS

按"每个订单一次 EVAL、单分片规划 10 万 ops/s（实测 20.8 万，留 50% 余量）"：

| 订单 QPS | 需要的 Redis 分片（主） | 集群规格（3 主 3 从） | 说明 |
|---:|---:|---|---|
| 10 万 | 1 | 3 主 3 从，4c8g × 6 | 单分片就够，瓶颈在应用 |
| 100 万 | 10 | 10 主 10 从，4c8g × 20 | 必须按商品分片；单商品热 key 仍在一个分片 |
| 1000 万 | 100 | 100 主 100 从 | 不现实；正确做法是本地库存/边缘拦截，把 Redis 调用降到订单数/chunk |

**内存**：`hc:stock:{id}` 一个 key 约 100 B，1 万个商品不到 1 MB；
真正的内存消耗在用户维度（一人一单去重、令牌），按 1 亿用户 × 50 B ≈ 5 GB 估算。

**关键结论**：Redis 的 QPS 不是靠"加机器"解决的。单商品热 key 只能：
① 本地缓存/批量批发（第 02 篇）；② 库存分段（`stock:{id}:0..N`，请求按用户哈希到不同段）；
③ 边缘拦截，让绝大多数请求根本不到 Redis。

## 5. 持久化与故障

| 风险 | 说明 | 应对 |
|---|---|---|
| 主从异步复制丢扣减 | 主库扣了，未同步就宕机 → 从库库存偏高 → 超卖 | `WAIT 1 0`（牺牲延迟）、或者接受"少量超卖 + 对账补偿" |
| AOF everysec 丢 1 秒 | 宕机丢最近 1 秒扣减 | 秒杀可接受；订单侧以 DB 唯一索引兜底 |
| Redis 整体不可用 | 所有请求失败 | 入口限流 + 本地配额 + 快速失败；不要让它拖垮整个站点 |
| 大 key / 热 key | 单分片 CPU 打满 | 分段、本地缓存、读写分离（从库读） |
| Lua 脚本死循环/超时 | Redis 单线程被阻塞 | 脚本必须 O(1)、禁止 `KEYS *`、设置 `lua-time-limit` 并告警 |

## 6. 面试问答

**Q：Lua 脚本能保证原子性，那还需要分布式锁吗？**
A：扣库存不需要。Lua 在 Redis 单线程内原子执行，比"加锁-读-扣-解锁"少 3 次往返，
还没有锁超时、误删、主从丢锁的问题。分布式锁适合"跨多个 key/多个资源"的临界区，
比如订单创建 + 优惠券核销，或者用户级串行。

**Q：EVAL 每次都传脚本，不会有性能问题吗？**
A：脚本 100 多字节，相对一次 RTT 可以忽略；高 QPS 用 EVALSHA 只传 SHA1。
真正的性能问题是脚本里做了 O(N) 操作或大 key 遍历，那会阻塞整个 Redis。

**Q：Redis 主从切换会不会超卖？**
A：异步复制下可能丢最后几条扣减，从库库存变多，理论上会超卖。
秒杀通常用"Redis 扣减 + DB 唯一索引 + 最终对账"兜底；要求强一致就用 `WAIT` 或改用 DB 乐观锁，
但吞吐会掉一个数量级。架构是取舍，不是免费的。

**Q：为什么不用 Redis 的 `DECR` 直接扣，还要先 GET 判断？**
A：`DECR` 会把库存减成负数，虽然能靠返回值判断，但负值会污染数据、对账困难，
而且无法在"库存不足"时保持原值。Lua 先判断再扣，语义清晰。

**Q：20 万 QPS 的 Redis 是怎么测出来的？业务里为什么只有 1.7 万？**
A：redis-benchmark 是纯内存命令、无业务逻辑、连接复用；业务链路里还有 HTTP 解析、
JSON、MQ 入队、JVM 调度，且压测客户端和服务端抢 CPU。分层压测的意义就在这：
先知道每一层的天花板，才知道优化哪一层有收益。

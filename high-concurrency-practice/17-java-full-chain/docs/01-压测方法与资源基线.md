# 01 压测方法与资源基线：先把"尺子"校准

> 结论先行：在同一台机器、同一个 512 MB 堆的服务进程、同样的 64 并发下，
> **DB 同步扣减只有 4,721 QPS（p50 12.8 ms）**，这是后面所有优化的参照系。
> 但本机是共享环境，三轮波动 4.0k~4.8k，**看比例，不要迷信绝对值**。

## 1. 为什么要自己写压测客户端

秒杀压测有三个特殊要求，现成工具要么做不到、要么很别扭：

1. **每个请求必须是不同用户**。用 JMeter/ab 复用同一个 userId，会被业务层的"一人一单"逻辑挡住，
   测到的是重复下单拦截，不是库存扣减。
2. **要区分 200/202/410/429/5xx**。秒杀的"失败"分很多种：售罄、限流、排队、系统错误，
   只统计 QPS 会把 429 也算成吞吐。
3. **要精确分位数**。平均值会被长尾掩盖，秒杀看 p99/p999。

所以 `LoadGen` 用虚拟线程 + JDK `HttpClient` 实现：每个线程一个独立 userId 段，
记录成功请求的完整延迟数组，结束后排序算 p50/p90/p99/p999；预热 3 秒后才开始计数，
避免 JIT、连接池、JVM 类加载污染结果。

```java
// LoadGen 核心：每个请求 userId 唯一，成功才记延迟
long uid = base + (seq++);
URI uri = URI.create(url + (url.contains("?") ? "&" : "?") + "userId=" + uid);
```

> 生产环境我会用 k6 / wrk2 / 全链路压测平台；这里自写是为了让实验**可复现、可解释**，
> 不引入外部工具差异。工具不是重点，口径才是。

## 3. 五档实验方案

| 模式 | 扣库存 | 落订单 | 说明 |
|---|---|---|---|
| `v0` | MySQL `UPDATE ... WHERE stock > 0` | 同事务 `INSERT` | 教科书式写法，基线 |
| `v1` | Redis Lua 原子扣减 | 同步 `INSERT` | 只把扣减移出 DB |
| `v2` | Redis Lua | RabbitMQ 异步 + 批量 `INSERT` | 热路径不再等 DB |
| `v3` | 进程内分段库存 + 售罄标记 | RabbitMQ 异步 + 批量 `INSERT` | 单机最优路径 |
| `v4` | 同 v3 | 同 v3 | 入口加令牌桶，验证限流保护 |
| `v5` | 本地"批发"库存（一次领 chunk） | RabbitMQ 异步 + 批量 | 多 Pod 水平扩容用 |

所有模式共用同一个 HTTP 接口、同一个压测客户端、同一个数据库表：

```
GET /seckill?goodsId=1&userId=123
200 扣减并落库成功（v0/v1）
202 已受理，排队落库（v2~v5）
410 售罄
429 被限流
503 队列满，背压拒绝
```

## 4. 基线 v0：瓶颈到底在哪

```sql
-- 一个事务里两条 SQL
UPDATE hc_stock SET stock = stock - 1 WHERE goods_id = ? AND stock > 0;
INSERT INTO hc_order(order_no, user_id, goods_id, status, create_time) VALUES (?,?,?,0,NOW(3));
```

实测（第 1 轮，64 并发）：

```
成功 QPS      4,721
p50          12.77 ms
p99          24.91 ms
服务端 CPU    约 0.7 核（进程平均 72%）
MySQL 写语句  7,841 条/s（2 条/单）
```

三个瓶颈叠加：

1. **行锁串行化**：同一件商品的 `UPDATE` 要对同一行加排他锁，64 个并发在数据库里排队，
   应用层并发再高也没用；
2. **两倍写放大**：扣库存 + 插订单，每单 2 条写 SQL，还要各自走 redo log / binlog；
3. **事务提交 fsync**：InnoDB 默认 `innodb_flush_log_at_trx_commit=1`，每单一次落盘。

所以 v0 不是"代码写得不好"，是**架构上把串行点放在了最慢、最难扩容的一层**。
后面所有优化，本质都是在把这个串行点往内存/Redis 前移，并把 DB 写改成批量。

## 5. 三轮波动：为什么同代码 QPS 会差一倍

同一份 v3 代码，三轮分别是 **31,460 / 19,405 / 13,733 QPS**。原因不是代码，是机器：

```
13:00  up 32 days, load averages: 13.70 12.42 10.80   # 8 核机器
WebKit 84% + 25%，Devin 33% + 21%，Hermes/IDE 若干
```

压测期间服务端进程只用了 1.0~1.6 核，客户端和后台进程在抢剩下的核。
CPU 被抢 → 客户端发包变慢 / 服务端线程被调度延迟 → p99 从 6 ms 涨到 30 ms → QPS 掉一半。

这件事本身是一个生产结论：

> **容量规划必须按 CPU 而不是 Pod 数来算**。K8s 里 `limits.cpu` 设得太紧会触发 CFS throttling，
> 表现和这里的"后台进程抢 CPU"一模一样：QPS 断崖、p99 飙高、但错误率为 0。
> 所以第 08 篇会专门讲 requests/limits、CPU 余量和 HPA 滞后。

文档里的表格同时给中位数和最佳值：

- **中位数**：更接近"这台机器日常状态"，用于保守估算；
- **最佳值**：更接近"服务独占 CPU"的理想状态，用于看代码上限。

## 6. 指标口径

| 指标 | 定义 | 为什么重要 |
|---|---|---|
| 成功 QPS | 每秒 200/202 的数量 | 真正的有效吞吐 |
| 总 RPS | 所有响应（含 410/429） | 售罄后看系统"拒绝能力" |
| p50 / p99 / p999 | 成功请求的延迟分位 | 秒杀看尾延迟，不看均值 |
| DB 写语句/订单 | `Com_insert + Com_update` 增量 ÷ 订单数 | 衡量 DB 写放大 |
| Redis 调用/订单 | `cmdstat_eval` 增量 ÷ 订单数 | 衡量 Redis 是否在热路径 |
| 服务端 CPU/RSS | 每秒 `ps -o %cpu,rss` 采样 | 判断瓶颈在应用还是下游 |
| 对账结果 | 订单数、DB 库存、Redis/本地余量 | 不超卖、不少卖 |

## 8. 面试问答

**Q：为什么不用 JMeter？**
A：用过，但秒杀要"每请求不同 userId + 精确分位 + 区分 429/410"，JMeter 要用 CSV 参数化 +
聚合报告二次计算，脚本反而更重。工具无所谓，关键是口径一致、可重复。

**Q：QPS 和 TPS 的区别？**
A：QPS 是请求数，TPS 是"完整业务事务"数。秒杀里一个下单请求可能对应多次 Redis/DB 操作，
我文档里的 QPS 指 HTTP 请求，DB 侧单独用"写语句/s"和"订单/s"衡量，不混用。

**Q：压测机自己会不会是瓶颈？**
A：会，而且这次就是。判断方法：压测机 CPU 打满、服务端 CPU 没满、QPS 不随并发线性涨。
所以我同时记录服务端 CPU，并在第 08 篇用"每请求 CPU 时间"反推单 Pod 容量，而不是直接拿 QPS 除。

**Q：为什么只压 15 秒？**
A：秒杀是脉冲场景，15 秒足够让队列、连接池、GC 进入稳态；更长会引入机器负载变化。
生产全链路压测一般 10~30 分钟，并做阶梯加压找拐点。

**Q：怎么保证压测结果可信？**
A：同一份代码跑 3 轮、同一口径、同时采服务端 CPU 和下游写入量，三个来源能对上
（例如 v3 的 331,817 个 202 对应 MQ persisted 331,817、DB 订单 331,817），
对不上就说明有丢失或统计错误。

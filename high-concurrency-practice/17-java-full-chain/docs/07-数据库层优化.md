# 07 数据库层优化：数据库不该出现在秒杀热路径

> 结论：v0 用 MySQL 行锁扣库存，每单 2 条写 SQL，只能跑 **4,721 QPS**；
> 把扣减移到 Redis/本地、订单改为 **200 条一批**落库后，
> 每单 DB 写语句降到 **0.008~0.012 条**，MySQL 写压力从 7,841 条/s 降到 **111 条/s**。
> 数据库没有被"优化得更快"，而是被**移出了热路径**。

## 1. v0 到底慢在哪

```sql
BEGIN;
UPDATE hc_stock SET stock = stock - 1 WHERE goods_id = ? AND stock > 0;
INSERT INTO hc_order(...) VALUES (...);
COMMIT;
```

| 开销 | 说明 |
|---|---|
| 行锁 | 同一 `goods_id` 的所有请求串行排队，64 并发在 InnoDB 里变成一条队列 |
| 两次写 | 库存行 + 订单行，各自 redo/binlog，写放大 2 倍 |
| 两次索引维护 | 订单表还有 `UNIQUE(order_no)`、`KEY(goods_id)` |
| 每次提交 fsync | 默认 `innodb_flush_log_at_trx_commit=1`，一单一次落盘 |
| 连接占用 | 每个请求占一条连接直到提交，池子再大也只是把排队挪到池子 |

实测 4,721 QPS、p50 12.8 ms、p99 24.9 ms；MySQL 写语句 7,841 条/s（约 3,900 单/s）。
这不是 SQL 写得不好，是**串行点选错了**。

## 2. 优化一：把扣减移出 DB

库存扣减是"单行热点写"，天然不适合关系库。移到 Redis Lua（第 03 篇）或本地库存（第 02 篇）后，
DB 只负责"订单持久化"，而订单是**可以批量、可以异步**的。

## 3. 优化二：批量插入

```java
try (PreparedStatement ps = cn.prepareStatement(
        "INSERT INTO hc_order(order_no,user_id,goods_id,status,create_time) VALUES(?,?,?,0,?)")) {
    for (OrderRow r : rows) { ps.set...; ps.addBatch(); }
    ps.executeBatch();
    cn.commit();
}
```

连接串加 `rewriteBatchedStatements=true`，MySQL 驱动会把 200 条 batch 改写成一条多值 INSERT。
200 条一提交，提交次数减少 200 倍，这是 DB 写压力下降的主因。

批量大小的取舍：

| 批量 | 吞吐 | 延迟/风险 |
|---:|---|---|
| 1 | 最低 | 每单一次 fsync |
| 50 | 高 | 事务短，较安全 |
| 200 | 很高 | 推荐，单事务 <10 ms |
| 1000+ | 最高 | 事务长、锁多、失败回滚代价大、GC 压力 |

## 4. 优化三：唯一索引做幂等

```sql
UNIQUE KEY uk_order_no (order_no)
```

消费端重复消费时，第二次插入会报 1062；捕获后当作成功，不再插入。
比"先 SELECT 再 INSERT"可靠：并发下 SELECT 查不到，两边都会插。

订单号生成：`业务前缀 + 用户/商品 + 秒杀活动 + 雪花ID/序号`，全局唯一、可追溯。
不要用 `UUID` 做主键（随机写放大），用自增/雪花做聚簇索引，订单号做唯一二级索引。

## 5. 优化四：分库分表（真正的百万级订单）

秒杀的订单量不等于入口 QPS。1,000 万 QPS、10 万件库存，最终只有 10 万订单；
真正需要分片的是"订单写入速率"：

| 订单/s | 单库能力（8c32g，批量写） | 分片数 |
|---:|---:|---:|
| 5,000 | 5,000/s | 1 主 1 从 |
| 5 万 | 5,000/s | 10 主 10 从 |
| 50 万 | 5,000/s | 100 主 100 从（不现实，必须拉长放量时间） |

分片键：`goods_id`（同一商品订单落同库，便于统计）或 `user_id`（便于用户查单）。
秒杀场景建议 `goods_id` 分片 + 异步同步到用户维度索引表；跨分片查询走 ES/数仓。

**分库分表不是越早越好**：单表 1,000 万行、写入 5,000/s 以内，单库完全够；
过早分片会带来分布式事务、跨库分页、扩容迁移的复杂度。

## 6. 优化五：连接池与参数

| 项 | 建议 | 原因 |
|---|---|---|
| Hikari `maximumPoolSize` | 单 Pod 8~16（异步消费者），不是 100 | 连接是 DB 的稀缺资源，池子越大锁竞争越强 |
| 总连接数 | Pod 数 × pool ≤ `max_connections` × 0.8 | 500 Pod × 32 = 16,000，DB 直接拒绝 |
| `innodb_buffer_pool_size` | 物理内存 60~70% | 热索引/数据常驻 |
| `innodb_flush_log_at_trx_commit` | 2（可容忍 1 秒丢失） | 批量写吞吐提升明显；金融场景保持 1 |
| `sync_binlog` | 100~1000 | 减少 binlog fsync；主从延迟可接受 |
| `max_connections` | 按上面公式反推 | 不够就用 ProxySQL/PgBouncer 连接池 |

**一个容易忽略的点**：异步下单后，应用侧只需要少量连接做批量写，
不需要每个 Web 请求一条连接。v2/v3 的 Hikari 池设 32 是因为实验里还兼做对账/统计，
生产批量消费者 4~8 条连接就够。

## 7. 读写分离与归档

- 写：主库，只承接订单插入/状态更新；
- 读：从库，商品详情、订单查询、后台报表；
- 秒杀开始前把商品详情预热到 Redis/本地缓存，读请求不打 DB；
- 订单表按月分区/归档，历史订单迁到冷库，控制单表大小。

## 8. 实测对比

| 方案 | QPS（中位/最佳） | 每单 DB 写 | MySQL 写/s | p99 |
|---|---:|---:|---:|---:|
| v0 同步扣减+插单 | 4,721 / 4,784 | 2.0 | 7,841 | 24.9 ms |
| v1 Redis + 同步插单 | 17,473 / 18,622 | 1.0 | 9,705 | 12.1 ms |
| v2 Redis + MQ 批量 | 19,389 / 24,044 | 0.012 | 120 | 8.7 ms |
| v3 本地 + MQ 批量 | 19,405 / 31,460 | 0.008 | 111 | 6.3 ms |

注意 v1 的 DB 写/s 反而比 v0 高（9,705），因为它把扣减移走后，DB 只插订单，
单条 INSERT 更快、并发更高——这正好说明**瓶颈转移了**：从行锁变成插入吞吐，
再加批量写才真正解决。

**省了多少（按第 09 篇的假设）**：10 万订单/s 时，同步方案每单 2 条写 = 20 万写/s，
按单库 5,000 写/s 要 40 个主库（¥12 万/月）；批量写后每单 0.012 条、单库 1 个（¥3,000/月），
**每月省约 ¥117,000**。分库分表不是目的，先把"每单 2 条写"降到"每 200 单 1 条写"才是。

## 9. 面试问答

**Q：为什么不用 `SELECT ... FOR UPDATE` 扣库存？**
A：`FOR UPDATE` 会锁行直到事务结束，和 `UPDATE ... WHERE stock>0` 一样是串行，
还多一次查询；而且热点行锁等待会让连接池耗尽。库存扣减应该用原子写或 Redis。

**Q：乐观锁（version）行不行？**
A：可以，但秒杀冲突率极高，大量 CAS 失败重试，吞吐不如 Redis Lua；
乐观锁适合冲突低的场景（比如商品信息更新）。

**Q：订单表怎么设计？**
A：自增/雪花主键 + `order_no` 唯一索引 + `user_id/goods_id` 普通索引 + 状态 + 时间；
按 `goods_id` 分片；历史数据按月归档。不要用 UUID 主键，随机写会打散 B+ 树。

**Q：分库分表后怎么保证订单号唯一？**
A：雪花算法/号段模式生成全局唯一 ID，不依赖 DB 自增；分片键从订单号或用户 ID 解析。

**Q：MySQL 能扛 10 万 QPS 吗？**
A：单机简单点查可以（配缓存），但 10 万次写不行。秒杀的正确做法是让 DB 只处理"成功订单"，
而成功订单受库存限制，通常每秒几千到几万，再用批量写 + 分片撑住。

**Q：为什么批量写能快 80 倍？**
A：不是单条 SQL 变快，是提交次数从"每单一次"变成"每 200 单一次"，
redo/binlog fsync、锁释放、网络往返都摊薄了 200 倍。

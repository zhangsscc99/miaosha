# 10 面试技术报告：秒杀商城高并发实践

> 这份报告可以直接拿去讲 30~45 分钟。结构：
> ① 问题与目标 → ② 基线有多差 → ③ 五次优化，每次一个实测 → ④ 最终架构与正确性 →
> ⑤ 10 万/100 万/1000 万 QPS 的容量与成本 → ⑥ 失败模式与取舍 → ⑦ 面试问答。

---

## 一、问题：秒杀到底难在哪

一句话：**在一个只有几秒钟的脉冲里，把 99% 注定失败的请求用最便宜的方式拒绝掉，
并保证剩下的 1% 不超卖、不少卖、不漏单。**

拆成四个子问题：

| 子问题 | 表现 | 本项目的解法 |
|---|---|---|
| 热点写 | 同一个商品库存行，所有请求串行 | 扣减前移到 Redis/本地内存 |
| 脉冲流量 | 几秒内 10~1000 万 QPS | 边缘拦截 + 分层限流 + 有界队列 |
| 下游脆弱 | DB 连接池、Redis、MQ 被打穿 | 批量写、异步下单、背压 |
| 一致性 | 超卖/少卖/重复订单 | Lua 原子、唯一索引、幂等消费、对账 |

目标不是"支撑 1000 万 QPS 的 CRUD"，而是"在 1000 万 QPS 下只让 10 万单成功，且正确"。

## 二、基线：教科书写法有多差

`v0`：一个事务里 `UPDATE stock = stock - 1 WHERE stock > 0` + `INSERT order`。

实测（8 vCPU 本机，服务 512 MB 堆，64 并发，15 秒）：

```
成功 QPS     4,721
p50         12.77 ms
p99         24.91 ms
MySQL 写     7,841 条/s（2 条/单）
服务端 CPU   约 0.7 核
```

瓶颈不在 Java，在三处：

1. **行锁**：同一 `goods_id` 的 `UPDATE` 在 InnoDB 里排队，64 并发变成一条队列；
2. **写放大**：扣库存 + 插订单，两条写 SQL、两次索引维护；
3. **提交 fsync**：默认每次事务落盘。

**结论：串行点放在了最慢、最难水平扩容的一层。** 后面所有优化，都是把这个点往内存前移。

## 三、五次优化，五个实测

### 优化 1：Redis + Lua 原子扣减（v1）

```lua
local s = tonumber(redis.call('get', KEYS[1]))
if (not s) or s <= 0 then return -1 end
return redis.call('decr', KEYS[1])
```

| 指标 | v0 | v1 | 变化 |
|---|---:|---:|---|
| QPS（中位/最佳） | 4,721 / 4,784 | 17,473 / 18,622 | **×3.9** |
| p50 | 12.77 ms | 2.73 ms | -79% |
| p99 | 24.91 ms | 12.08 ms | -52% |
| DB 写/单 | 2.0 | 1.0 | -50% |

为什么快：扣减从"行锁 + 事务"变成"一次内存操作 + 一次 RTT"，
Redis 单机实测 20.8 万 EVAL/s，业务侧一次 EVAL 服务端耗时 4.2 µs。

### 优化 2：分布式锁 → Lua（横向对比，不是线上方案）

很多人第一反应是"加分布式锁"。我做了微基准（8 线程 × 3,000 次，同一热点 key）：

| 策略 | QPS | p50 | p99 |
|---|---:|---:|---:|
| 本地 synchronized | 5,397,959 | 0.2 µs | 34 µs |
| **Redis 分布式锁** | **13,078** | 67.5 µs | **12.0 ms** |
| **Redis Lua** | **143,428** | 48.0 µs | **0.175 ms** |

分布式锁每单 4 次 RTT + 锁竞争重试（实测 2.5 万次重试），比 Lua 慢 **11 倍**，p99 高 **68 倍**。
**结论：分布式锁不适合单 key 热路径**，适合跨资源临界区、用户级串行、对账/选主。

### 优化 3：MQ 异步下单 + 批量落库（v2）

扣减成功后投递 RabbitMQ，立即返回 202；消费者每 200 条批量 INSERT。

| 指标 | v1 同步 | v2 异步 | 变化 |
|---|---:|---:|---|
| QPS（中位/最佳） | 17,473 / 18,622 | 19,389 / 24,044 | +11% / +29% |
| p50 | 2.73 ms | 2.27 ms | -17% |
| p99 | 12.08 ms | 8.71 ms | -28% |
| **DB 写/单** | 1.0 | **0.012** | **约 80 倍** |
| MySQL 写/s | 9,705 | 120 | 约 80 倍 |
| 消息落库 | — | 393,931 投递 = 393,931 落库 | 0 丢失 |

关键不是 QPS 涨了多少，是 **DB 从"每单一次提交"变成"每 200 单一次提交"**，
提交次数降 200 倍，DB 压力降 80 倍。多出来的 QPS 受限于本机 HTTP/客户端，不是 MQ。

### 优化 4：本地库存 + 售罄标记（v3）

把库存按 16 段放进 JVM，卖完置 `volatile soldOut`；多 Pod 用 Redis "批发 chunk"（v5）。

| 指标 | v2 Redis | v3 本地 | 变化 |
|---|---:|---:|---|
| QPS（最佳） | 24,044 | **31,460** | +31% |
| p50 | 2.27 ms | **1.79 ms** | -21% |
| p99 | 8.71 ms | **6.31 ms** | -28% |
| Redis 调用/单 | 1.0 | **0** | 热路径清零 |
| 售罄后拒绝 RPS | — | **43,806**（v0 仅 12,932） | ×3.4 |
| 售罄后 DB 写/s | 6,198（v0） | **0** | 归零 |

QPS 只涨 31%，因为单机 HTTP 层先到瓶颈；真正的收益是**下游成本**：
10 万 QPS 时 Redis 只需 50 次批发/s，Redis 集群可以从 30 个节点降到 3 个。

### 优化 5：限流 + 降级（v4）

入口令牌桶 5,000/s，256 并发硬打：

| 指标 | 结果 |
|---|---|
| 客户端尝试 | 31,521 RPS |
| 放行 | 5,009/s（误差 <0.4%） |
| 429 | 40.8 万次（15 秒） |
| 5xx | **0** |
| 服务端 CPU | 93% |

限流不是"挡住用户"，是**把系统从雪崩边缘拉回来**：429 在入口返回，不碰 Redis/MQ/DB。

## 四、最终架构

```
                    ┌──────────────────────────────┐
                    │ CDN / 边缘                    │
                    │ 静态页、售罄页、IP/UID 频控     │  挡住 90~95%
                    └──────────────┬───────────────┘
                                   │ 回源
                    ┌──────────────▼───────────────┐
                    │ Ingress / API Gateway         │
                    │ 全局限流、连接数、黑白名单      │
                    └──────────────┬───────────────┘
                                   │
              ┌────────────────────▼────────────────────┐
              │ seckill-api Pod × N（无状态）             │
              │  令牌桶 → 本地库存(分段+售罄标记)          │
              │       → 有界队列 → 单线程 publisher        │
              └───────┬───────────────────────┬──────────┘
                      │ chunk 批发             │ 202 已受理
              ┌───────▼────────┐      ┌───────▼────────────┐
              │ Redis Cluster  │      │ RabbitMQ / RocketMQ │
              │ 库存、活动状态  │      │ 订单消息、DLQ        │
              └────────────────┘      └───────┬────────────┘
                                              │ 批量 200 条
                                      ┌───────▼────────┐
                                      │ MySQL 主从      │
                                      │ 订单、唯一索引   │
                                      └────────────────┘
```

请求生命周期：

1. 边缘判断活动状态/售罄 → 直接返回静态页（绝大多数请求到此结束）；
2. 网关限流/鉴权；
3. 应用令牌桶 → 本地库存扣减（无锁 CAS）；
4. 扣减成功 → 有界队列 → publisher → MQ → 返回 202；
5. 消费者批量落库，唯一索引幂等，ACK；
6. 前端轮询订单状态；活动结束对账（Redis+本地余量 → DB）。

**降级路径**：Redis 不可用 → 本地配额继续卖（少卖可接受）；MQ 积压 → 停止入队并 503；
DB 不可用 → 只读售罄页；整机房故障 → 切流 + 活动延期。

## 五、正确性：比 QPS 更重要

库存 100 件、3,000 个不同用户、128 并发：

| 方案 | accepted | DB 订单 | DB 库存（对账后） | Redis/本地余量 | 结果 |
|---|---:|---:|---:|---:|---|
| v2 Redis+MQ | 100 | 100 | 0 | 0 | ✅ |
| v3 本地+MQ | 100 | 100 | 0 | 0 | ✅ |
| 3 Pod（v5, chunk=10） | 100 | 100 | — | — | ✅ |

三个不变量：

1. **不超卖**：`accepted == stock`；
2. **不少卖**：`dbOrders == stock`（等 MQ 消费完再校验）；
3. **不重复**：`order_no` 唯一索引 + 幂等消费。

对账是最后一道防线：活动结束停写 → 汇总 `Redis 余量 + 各 Pod 本地余量` → 回写 DB →
与订单数交叉校验。差异告警，人工介入。

## 六、10 万 / 100 万 / 1000 万 QPS：资源与钱

按单 Pod 4c8g 规划 2 万 QPS，1.5 倍余量；价格见第 09 篇假设。

| 峰值 QPS | 方案 | 应用 Pod | DB 主库 | Redis 节点 | 月成本 | 节省 |
|---:|---|---:|---:|---:|---:|---:|
| 10 万 | A DB 同步 | 38 | 25 | 0 | ¥91,200 | — |
| 10 万 | C 本地+MQ | 8 | 2 | 3 | **¥13,200** | **-86%** |
| 100 万 | A DB 同步 | 375 | 250 | 0 | ¥901,000 | — |
| 100 万 | C 本地+MQ | 75 | 2 | 3 | **¥40,000** | **-96%** |
| 1000 万 | A DB 同步 | 3,750 | 2,500 | 0 | ¥9,001,000 | — |
| 1000 万 | C 本地+MQ | 750 | 2 | 3 | **¥310,000** | **-97%** |

再加边缘拦截：

| 峰值 | 边缘拦截 | 回源 | Pod | 边缘费用/10 分钟 |
|---:|---:|---:|---:|---:|
| 10 万 | 90% | 1 万 | 1 | ¥30 |
| 100 万 | 90% | 10 万 | 8 | ¥300 |
| 1000 万 | 95% | 50 万 | 38 | ¥3,000 |

**三个反直觉结论**：

1. 1000 万 QPS 的钱主要花在**边缘和带宽**，不是应用服务器；
2. 本地库存方案里 Redis 是"协调者"，1000 万 QPS 也只要 3 个节点；
3. 传统 DB 方案在 100 万 QPS 时不是贵，是**单行热点根本拆不开**——加钱也跑不了。

成本模型最敏感的两个变量：**单 Pod 吞吐**、**边缘拦截率**，不是机器单价。
所以优化顺序：先挡流量，再提单机吞吐，最后谈采购。

## 七、失败模式与取舍

| 失败 | 影响 | 兜底 |
|---|---|---|
| Redis 主从切换丢扣减 | 可能超卖 | `WAIT`、DB 唯一索引、对账补偿 |
| Pod 崩溃丢本地 chunk | 少卖 | preStop 退回、chunk 调小、对账 |
| MQ 消息重复 | 重复订单 | 唯一索引 + 幂等消费 |
| 202 后消息丢失 | 用户看到排队但无订单 | 本地消息表/事务消息 + 对账 |
| 队列积压 | 延迟增长 | 有界队列 + 背压 503 + 限流 |
| HPA 扩容慢 | 峰值打穿 | 提前扩容、热 Pod、边缘拦截 |
| 网关成为瓶颈 | 聚合 QPS 上不去 | Nginx/Envoy，不要用 JVM 写代理（实测只有 4,080 QPS） |

**取舍清单**：

- 强一致 vs 吞吐：选最终一致 + 对账；金融级扣款另说。
- 同步 200 vs 异步 202：选 202，前端轮询；用户体验换系统稳定。
- 本地库存 vs Redis 扣减：选本地，接受"少卖"和对账复杂度。
- 分布式锁 vs Lua：热路径 Lua，跨资源才用锁。
- 自建 vs 云托管：秒杀峰值用云弹性，常态用包年包月。

## 八、如果重做，我会改什么

1. **第一天就上边缘拦截**：这是 1000 万 QPS 唯一现实的解，比任何应用层优化都值钱。
2. **压测机独立**：本次服务端和客户端抢 8 核，v3 在 13.7k~31.5k 之间波动，
   绝对值不够硬；生产压测必须独立发压机 + 固定规格。
3. **用真实网关**（Nginx/Envoy）而不是 JVM 代理：L7 代理自己成了瓶颈。
4. **消息可靠性做成 outbox**：202 之前只保证"进了本地队列"，严格场景需要本地消息表。
5. **可观测性前置**：QPS、p99、队列深度、库存差值、对账差异，四个 dashboard 先于优化。
6. **混沌演练**：Redis 挂、MQ 挂、Pod 被杀、发布中库存退回，这些比 QPS 更能暴露问题。

## 九、20 个面试问答（速查）

1. **秒杀为什么不能用 DB 直接扣？** 行锁串行 + 两倍写 + 每次 fsync，实测 4,721 QPS。
2. **Redis 扣减为什么要 Lua？** 读-判断-扣必须原子，否则超卖；Lua 1 次 RTT 无锁。
3. **分布式锁行不行？** 热点 key 实测 1.3 万 ops/s，比 Lua 慢 11 倍，p99 12 ms，不适合热路径。
4. **本地库存怎么防超卖？** Redis 原子批发 chunk，Pod 只卖自己的；本地扣减无需跨进程同步。
5. **Pod 挂了库存怎么办？** preStop 退回 + 小 chunk + 对账；接受少卖，不接受超卖。
6. **MQ 消息丢了怎么办？** confirm + 持久化 + 手动 ACK + 本地消息表 + 对账。
7. **消息重复怎么办？** 唯一索引 + 幂等消费，不要"先查再插"。
8. **为什么返回 202？** 语义是"已受理"，前端轮询；200 会误导用户。
9. **批量写为什么快？** 提交次数从每单一次变成每 200 单一次，fsync/锁/网络摊薄 200 倍。
10. **DB 连接池开多大？** 异步消费者 8~16 就够；Pod 数 × pool 不能超过 DB 上限。
11. **分库分表键怎么选？** 秒杀按 goods_id（同商品聚合），用户查单走异步索引/ES。
12. **限流阈值怎么定？** 下游安全容量 × 0.7；令牌桶 rate/burst 按秒级放量。
13. **为什么会超卖？** 扣减非原子、主从丢写、本地缓存各自为政、补偿逻辑错误。
14. **怎么保证不少卖？** 对账 + 库存回收 + 活动结束校验订单数；少卖比超卖可接受。
15. **HPA 为什么来不及？** 指标 15s + 控制循环 15s + JVM 冷启动 30s，峰值只有几秒。
16. **K8s 里 JVM 怎么配？** MaxRAMPercentage=70、容器感知、G1/ZGC、优雅停机、AppCDS。
17. **10 万 QPS 要多少机器？** 回源 10 万 → 8 个 4c8g Pod + 3 Redis + 3 MQ + 2 DB，约 ¥1.3 万/月。
18. **1000 万 QPS 呢？** 边缘挡 95% → 回源 50 万 → 38 个 Pod；不挡要 750 个，不现实。
19. **成本花在哪？** 传统方案在 DB/Redis，优化方案在边缘带宽和应用 Pod；机器单价不是最敏感的。
20. **这套方案最大的风险？** 最终一致性（少卖/重复）和对账复杂度；用唯一索引、状态机、对账兜底。

## 十、一页纸总结（电梯陈述）

> 我在秒杀项目里做了一套可复现的高并发实验：从 DB 直接扣库存的 4,721 QPS 起步，
> 依次用 Redis Lua 把扣减原子化（×3.9）、用 MQ 批量落库把 DB 写降 80 倍、
> 用本地分段库存把 Redis 从热路径移除（31,460 QPS，p50 1.8 ms），
> 再用分层限流和售罄标记保证过载时不雪崩（31,521 RPS 冲击下 0 个 5xx）。
> 100 件库存、3,000 个请求（128 并发），最终恰好 100 个订单，不超卖不少卖。
> 按实测 CPU 时间推算，10 万/100 万/1000 万 QPS 分别需要 8/75/750 个 4c8g Pod，
> 相比传统 DB 方案月成本降低 86%/96%/97%；1000 万 QPS 的关键不是服务器，
> 而是用边缘拦截把回源压到 5%。

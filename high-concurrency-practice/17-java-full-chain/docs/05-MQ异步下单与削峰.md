# 05 MQ 异步下单与削峰：把"下单"从请求链路里拿掉

> 结论：扣减成功后不再同步写订单，而是投递消息、立即返回 202；
> 消费端每 200 条批量落库。**每单 DB 写语句从 1.0 降到 0.012（约 80 倍）**，
> MySQL 写压力从 7,841 条/s 降到 111 条/s，QPS 从 17,473 提到 19,389~24,044，
> 且 33 万个订单 **0 丢失、0 重复、0 错误**。

## 1. 同步下单的问题

v1 的链路：

```
HTTP → Redis Lua 扣减 → INSERT 订单 → 返回 200
                          ↑ 用户要等这次 DB 写完
```

即使 Redis 扣减只要 50 µs，同步 INSERT 也要 1~5 ms（还要走 redo/binlog/fsync）。
更麻烦的是**流量脉冲**：10 万人同时点，DB 连接池瞬间打满，请求排队，p99 爆炸。

异步下单把"是否抢到"和"订单落库"拆开：

```
HTTP → Redis/本地扣减 → 投递 MQ → 立即 202（已受理）
                              ↓
                    消费者批量聚合 → 一次 INSERT 200 条 → ACK
```

用户感知的是"排队中"，前端轮询订单状态；DB 按自己的节奏消费，不被入口流量拖着走。

## 2. RabbitMQ 拓扑与可靠性

```
producer ──publish(persistent)──> hc_order_queue (durable)
                                      │ prefetch=2000, manual ack
                                      ▼
                              batch writer (200 条 / 15 ms)
                                      │
                                   MySQL
```

关键配置：

| 配置 | 值 | 作用 |
|---|---|---|
| queue durable | true | broker 重启队列不丢 |
| message deliveryMode | 2（persistent） | 消息落盘 |
| publisher confirm | 开启，每 200 条 `waitForConfirms` | 确认 broker 收到 |
| consumer manual ack | true | 落库成功才 ACK |
| prefetch | 2000 | 控制未确认消息数，避免压垮消费者 |
| 批量大小 | 200 条 / 15 ms | 吞吐与延迟的平衡 |
| 有界队列 | 200,000 | 满了 `offer` 失败 → 503 背压 |

Java 侧生产者是**单线程 + 批量 publish**：RabbitMQ 的 `Channel` 不是线程安全的，
每个请求线程各自建 Channel 会打爆连接；用一个有界队列 + 单 publisher 线程，
既安全又能合并 confirm。

## 3. 实测

### 3.1 吞吐与 DB 压力

| 指标 | v1 同步写 | v2 Redis + MQ | 变化 |
|---|---:|---:|---|
| 成功 QPS（中位/最佳） | 17,473 / 18,622 | 19,389 / 24,044 | +11% / +29% |
| p50 | 2.7 ms | 2.3 ms | -15% |
| p99 | 12.1 ms | 8.7 ms | -28% |
| DB 写语句/订单 | 1.0 | **0.012** | **约 80 倍** |
| MySQL 写语句/s | 9,705 | **120** | 约 80 倍 |
| 消息落库 | — | accepted = persisted | 100% |

第 1 轮 v2：393,931 个 202，`published=393,931`、`confirmed=393,931`、`persisted=393,931`，
`publishFailed=0`、`persistFailed=0`。三个数字对得上，说明没有静默丢失。

### 3.2 批量写为什么能省这么多

- 同步：1 单 = 1 条 INSERT = 1 次事务提交 = 1 次 redo fsync；
- 批量：200 单 = 1 条多值 INSERT（`rewriteBatchedStatements=true`）= 1 次提交。

按 15 万订单算：同步 15 万次提交，批量 750 次，**提交次数减少 200 倍**。
MySQL 的瓶颈往往不是行数，而是事务提交次数。

### 3.3 背压

队列设 20 万上限。当生产速度持续大于消费速度：

```
offer 失败 → 回滚 Redis/本地库存 → 返回 503 → 客户端退避重试
```

实测 33 万订单、多轮压测，`backpressure=0`、`errors=0`；说明在本机消费能力足够。
生产上要监控队列深度和消费延迟，超过阈值就限流入口，而不是无限堆内存。

## 4. 消息不丢、不重的完整方案

本项目是"教学版可靠"：persistent + confirm + manual ack + 唯一索引。
生产还要补三块：

| 问题 | 方案 |
|---|---|
| 202 已返回，但 publish 失败/ broker 宕机 | 本地消息表（outbox）：扣减与"待发送消息"同库事务，后台补发；或 RocketMQ 事务消息 |
| 消费者落库成功、ACK 前宕机 → 重复消费 | `order_no` 唯一索引 + `INSERT IGNORE`/捕获 1062；消费幂等 |
| 消息顺序 | 同一用户的订单不要求严格顺序；若要求，按 userId 哈希到固定队列/分区 |
| 死信 | DLQ + 重试 3 次 + 告警，人工补偿 |
| 积压 | 扩容消费者、提高批量、临时降级非核心消费；监控 lag |

**202 的语义要说清楚**：它只代表"扣减成功且消息已进入本地队列"，
不代表"订单已落库"。前端必须轮询/订阅订单状态，不能拿 202 当成功页。

## 5. RabbitMQ / RocketMQ / Kafka 怎么选

| 维度 | RabbitMQ | RocketMQ | Kafka |
|---|---|---|---|
| 单机吞吐 | 万级~十万级 | 十万级 | 十万~百万级 |
| 延迟 | 微秒~毫秒 | 毫秒 | 毫秒 |
| 顺序消息 | 队列级 | 分区级，支持顺序 | 分区级 |
| 事务消息 | 不支持（需 outbox） | **原生支持** | 支持（较复杂） |
| 延迟消息 | 插件 | 原生 | 不支持 |
| 运维复杂度 | 低 | 中 | 高（依赖 ZK/KRaft） |
| 适合 | 业务解耦、任务队列 | 电商交易、事务消息 | 日志、流处理、超高吞吐 |

秒杀订单场景：RocketMQ 的事务消息/顺序消息最贴合；已有 RabbitMQ 的中小团队也够用；
Kafka 更适合把订单变更流式同步到数仓/风控，而不是直接当订单主链路。

## 6. 容量换算

**关键：MQ 的容量按"成功订单/s"算，不是入口 QPS。**

| 入口 QPS | 库存 | 成功订单/s（峰值） | 消息量 | MQ 规格 |
|---:|---:|---:|---|---|
| 10 万 | 1 万 | 1 万（1 秒抢完） | 1 万条 | 3 节点 4c8g 足够 |
| 100 万 | 10 万 | 10 万（1 秒） | 10 万条 | 3~5 节点，分区 12+ |
| 1000 万 | 100 万 | 100 万（1 秒） | 100 万条 | 6~12 节点；或分批放量，把 1 秒拆成 10 秒 |

如果业务允许"每秒放 1 万库存"，1000 万入口 QPS 也只有 1 万订单/s 的消息量，
MQ 根本不需要跟着入口 QPS 扩容——这就是"削峰"的本质：**用时间换峰值**。

## 7. 坑

| 坑 | 现象 | 处理 |
|---|---|---|
| 202 当成功 | 用户看到"抢到了"但订单没落库 | 状态机：排队中→成功/失败；前端轮询 |
| 消息重复 | 同一订单插两次 | 唯一索引 + 幂等消费 |
| 批量太大 | 一次 2000 条，事务长、锁表、GC | 200~500 条/批，按 DB 能力调 |
| prefetch 太大 | 消费者拿了一堆没处理，宕机后大量重投 | prefetch 与批量匹配，2000 以内 |
| 队列无界 | OOM 或延迟无限增长 | 有界队列 + 背压 + 监控 |
| 消费者单线程 | CPU 用不满 | 多消费者/多线程，按分区或加实例 |

## 8. 面试问答

**Q：为什么用 MQ，不用线程池异步写？**
A：线程池在进程内，Pod 一挂任务就丢；MQ 能持久化、跨实例消费、削峰、重试。
小流量可以用线程池 + 本地队列，上了规模必须外置。

**Q：消息丢了怎么办？**
A：三层：① 生产端 confirm + 失败重发/本地消息表；② broker 持久化 + 副本；③ 消费端手动 ACK，
落库成功才确认。再加一层对账（Redis 扣减数 vs DB 订单数），兜底发现差异。

**Q：消息重复怎么办？**
A：业务幂等。订单用 `order_no` 唯一索引，重复插入捕获唯一键冲突当成功；
不要用"先查再插"，并发下查不到还是会重复。

**Q：为什么返回 202 而不是 200？**
A：200 表示订单已创建；202 表示已受理、异步处理。语义诚实，前端才能正确展示"排队中"。
如果业务强要求同步结果，那就得接受更低的吞吐。

**Q：MQ 积压了怎么处理？**
A：先看是消费慢还是生产突增：消费慢就扩消费者/提高批量/优化 SQL；生产突增就入口限流。
临时可以把消息转到临时队列、多线程消费，但要注意顺序和 DB 压力。根治是容量规划 + 限流。

**Q：RabbitMQ 单队列能不能扛 10 万/s？**
A：单队列在普通机器上通常几万/s，取决于持久化、confirm、消息大小。要更高就多队列/多分区，
或者换 RocketMQ/Kafka。本项目单节点实测 2.4 万/s 订单无压力，瓶颈先在应用 HTTP 层。

# 08 K8s 部署与弹性扩容：扩容速度才是秒杀的生命线

> 结论：应用单 Pod（4c8g）按 **2 万 QPS** 规划，10 万 QPS 需要 8 个 Pod，100 万需要 75 个，
> 1000 万需要 750 个（或边缘挡掉 95% 后回源 38 个）。
> 但 K8s 的 HPA 有 30~60 秒冷启动，秒杀峰值只有几秒——**必须提前扩容，不能等 HPA**。

## 1. 为什么用 K8s

- **弹性**：大促前扩容、结束后缩容，不为 10 分钟的峰值付整月账单；
- **隔离**：CPU/内存 requests/limits 限制单 Pod，避免一个服务打挂整个节点；
- **发布**：滚动更新、灰度、快速回滚；
- **自愈**：探针失败自动重启/摘流量。

但 K8s 不是银弹：它解决"编排"，不解决"单机吞吐"和"下游容量"。秒杀的核心优化
（本地库存、Lua、批量写、限流）在容器里外都一样。

## 2. 资源模型：一个 Pod 能扛多少

实测 v3（本地库存 + MQ）单进程 **31,460 QPS** 时，`ps` 采样服务端约 **1.26 核**，
即每请求约 **40 µs CPU**。换算：

| Pod 规格 | 100% CPU 理论 QPS | 50% CPU 余量 | 规划值（保守） |
|---|---:|---:|---:|
| 2c4g | 50,000 | 25,000 | 10,000 |
| 4c8g | 100,000 | 50,000 | **20,000** |
| 8c16g | 200,000 | 100,000 | 40,000 |

规划值再打一次折（日志、TLS、GC、流量不均），所以 4c8g 取 2 万 QPS。
**不要按"理论值"申请资源**，否则一次 Full GC 或节点争抢就会雪崩。

`deployment.yaml` 里 requests 500m/1Gi、limits 2/2Gi：

- requests 决定调度和 HPA 的 CPU 利用率分母；
- limits 太小会触发 CFS throttling（表现为 p99 周期性尖刺），太大则失去隔离意义；
- JVM 用 `-XX:MaxRAMPercentage=70` 跟随 limit，不要写死 `-Xmx`。

## 3. 探针与优雅停机

```yaml
startupProbe:   /stats  2s × 30   # JVM 启动最多 60s
readinessProbe: /stats  5s × 2    # 失败就摘流量
livenessProbe:  /stats  10s × 3   # 连续失败重启
preStop:        sleep 15          # 先等 kube-proxy/Ingress 摘流量
terminationGracePeriodSeconds: 60
```

顺序很重要：

1. Pod 进入 Terminating，Endpoint 从 Service 摘除（有传播延迟，所以 preStop sleep 15s）；
2. 应用收到 SIGTERM：停止接收新请求 → 等在途请求完成 → 取消 MQ 消费者并 drain →
   **把本地未卖完的库存退回 Redis** → 关闭连接池；
3. 超过 60s 强杀。

如果跳过第 2 步的"退库存"，滚动发布一次就少卖一批库存（第 02 篇的坑）。

## 4. HPA：为什么秒杀不能只靠它

`hpa.yaml` 用了两个指标：

- **CPU 60%**：常规扩容依据；
- **QPS 12,000/Pod**：需要 prometheus-adapter 把 `/stats` 的 QPS 暴露成 Pods 指标。

秒杀场景 HPA 的三个硬伤：

| 问题 | 现实 |
|---|---|
| 指标滞后 | metrics-server 15s 一次，HPA 控制循环 15s，扩容决策至少 15~30s |
| 冷启动 | JVM 启动 + 类加载 + JIT 预热 20~60s；镜像拉取可能更久 |
| 缩容慢 | 默认 stabilization 5 分钟，峰值过去后资源还在烧 |

**正确做法**：

1. **提前扩容**：活动前 10 分钟按预估峰值把 minReplicas 调到目标值（定时伸缩/发布平台）；
2. **预留热 Pod**：维护一批 pause 容器/已预热 Pod，扩容时替换镜像而不是从零启动；
3. **AppCDS / CRaC / Native Image**：把启动从 30s 降到 1~5s（GraalVM native 最快，但生态受限）；
4. **容量兜底**：HPA maxReplicas 要大于预估峰值，否则扩到上限就拒绝服务；
5. **边缘拦截**：让回源 QPS 只有峰值的 5%~10%，扩容压力直接降一个数量级。

## 5. 水平扩容实测（3 进程等价模拟）

`scripts/run_cluster.sh` 用 3 个 JVM（各 384 MB 堆）模拟 3 个 Pod，
客户端按轮询直连 3 个端口（等价 L4 Service），库存走 v5 的"批发 chunk"模式：

```
库存 300 万，chunk=2000，192 并发，15 秒
accepted=88,726  published=88,726  persisted=88,726  errors=0
聚合 QPS=5,055  p50=27 ms  p99=211 ms
3 Pod 正确性：100 库存 / 3000 请求 → accepted=100, orders=100, 0 超卖 ✅
```

**必须诚实说明**：这个 5,055 不是"3 个 Pod 只能扛 5 千"。同一时刻这台 8 核机器上还有
浏览器（WebKit 84%+25%）、IDE、Hermes 等进程；单 Pod 单独测能到 1.0~1.7 万 QPS，
3 个 Pod 一起跑时 CPU 被 5~6 个进程争抢，per-Pod 吞吐反而下降。
**多进程实验证明了"功能正确、可水平部署"，不能当作线性扩容的容量证据**；
容量数字用上面的 CPU 时间模型推导。

顺带一个教训：最初用 Java 写的 L7 轮询代理，聚合只有 4,080 QPS——**代理本身成了瓶颈**。
生产网关必须用 Nginx/Envoy 这类 C/Go 实现，或者直接用 L4 Service/kube-proxy，
不要在请求链路上再放一个 JVM。

## 6. 容量表：10 万 / 100 万 / 1000 万 QPS

按 4c8g / 2 万 QPS 规划，1.5 倍余量（含滚动发布、故障域）：

| 峰值 QPS | 回源比例 | 回源 QPS | Pod 数 | 节点（16 Pod/节点） | 说明 |
|---:|---:|---:|---:|---:|---|
| 10 万 | 100% | 10 万 | 8 | 2~3 台 16c64g | 小促，Redis 单分片够 |
| 100 万 | 90% | 10 万 | 8 | 3 台 | 边缘挡掉 90% |
| 100 万 | 100% | 100 万 | 75 | 8~10 台 | 不做边缘的代价 |
| 1000 万 | 95% | 50 万 | 38 | 5~6 台（需实测） | 必须边缘 + 预热 |
| 1000 万 | 100% | 1000 万 | 750 | 50+ 台 | 不现实，成本爆炸 |

节点规格建议 16c64g（每节点 8~12 个 4c8g Pod，留系统预留），
配合 cluster-autoscaler；秒杀型负载用"固定节点池 + 提前扩容"，不要指望 1 分钟内自动加 50 台。

## 7. 成本优化

| 手段 | 节省 | 注意 |
|---|---|---|
| 边缘拦截 90~95% | 回源 Pod 减少 10~20 倍 | 需要边缘可编程/短 TTL 缓存 |
| 活动后立即缩容 | 峰值只付几小时 | 缩容前确认流量已回落 |
| Spot/抢占式节点 | 60~80% 单价 | 需容忍中断 + 多可用区 |
| 混合部署（在线+离线） | 提升 CPU 利用率 | 秒杀期间驱逐离线任务 |
| 本地库存减少 Redis 分片 | Redis 成本降一个数量级 | 对账/少卖要处理好 |

## 8. 面试问答

**Q：HPA 为什么扩不出来？**
A：指标采集 + 控制循环至少 15~30s，JVM 冷启动 20~60s，镜像拉取更久；
秒杀峰值只有几秒，等 HPA 反应过来活动已经结束。所以要提前扩容/预留热 Pod/边缘拦截。

**Q：滚动发布时本地库存怎么办？**
A：新 Pod 启动后向 Redis 批发自己的 chunk；老 Pod 在 preStop 阶段停止接单、
把本地余量退回 Redis。为了绝对不超卖，库存 key 可以带活动版本号，
新老版本互不影响，活动结束后统一对账。

**Q：为什么 requests 和 limits 不一样？**
A：requests 是调度保证，limits 是上限。requests 太小会被挤到资源紧张的节点，
limits 太大会影响邻居、太小会 throttling。CPU 密集型服务一般 limits = 2~4 倍 requests，
内存 limits 建议等于 requests（OOM 比 throttle 更可控）。

**Q：Pod 被 OOMKill 了怎么办？**
A：先看是堆还是堆外（Netty/直接内存/线程栈）。JVM 设 `MaxRAMPercentage=70`，
留 30% 给元空间、直接内存、系统；加 `-XX:+ExitOnOutOfMemoryError` 快速失败，
让 K8s 重启而不是僵死。然后查内存泄漏/大对象/批量过大。

**Q：K8s 里跑 JVM 要注意什么？**
A：① 用容器感知参数（JDK 10+ 默认开启）；② 堆不超过 limit 的 70%；
③ 虚拟线程注意 `synchronized` 导致的 pinning（JDK 21 有，24 改善）；
④ 启动慢用 AppCDS/CRaC；⑤ 优雅停机要处理 MQ 消费和在途请求。

**Q：为什么不用 Serverless（如 Knative）？**
A：冷启动对秒杀是致命的；而且秒杀需要长连接、本地缓存、稳定的 CPU，
Serverless 的按需实例和缩容到零不适合。它适合低频后台任务，不适合峰值业务。

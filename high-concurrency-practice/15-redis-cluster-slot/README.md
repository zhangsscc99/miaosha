# 15 同机 Redis Cluster 的槽和迁移

库存还是一个热 key。Cluster 把 16384 个槽分给多个主库。一个 key 只进一个槽，这个槽只在一个主库上。三个主库不会把这一个库存 key 变成三倍 QPS。第 3 章是客户端自己拆了两个 key、放进两个进程。这一章不拆这个 key。

没有副本，没有 `CLUSTER FAILOVER`，没有第二台机器，没有 Sentinel。`kill -9` 是杀进程，页还在，不是断电。6 秒的 `DEBUG SLEEP` 是主线程里的 `nanosleep`，不是跨机房。

面试口径在上一层的 [技术报告](../REPORT.md)。原始数字在 `results/*.json`。`pass: true` 才算这组成立。延迟仍是直方图桶的上界。

## 复现

依赖本机的 Go 1.22。Redis 不在仓库里。

```bash
bash run.sh
```

脚本会把 Redis **7.0.15** 装到 `/tmp/redis-7015`（已经有就直接用），清掉 `/tmp/miaosha-cluster`，关掉 7101–7104 上的 Redis，建一个 3 主、0 副本的集群，再加一个没开 cluster 的 7104。测完再关掉。不要对已经有业务数据的实例运行。

## 槽和 hash tag

本地 CRC16 和 `CLUSTER KEYSLOT` 对过 500 个键，差 **0**。hash tag 只认第一对花括号，括号里至少要有一个字符。

| key | 槽 |
| --- | --- |
| `foo` | 12182 |
| `foo{bar}`、`foo{bar}baz`、`{bar}baz` | 都是 **5061** |
| `foo{}bar` | 14292，空括号不算 tag |
| `{bar`、`foo{bar` | 4015、15278，没有右括号，按整段算 |
| `a{b}c{d}` | 3300，只取第一对，也就是 `b` |

10 万个 `u:%d`：三个节点 **33,296 / 33,387 / 33,317**。单个槽最多 **13** 个键，16384 个槽里用到 16,260 个。键可以摊开。摊开之后，每个键仍旧只在一个主库上。

## 没有 tag 的两次 key

`plain:stock` 在槽 14190，`plain:win` 在槽 6177。`EVAL` 和 `MGET` 都是：

`CROSSSLOT Keys in request don't hash to the same slot`

库存还是 **5**，脚本没有跑。

带上 `{t2}` 之后，库存和已购集合在同一个槽。8 条连接、800 个不同用户、库存 100：成功 **100**、售罄 **700**、重复 0、错误 0，库存 0，集合 100。这是正确性，不是 QPS。第 1 章的 Lua 扣减数字不要换成这一组。

## MOVED

槽 3451 的键在 7101。连到 7102 去 `GET`，20 次都是：

`MOVED 3451 127.0.0.1:7101`

没有因为多问几次就改口。客户端记住回复里的地址之后，20 次里只有 **第 1 次**是 MOVED，20 次最终都读到值。

## 热 key 只打满一个主库

预热 1 秒，统计 4 秒。`hot:get` 在 7103。连接直接打到 7103。

| | QPS | 延迟上界 | 7103 | 另外两个 |
| --- | --- | --- | --- | --- |
| GET，16 连接 | **216,211** | p50 ≤ 100 微秒，p99 ≤ 200 微秒，最慢 4.265 毫秒 | **98.5%** | 命令增量都是 2，CPU 是 0 |
| GET，32 连接 | **227,878** | p50 ≤ 200 微秒，p99 ≤ 500 微秒，最慢 3.856 毫秒 | **98.5%** | 7101 是 0.5%，7102 是 0 |
| INCR，16 连接 | **231,251** | p50 ≤ 100 微秒，p99 ≤ 200 微秒，最慢 9.904 毫秒 | 这一组在 **7101**，**98.2%** | 7102 是 0，7103 是 **0.2%** |
| 7104，没开 cluster，GET 16 连接 | **196,266** | p50 ≤ 100 微秒，p99 ≤ 500 微秒，最慢 11.826 毫秒 | 这一进程 **95.0%** | 不在集群里 |

32 连接是 16 连接的 **1.05** 倍，p99 从不超过 200 微秒变成不超过 500 微秒。规划用 16 连接的 **216,211**。7104 这次只有 95.0%，没有打满，不拿它证明「开了 cluster 反而更快」。

INCR 和 GET 不是同一条命令，也不在同一个节点上。它说明的是同一件事：成功写仍然只占一个主库。不要把 231,251 和 216,211 平均，也不要拿 231,251 去除。

## 每次都先走错节点

16 连接。每次先问没有这个槽的主库，读到 `MOVED` 再去真正的主库，槽位缓存故意不更新。完成 **133,011** QPS，是直连 216,211 的 **0.615** 倍。p99 不超过 500 微秒，p999 不超过 2 毫秒，最慢 14.662 毫秒。

真正的主库 CPU **68.7%**，错的那个主库 **69.7%**，第三个 **0.2%**。客户端 180.2%。两个核都在忙，完成的 QPS 比一个核直连还低。

错节点的 `total_commands_processed` 只多了 **2**。这份 7.0.15 里，重定向在进入命令实现之前就返回了，计数器不加。那 2 条是采样。完成的 **532,056** 次里，每一次都先收到了 MOVED。看 CPU，不要看这个计数器。

## 三个主库各读各的键

每个主库 16 条连接，只读自己槽上的键。合计 **309,036** QPS，是单节点 216,211 的 **1.43** 倍，不是 3 倍。三次操作数是 **383,539 / 416,484 / 436,147**。CPU 是 **53.0% / 59.7% / 61.5%**，客户端 **196.0%**。4 个核已经占满，所以这一倍不能当成每个分片的上限。分片上限用上面那个单节点、CPU 98.5% 的 216,211。不要把 309,036 除以 3。

## ASK 和 ASKING

槽 4748，键先在 7101，迁到 7102。逐步回复：

| 步骤 | 回复 |
| --- | --- |
| 迁之前，问源 | `100` |
| 迁之前，问目标 | `MOVED 4748 127.0.0.1:7101` |
| 已经 MIGRATING，键还在源上 | 源仍是 `100` |
| 目标没有 ASKING | 仍是 `MOVED` 回源 |
| 目标先 ASKING 再 GET，键还没迁 | `nil` |
| `MIGRATE` | `OK`。源上这个槽的键数变成 **0** |
| 再问源 | `ASK 4748 127.0.0.1:7102` |
| 问目标，不带 ASKING | `MOVED` 回源。槽的主人还没改 |
| ASKING 之后先 `PING` 再 GET | `MOVED`。ASKING 只覆盖下一条命令 |
| 再来一次 ASKING 然后 GET | `100` |
| 三个节点都 `SETSLOT NODE` 之后 | 旧主库是 `MOVED` 到 7102，新主库直接是 `100` |

`MOVED` 是槽的主人换了，客户端应该改地图。`ASK` 是这一次去目标上看看，地图先别改。

## 只告诉源节点

键迁完，`SETSLOT NODE` 先只打给源。立刻问第三个节点，回复仍是 `MOVED 4748 127.0.0.1:7101`，也就是旧主人。接着等了 **8 秒**，第三个节点的 `CLUSTER NODES` 还是源的 id。这一次没有等到它自己改口。

导入方执行 `SETSLOT` 才会抬高 config epoch 并广播。只改源节点，第三方可以一直拿着旧地图。三个主库都要收到 `SETSLOT NODE`。

## REPLACE 丢掉目标上的 50 次递增

迁的过程中，对目标先 `ASKING` 再 `INCR`，做了 **50** 次。当时目标上的值是 **50**。然后 `MIGRATE REPLACE`。目标上的值变成源上的 **100**。这 50 次已经返回的递增不在了。

不带 `REPLACE`：目标上先写成 9，源上是 7。`MIGRATE` 返回

`ERR Target instance replied with error: BUSYKEY Target key name already exists.`

源仍是 **7**，目标仍是 **9**。两个值同时在，后面的 `REPLACE` 会用源盖掉目标。

## 同一个槽先迁 40 个

100 个键在同一个 tag 里。先迁 40 个。不跟着 ASK 的客户端：这 **40** 个在源上只看到 ASK，另外 **60** 个仍能读到原值。坏回复 **0**。

## 库存和已购集合只迁走一个

两个键共用一个 tag。只把库存键迁走，已购集合还在源上。源和目标上的同一次 `EVAL` 都是：

`TRYAGAIN Multiple keys request during rehashing of slot`

两个键都到了目标上之后，源返回 `ASK`。目标先 `ASKING` 再执行，返回 **1**，库存从 5 变成 **4**。多 key 的脚本不能在槽迁到一半时当它已经原子。

## 键已经迁走、槽还没改主

16 连接，每次从源拿到 `ASK`，再 `ASKING` 后去目标读。完成 **92,693** QPS，是直连的 **0.429** 倍。p99 不超过 500 微秒，p999 不超过 2 毫秒，最慢 6.687 毫秒。

目标 CPU **86.5%**，`total_commands_processed` 多了 **741,570**。370,784 次完成乘 2 是 741,568，多出来的 2 是采样：计数的是 `ASKING` 和后面的 `GET`。源 CPU **55.0%**，命令增量只有 **2**，`ASK` 同样不进这个计数器。第三个主库的命令增量也是 2。

这是迁移窗口。不要把它当成平时的 QPS，也不要按这个数去买一整月的机器。

## 一次 MIGRATE 堵住同一个进程

200 字节的值。40 个键逐条迁：单次命令 p50 不超过 100 微秒，p99 不超过 200 微秒，最慢 **138** 微秒。这一段墙钟 7.6 毫秒，不引用 CPU。

200 个键合成一条 `MIGRATE`：命令本身 **742** 微秒。同一进程上同时在飞的 `GET`，最慢 **730** 微秒，p99 仍不超过 100 微秒，因为大部分 GET 没有排在这条命令后面。另一个主库上的 `GET` 最慢 **150** 微秒。

一条大的 `MIGRATE` 在主线程里做完才返回。同一进程上的读会排在它后面。不要在秒杀进行时对热槽做大批量的一次 `MIGRATE`。

## 主线程睡 6 秒，没有被标成 FAIL

`node-timeout` 是 5000。对 7102 执行 `DEBUG SLEEP 6`，命令在 **6,000** 毫秒返回。这 6 秒里，7101 上对它自己的键做了 **293** 次成功的 `GET`，没有一次 `CLUSTERDOWN`。日志里没有 `Marking node`。醒来之后集群状态仍是 **ok**。

6 秒比配置的 5 秒长，可是节点没有被标失败。失败看的是「已经发出去、还没回来的那次 PING」超过 node-timeout，而且链路会在大约一半超时时被拆掉重连，计时重新开始。这次 6 秒不够走完这个过程。不要把 `cluster-node-timeout 5000` 说成「主线程卡 5 秒就一定切换」。这次也没有副本可以切。

## 一个主库被 kill -9

默认 `cluster-require-full-coverage yes`。杀掉 7103，它有 **5,461** 个槽。只跑了一次。

| | 距 kill |
| --- | --- |
| 7101 上自己的键第一次 `CLUSTERDOWN The cluster is down` | **6,699** 毫秒 |
| 接着 20 次 | **20/20** 都是这句 |
| 问一个属于 7103 的键 | 同样是 `CLUSTERDOWN The cluster is down`，不是 MOVED |
| 重新拉起 7103，到 PING | **55** 毫秒。从 kill 算是 **6,755** 毫秒 |
| 立刻对新进程 `SET` 20 次 | **0** 次成功，错误仍是 `CLUSTERDOWN The cluster is down` |
| 这 20 次同时问 7101 | **20/20** 仍是 CLUSTERDOWN |
| 新进程自己的 `cluster_state` 变成 ok | 从拉起开始 **2,023** 毫秒 |
| 就在这一刻问 7101 | 仍是 `CLUSTERDOWN The cluster is down` |
| 这时再对新进程 `SET` | `OK`。最后这个键的值是 `gap` |
| 7101 恢复成 ok | 距 kill **17,848** 毫秒 |

日志：`Marking node ... as failing` 在 19:07:57.707，`Clear FAIL state ... is reachable again and nobody is serving its slots after some time` 在 19:08:08.859，相隔 **11.152** 秒。这份源码里，主库重新可达之后，要再过 `node-timeout * 2`（这里是 10 秒）才会清掉 FAIL。11.152 秒是这一次从打出标记到打出清除的间隔，包含等下一次 PONG。不要把 11.152 说成配置写了 11 秒。

没有副本，所以没有人把槽接走。清除的原因是这句日志：过了那段时间，槽仍然没有别人服务。`CLUSTER FAILOVER` 没跑。

新进程刚起来的大约 2 秒里，自己也拒绝写入。2,023 毫秒和源码里的 `CLUSTER_WRITABLE_DELAY` 2 秒对得上，这是一次。在这之前，20 次 `SET` 已经失败。等它自己变成 ok、别的节点还没清 FAIL 的时候，直接连它的 `SET` 成功了，问 7101 仍然是 CLUSTERDOWN。客户端如果还拿着旧地图、或者还在问别的节点，会认为集群不可用；直接打到这个新进程上的写已经返回了。

没有 AOF，`save ""`。重启之后，原来写在 7103 上的 **20** 个键都是 nil。7101 上的键还是 `v`。这是杀进程，不是断电。

然后把 `cluster-require-full-coverage` 设成 no，再杀一次 7103。

| | 值 |
| --- | --- |
| `cluster_slots_fail` 变成 5461 | 距这次 kill **7,048** 毫秒 |
| 当时 `cluster_state` | **ok**，不是 fail |
| 7101 上自己的键，20 次 | **20/20** 成功 |
| 问 7103 的槽 | `MOVED 12776 127.0.0.1:7103` |
| 再拨 7103 | `connection refused` |

coverage 还开着时，一个主库失败，活着的槽也不对外服务。关掉之后，活着的槽继续服务，死掉的槽被指到一个已经没有进程的地址。客户端要是只重试 MOVED、不看连接失败，会打到这个空地址上。

## 扩到 10 万、100 万、1000 万

目录价仍是第 1 章的 Redis 社区版 1GB：**151.2** 元/月。不是 ECS 的 470。一个分片一份。GB 按 10^9 字节，不满 1GB 也进位。

### 这一个库存键

16 连接的直连 GET 是 216,211，另外两个主库 CPU 是 0。加主库不加这个 key 的 QPS。

| 点击 QPS | 这个 key 用得上的分片 | 目录价 | 买成 3 主来扛它 |
| --- | --- | --- | --- |
| 10 万 | 1 | 151.2 | 3 个，453.6，多 **302.4** |
| 100 万 | 仍是 1。216,211 不够 100 万，加主库也不够 | 151.2 | 若按官方 10 片再乘 3，是 30 片，比 10 片多 **3,024** |
| 1000 万 | 仍是 1 个槽 | 151.2 | 若按官方 100 片再乘 3，是 300 片，比 100 片多 **30,240** |

302.4 是这次 3 个进程里空转的那两个。3,024 和 30,240 是「官方片数再乘 3」的另一笔，那些片没有跑起来。第 1 章已经算过「一个 key 按点击买 100 个分片」少付的 14,969。不要把 30,240 和 14,969 加在一起，也不要和第 3 章的 1.73 倍相乘。要让这一个 key 超过一个核，得像第 3 章那样拆成多个 key。Cluster 的槽不会替你拆。

### 键能摊开，客户端记住槽

用 216,211。32 连接是 227,878，只快 1.05 倍，p99 更差，不拿去除。同机三个进程的 1.43 倍是 4 个核挤在一起，也不拿去除。

| 读 QPS | 分片 | 月费 | 按官方 10 万/片 | 少 |
| --- | --- | --- | --- | --- |
| 10 万 | 1 | 151.2 | 1 片，151.2 | 0 |
| 100 万 | **5** | **756** | 10 片，1,512 | **756** |
| 1000 万 | **47** | **7,106.4** | 100 片，15,120 | **8,013.6** |

47 个进程没有同时跑。前提是键均匀落到不同槽，而且每个分片都能像这次单节点那样吃到大约一个核。官方 10 万比这次的 216,211 保守，少出来的是这个差。

47 个核如果改成自建、一台 2 核 ECS 只放一个进程，是 47 × 470 = **22,090** 元/月。那是机器，不是上面的 7,106.4。不要相加。

### 客户端不缓存槽

每次都先走错节点，是 133,011。1000 万是 **76** 个分片、**11,491.2** 元/月。比记住槽的 47 个多分片 **29** 个、**4,384.8** 元/月。100 万是 8 个对 5 个，多 **453.6**。10 万两边都是 1 个。错节点的 CPU 已经在 69.7%，这不是「再买一个分片就能补上」的那种慢：槽还是只在一个主库上，另一个主库只是在回答 MOVED。

4,384.8 不要和 8,013.6 相加。8,013.6 是记住槽、相对官方 10 万。4,384.8 是同一个实测能力里，不缓存相对缓存。

如果把迁移窗口里的 92,693 当成平时的能力，1000 万是 **108** 个分片、**16,329.6** 元/月，比 47 个多 **9,223.2**。槽不该整月停在 MIGRATING。9,223.2 不要加进月费。

### 200 字节的值占多少内存

| 键数 | Cluster，309.08 字节/键 | 没开 cluster，288.75 字节/键 |
| --- | --- | --- |
| 10 万 | 0.031 GB，1 份 | 0.029 GB，1 份 |
| 100 万 | 0.309 GB，1 份 | 0.289 GB，1 份 |
| 1000 万 | **3.09 GB，4 份，604.8** | **2.89 GB，3 份，453.6** |

1000 万这一档多出来的是 **151.2** 元/月。字节差是 0.20 GB，不是整整 1GB，目录价按 1GB 进位才多出一份。这是内存，不是上面的 QPS。QPS 那几行默认工作集放得进 1GB。1000 万个这种键放不进。151.2 不要和 7,106.4、4,384.8 或 302.4 相加。

302.4、3,024、30,240、756、8,013.6、4,384.8、9,223.2、7,106.4、22,090、604.8、151.2 是不同的账。不要相加，也不要和第 1 章的 14,969、第 3 章的分片差、第 13 章的 19,958.4、第 14 章的 21,150 相加。

## 这次没有当成优化的事

- 把三个主库说成这个库存 key 的 3 倍。16 连接时另外两个 CPU 是 0。32 连接是 1.05 倍，不是 3 倍。
- 把同机三个进程的 309,036 当成 3 倍，或除以 3 当成每个分片的能力。测到的是 1.43 倍，三个 Redis 的 CPU 是 53% 到 61.5%，客户端 196%。

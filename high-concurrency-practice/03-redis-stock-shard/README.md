# 03 把成功扣减拆到两个 Redis 进程

一个库存 key 由一个 Redis 线程执行。第 1 章已经看到：售罄读在同一个进程里拆两个 key 还是大约 19.5 万 QPS，拆成两个进程才到 32.6 万，1.69 倍。这一章补的是成功路径。成功路径要做 `SISMEMBER`、判断库存、`DECR`、`SADD`，比售罄读重，而且胜出用户会把内存写上去。

机器还是那台 4 核虚拟机。Redis 是 7.0.15，这次编译出来的分配器是 jemalloc 5.2.1。第 1 章那份二进制是 jemalloc 5.3.0，所以两边的绝对 QPS 差几千，对照以这一章同一次跑出来的单进程为准。

面试口径也写进了上一层的 [技术报告](../REPORT.md)。

## 复现

依赖本机的 `redis-server` 7 和 Go 1.22。脚本会自己拉起 Redis，测完关掉。`FLUSHDB` 会清掉 6379 和 6380 的当前库。

```bash
bash run.sh
```

本机如果没有在 `PATH` 里，脚本会用 `/tmp/redis-7015/bin/redis-server`。`results/*.json` 是 2026-11-12 这次跑出来的。`pass: true` 才算这组成立。

## 和现有代码的关系

`MiaoshaController` 对一个商品只做一个 `DECR`，key 是商品 id。v1 在 `redisService.decr(GoodsKey.getMiaoshaGoodsStock, "" + goodsId)`，v2 是同一句。库存是一个热 key。这一章不改那两处 Java，只回答「把这一个 key 拆开之后，成功扣减能不能变快，以及哪些拆法会把账做坏」。

扣减脚本和 [第 1 章](../01-redis-lua-atomic-stock/lua/stock.lua) 是同一份：先看用户是否已成功，再判断库存，然后 `DECR` + `SADD`。两个进程各有自己的库存 key 和已购集合。Lua 仍然只在一个进程里原子。跨进程没有事务。

## 资源

| 部署 | 配置 | 用来回答什么 |
| --- | --- | --- |
| 一个进程 | `redis-64mb.conf`，64MB，6379 | 成功路径的单核对照 |
| 一个进程两个 key | 还是上面那个 64MB | 只拆 key、不拆进程 |
| 两个进程 | `redis-64mb-6379.conf` + `redis-64mb-6380.conf`，各 64MB | 同样 4 秒窗口下的加速比 |
| 两个进程 | 各 32MB，合计仍是 64MB | 内存预算不加倍时还快不快 |
| 钉核 | 两个 64MB 进程分别钉在 CPU 0 和 CPU 1，压测钉在 CPU 2 和 3 | 把客户端和 Redis 隔开能不能更接近 2 倍 |

关掉 RDB。AOF 只在标明的那一组打开，`appendfsync everysec`。压测进程和 Redis 在同一台机器。延迟仍然用直方图桶的上界。

吞吐那几组把 worker 固定分到进程上，每个 worker 一条连接。取模是否正确、偏斜会不会剩库存，是另外几组小请求量的正确性测试，不拿它们的 QPS 当容量。

## 正确性

库存按桶切开之后，超卖要分两种：件数超了，或者一个人买到两件。下面每组都对上了 Redis 里的库存和已购集合。

| 场景 | 结果 | 原始文件 |
| --- | --- | --- |
| 400 个用户按 id 取模，库存 50+50，每人 10 次 | 成功 100，重复 900，售罄 3000。两个集合没有交集 | `hash-correct.json` |
| 同样 400 个用户全部打到 0 号桶 | 成功 50，1 号桶原样剩 50 | `hash-skew.json` |
| 流量对半，库存 10 和 90 | 最终仍然卖完 100。薄桶第一次返回售罄时，厚桶还剩 **67** | `hash-unfair.json` |
| 100 个用户，每人同时打两个桶 | 库存卖完 100 件，但是只有 **50** 个人，每人两件 | `fallback-dup.json` |
| 读走 50 件再清零，崩溃在写入另一个进程之前 | 两个进程的库存都是 0，50 件消失 | `rebalance-gap.json` |
| 16 个线程正在买，GET 到 196965 后睡 30 毫秒再 SET 0，把旧值加到另一个进程 | 卖出 7633，账上变成 **204598**，多出 **4598** | `rebalance-unsafe.json` |
| 同样的并发下，源桶用 Lua 一次取走剩余再 `INCRBY` | 卖出 4520，搬走 195480，合计 **200000**，和最初库存一致 | `rebalance-lua.json` |

取模把人和库存放进同一个进程，一人一单不用跨进程。流量不均时，另一个桶的库存不会自己流过来。10 和 90 这组最后也能卖完，是因为每个桶的用户数（200）都大于该桶库存；不公平发生在中途：薄桶的用户已经收到售罄，厚桶里还有 67 件。

同时打两个桶可以把库存件数卖满，集合的并集却只有 50 人。库存 key 没变成负数，人已经买重了。这种错误用「最后库存是 0」检查不出来，要看两个已购集合的交集。

搬库存的崩溃窗口是实测的：`GET` 到的 50 件被清掉之后，另一个进程没有加上，账就短 50。并发下的 `GET` 再 `SET` 则会把窗口里新卖出的件数再加一遍，这次多了 4598。Lua 把「读剩余」和「清零」放在源进程的一个线程里，再在目标进程 `INCRBY`。两次调用都做完时账是平的。Lua 返回之后、`INCRBY` 之前如果进程停了，丢的就是 `rebalance-gap` 那种。

## 吞吐

统计窗口 4 秒，预热 1 秒。单进程把 Redis 打到大约 100% CPU。成功请求的用户 id 全程不重复，所以测到的是 `DECR` + `SADD`，不是重复购买那条只做 `SISMEMBER` 的路径。

| 场景 | QPS | 延迟上界 | Redis CPU | 客户端 CPU |
| --- | --- | --- | --- | --- |
| 一个进程，一个 key，16 连接 | 141,786 | p50 / p99 ≤ 200 微秒 | 100.0% | 124.5% |
| 一个进程，一个 key，32 连接 | 139,470 | p99 ≤ 500 微秒 | 99.5% | 109.7% |
| 一个进程，两个 key，16 连接 | 142,597 | p99 ≤ 200 微秒 | 99.5% | 128.7% |
| 两个进程各 64MB，32 连接 | 244,922 | p99 ≤ 500 微秒 | 185.7%（92.7% + 93.0%） | 164.5% |
| 两个进程各 64MB，16 连接 | 239,696 | p99 ≤ 200 微秒 | 182.2% | 155.7% |
| 两个进程各 64MB，AOF everysec，32 连接 | 227,395 | p99 ≤ 500 微秒 | 190.5% | 150.2% |
| 两个进程各 32MB，32 连接，窗口 2 秒、预热 0.3 秒 | 254,713 | p99 ≤ 500 微秒 | 184.5% | 161.5% |
| 钉核之后的两个 64MB 进程，32 连接 | 229,339 | p99 ≤ 500 微秒，最慢一次 13.8 毫秒 | 179.7%（CPU 0 上 90.0%，CPU 1 上 89.7%） | 127.0% |

两个 key 放在同一个进程里是 142597，相对单 key 的 141786 是 **1.006 倍**，多 0.6%。CPU 还是一个核。Redis 集群如果只把同一个商品的两个桶落到同一个节点，成功 QPS 不会变成两倍。

两个进程、同样 4 秒是 244922，相对 141786 是 **1.73 倍**。两个 Redis 加客户端合计 350% CPU，这台机器一共 4 个核。每个 Redis 停在 93% 左右，没有再多出一个空核去跑第三个进程。第 1 章售罄读的双进程是 1.69 倍，成功写这一次是 1.73 倍，两次都卡在同一台 4 核机器上。

16 连接的双进程是 239696，只比 32 连接少 2.1%，p99 从 500 微秒的桶回到 200 微秒的桶。连接数沿用第 1 章的结论：再加连接，QPS 几乎不涨，尾延迟变长。

AOF `everysec` 从 244922 降到 227395，少 **7.2%**。第 1 章单进程成功路径的 AOF 损失是 13.4%，第 2 章入队是 13.8%。这次损失更小，和那两组不是同一次二进制、也不是同一个脚本，不能合成一个「AOF 总是少百分之几」。生产如果要开 AOF，这一章能引用的数字是双进程 **22.7 万**。

32MB + 32MB 的窗口只有 2 秒。结束时每个进程大约 29.2 万个胜出者，`used_memory` 17.2MB，还在 32MB 上限下面。QPS 是 254713，相对单进程 4 秒窗口是 1.80 倍。它比 64MB 双进程的 244922 更高，是因为胜出集合更小，`SADD` 更便宜，不是因为把 `maxmemory` 调小会变快。4 秒窗口在单个 64MB 进程上已经写到 71.7 万个胜出者、32.9MB。同样的增长放到 32MB 上限里会在窗口后段被 `noeviction` 拒绝，所以小内存那组把窗口收短了。

钉核没有更快。Redis 的 `Cpus_allowed_list` 分别是 `0` 和 `1`，压测进程限制在 CPU 2 和 3。QPS 从 244922 降到 229339，少 6.4%。客户端 CPU 从 164% 降到 127%，两个 Redis 都停在 90% 左右。尾部最慢的一次从 9.5 毫秒变成 13.8 毫秒。在这台 4 核机器上，把客户端和 Redis 隔开之后，客户端剩下的两个核喂不饱两个 Redis。

## 卖完 20 万件要多久

库存 20 万，32 个 worker，从第一笔打到第 20 万笔成功返回。QPS 用库存除以这段墙钟时间，尾部多出来的售罄请求不算进分子。

| 部署 | 墙钟 | 相当于 | Redis CPU |
| --- | --- | --- | --- |
| 一个 64MB 进程 | 1.425 秒 | 140,339 QPS | 98.9% |
| 两个进程，各 10 万 | 0.745 秒 | 268,598 QPS | 190.4% |

两次都是卖完正好 20 万，库存 0。双进程是 **1.91 倍**，少 0.681 秒。这个倍数高于 4 秒窗口的 1.73 倍，因为 20 万里每个进程只写 10 万个胜出者，集合比 4 秒窗口里的 60 万小。拿「卖完一小段库存」的倍数去规划持续几秒的成功流量，会估高。持续流量用 4 秒窗口的 24.5 万。

按单进程 141786 QPS 去除，20 万件是 1.411 秒，和测到的 1.425 秒差 14 毫秒。短库存的集合更小，所以实测卖完速度（140339）反而略低于 4 秒窗口。差在集合大小，不在公式。

5000 件按 141786 QPS 是 **35 毫秒**。这种库存不需要拆进程。拆进程要处理取模不均和搬库存，35 毫秒的决策用一个核做完。

## 胜出集合占多少内存

用两组 `used_memory` 对齐同一条直线：20 万胜出者 10.40MB，71.67 万胜出者 32.86MB。斜率大约 **43.5 字节/人**，截距大约 1.7MB。这是 jemalloc 5.2.1 这一份二进制上的估算。第 1 章在另一份二进制上是大约 52 字节，两份不要混用。

按 43.5 字节和 1.7MB 基线：

| 上限 | 大约能记下的胜出者 |
| --- | --- |
| 32MB | 73 万 |
| 64MB | 150 万 |
| 1GB | 大约 2400 万。外推，没有写到 1GB |

20 万件的决策内存可以忽略。1000 万件大约 415MB，一个 1GB 实例装得下，单线程仍要按 14.2 万/秒写 70 秒。拆进程是为了核，不是为了把 64MB 换成 1GB。

## 扩到 10 万、100 万、1000 万成功 QPS

这里的 QPS 是成功扣减，不是点击。点击里的售罄流量用第 1 章的进程内标记挡掉，不进这些桶。桶的数量按「这些成功请求要在 1 秒内做完」来算。

单核规划用这一章打满一个核的 **141786 QPS**。这是客户端和 Redis 在同一台机器、没有跨机房延迟时的上限。两个进程挤在同一台机器上时，每个进程实际只有大约 12.2 万（244922 的一半），因为核被客户端分走了。下表的「独占一核」列假设每个新进程都有自己的核，客户端在别的核上。超过 2 个进程没有再跑，那一列是按单核上限做的除法。

官方列仍然用云原生分片的参考值 **10 万 QPS**。它和内存规格无关。容量按官方列买，实验列用来看官方数有没有把头留够。

| 1 秒内要做完的成功扣减 | 官方 10 万/进程 | 按本机单核 14.2 万外推 | 这次实际跑到的 |
| --- | --- | --- | --- |
| 10 万 | 1 个 1GB 分片 | 1 个进程 | 1 个进程，16 连接，141786 |
| 100 万 | 10 个分片 | 8 个进程 | 2 个进程，244922。离 100 万还差 4 倍，这台 4 核机器没有空核再加进程 |
| 1000 万 | 100 个分片 | 71 个进程 | 没有跑 |

100 万件如果接受 4 秒而不是 1 秒，按双进程实测的 244922 QPS 去除大约 4.1 秒，仍然是这台机器上的两个进程。这是用 4 秒窗口的速率做的除法，不是另一次把 100 万库存卖完的实验。100 万个胜出者大约 43MB，两个 64MB 进程各放 50 万，装得下。

1000 万件按单核 70 秒，或者 100 个官方分片在 1 秒内做完。每个分片大约 10 万个胜出者、4.4MB。内存不是那 100 个分片的理由，线程数才是。

应用服务器这一章没有重测。请求还没进 Redis 时，台数用第 1 章 HTTP 本地拒绝的 12.0 万/台。每个请求都打到成功路径 Lua 上时，接口容量会低于第 1 章「每次只做售罄 GET」的 6.6 万，那个数字这次没有再测。

## 钱

价格沿用前两章的目录价。Redis 社区版 1GB 标准版，杭州按量 0.21 元/小时，帮助中心算例是 **151.2 元/月**。应用服务器不在这一章重算。

同一个商品的 key 如果不拆，加分片不会加成功 QPS。10 个分片按官方参考值是 1512 元/月，流量仍落在 1 个槽上，得到的还是 10 万 QPS。拆成 10 个库存桶、按用户取模之后，同样 1512 元对应的是 10 个分片都在干活。中间 9 个分片的目录价是 9 × 151.2 = **1361 元/月**。不拆桶时这 1361 元每个月都在，成功 QPS 不加；拆桶之后这 1361 元买到的是额外大约 90 万官方 QPS。

1000 万成功 QPS、官方 100 个分片是 15120 元/月。不拆桶时 99 个分片空转，99 × 151.2 = **14969 元/月**，容量仍停在 1 个分片。

按本机单核 14.2 万外推，100 万成功 QPS 是 8 个进程，8 × 151.2 = **1210 元/月**；1000 万是 71 个进程，**10735 元/月**。相对官方列少 2 个和 29 个分片，目录价少 302 元/月和 4385 元/月。这是「单核真能维持 14.2 万，并且每个进程独占一个核」才成立的差。同一台机器上的第二个进程只贡献了 0.73 倍而不是 1 倍。超过两个进程没有测，买的时候仍按官方 10 万留余量。

5000 件的典型秒杀用不上这笔差。一个分片 35 毫秒做完，再买一个分片是每个月多 151.2 元，决策时间从 35 毫秒变成十几毫秒，活动通常不靠这十几毫秒。

把内存从 64MB 换成更大的规格，官方单分片 QPS 参考值不变。同进程两个 key 只多了 0.6%。升内存规格买不到成功路径的第二核。

第 1 章的分布式锁是 1263 QPS，不是今天重测的。今天的单进程 141786 大约是它的 112 倍，双进程 244922 大约是它的 194 倍。锁没有单独的云账单，它换不来这些 QPS。

## 面试时可以主动讲的取舍

5000 件库存不拆桶。拆桶是库存大到一个核在时间预算里写不完，或者同一个商品的成功 QPS 必须超过大约 14 万的时候才做。

拆的是进程，不是 key。同进程两个 key 的 1.006 倍要报，避免被问「那 Redis 集群把槽迁开不就行了」时只记得 1.73 倍。槽迁到同一个节点上，还是一个线程。

1.73 倍和 1.91 倍都要报，并说明哪个是 4 秒持续窗口、哪个是 20 万件卖完。只报 1.91 会被问集合变大之后还在不在。

取模保证一人一单，也保证偏斜时另一个桶卖不动。10/90 那组的 67 件是中途快照：总库存 100，已经有人收到售罄，架上还剩 67。最终卖完不能用来证明中途公平。

「库存最后是 0」cover 不住一人两单。同时打两个桶那组，件数是 100，人是 50。

搬库存要么接受崩溃时丢掉刚取走的那一段，要么把两次写入做成可重试的账。`GET` 再 `SET` 在并发下会多出库存，这次是 4598 件。

钉核在这台 4 核机器上更慢。不要把「绑核」讲成已经验证的优化。

## 本轮明确没做的

没跑第三个 Redis 进程，没测跨机器 RTT，没测 Redis Cluster 的槽迁移协议，没重测单进程 AOF，没重测 HTTP。没跑 RabbitMQ、Kafka、RocketMQ、Docker、Kubernetes。超过两个进程的台数是除法，不是新的压测。

# 秒杀高并发技术报告（面试用）

日期：2026-11-12。代码和原始 JSON 在 [`01-redis-lua-atomic-stock`](01-redis-lua-atomic-stock/README.md)。

这一轮只做了扣库存决策。消息队列、Docker、Kubernetes 还没跑，报告里不把它们说成已验证。

## 30 秒版本

秒杀的库存是一个热 key。正确做法是用 Redis Lua 在一次往返里完成「是不是已经买过、还有没有库存、扣减、记下用户」。在这台 4 核虚拟机上，一个 64MB 上限的 Redis 进程把一个核打满之后：

- 成功扣减大约 **13.9 万 QPS**（16 条连接，p99 不超过 200 微秒）
- 售罄判断大约 **19.5 万 QPS**（16 条连接）
- 打开 AOF `everysec` 之后，成功路径降到 **11.9 万 QPS**（少 13.4%），售罄读路径没有变慢
- 同一把分布式锁的成功扣减只有 **1263 QPS**，大约是 Lua 的 1/110
- 应用侧先 GET 再 SET，100 件库存卖出了 **400** 件，库存最后还剩 74
- 进程内售罄标记把同一批 2 万个请求的 Redis 命令从 **60203** 降到 **578**，两轮都正好卖出 100 件
- 带上 HTTP 之后，本地直接拒绝大约 **12.0 万 QPS**，每个请求都打 Redis 大约 **6.6 万 QPS**。进程内原子读的 3170 万 QPS 不能当成接口容量

单分片有单线程上限。两个 key 放在同一个 Redis 里还是大约 19.5 万 QPS。拆成两个进程、内存合计仍是 64MB，售罄读到 **32.6 万 QPS**，是 1.69 倍，因为客户端和两个 Redis 抢 4 个核，没有线性到 2 倍。

## 和现有代码的关系

`MiaoshaService.miaosha` 现在还是同步 RPC 减库存，减失败再 `setGoodsOver`。这一章把「减库存的决策」单独抽出来压测，对应两件原有想法：售罄标记，以及仓库里已有的 Lua 限流。旧的 `luaLockScript.lua` 把判断写进了 `redis.call` 的参数，还用了 `KEY` / `AVG`，脚本本身不能执行。这次用的解锁脚本是比较 value 再删除。

## 测试机，也就是「一小部分资源」

| 项目 | 实际使用 |
| --- | --- |
| 机器 | 4 vCPU，KVM 上的 Intel Xeon（family 6 model 207），内存 15GB。压测进程和 Redis 在同一台机器 |
| Redis | 7.0.15，一个进程，`maxmemory 64mb`，关掉 RDB。售罄场景 RSS 约 10MB，成功扣减场景 RSS 约 49MB |
| 横向对照 | 两个进程，各 32MB，合计仍是 64MB |
| 持久化对照 | 同一进程打开 `appendonly yes`、`appendfsync everysec` |
| 数据库对照 | 本机 SQLite WAL，一条库存记录。没有 binlog，没有从库，比线上 MySQL 乐观 |
| 没测的 | MySQL / RDS、跨机器网络、Spring Boot、Redis 主从切换、Kubernetes |

延迟用直方图桶的上界：写成「p99 不超过 200 微秒」是桶的边界，真实值可以更小。本地原子读的 p99 落在 200 纳秒这个最小桶里，JSON 里的 `p50us` 用整数微秒会显示成 0。

Redis 在成功路径和售罄路径上都到了大约 99% CPU（单线程，所以是一个核）。瓶颈在 Redis，不在压测客户端没把请求发出去。本地回环的网络延迟被足够的并发挡住了，这个单核数字可以拿来估计「同机房、客户端连接数足够」时一个分片的上限。跨可用区、经过 Proxy、再加鉴权和日志，都会更低。容量规划同时放了阿里云文档里的单分片参考值 **10 万 QPS**，取更保守的那个。

价格口径，全部是目录价，不是账单：

- Redis 社区版 1GB 标准版，杭州按量 **0.21 元/小时 = 151.2 元/月**。来源是阿里云帮助中心《Redis 资源包介绍》里的算例。云原生分片的官方 QPS 参考值是 10 万，和规格大小无关。
- ECS 计算型 c9i：2 核 4G 约 470 元/月，4 核 8G 约 940 元/月，8 核 16G 约 1880 元/月，16 核 32G 约 3760 元/月。来源是阿里云开发者社区 2026 年规格文的转述，下单以控制台为准。应用服务器按 4 核 8G 这档估算，因为我们的 HTTP 压测就是 4 个核。

## 六组成对结果

库存 100，用户 400，每人 10 次，64 个并发。正确的结果是成功 100、重复 900、售罄 3000、库存 0。

| 做法 | 结果 | 耗时 | 说明 |
| --- | --- | --- | --- |
| GET 再 SET | 成功 400，库存剩 74 | 26 毫秒 | 超卖，而且丢失更新。这组成了测试，因为不变量被破坏了 |
| Lua | 成功 100，库存 0 | 24 毫秒 | 和上面同一批请求 |
| 一把分布式锁，锁内仍是 GET/SET | 成功 100，库存 0 | 3.43 秒 | 业务 QPS 1167。中间忙等了 70.2 万次 |

持续压测，预热 1 秒，统计 4 秒：

| 场景 | QPS | 延迟上界 | Redis CPU |
| --- | --- | --- | --- |
| Lua 成功路径，16 连接 | 138,581 | p50 / p99 ≤ 200 微秒 | 99.7% |
| Lua 成功路径，32 连接 | 137,331 | p99 ≤ 500 微秒 | 99.0% |
| 同上，AOF everysec | 118,892 | p99 ≤ 1000 微秒 | 99.2% |
| Lua 售罄，16 连接 | 194,907 | p99 ≤ 200 微秒 | 99.7% |
| Lua 售罄，32 连接 | 185,037 | p99 ≤ 500 微秒 | 98.7% |
| Lua 售罄，128 连接 | 172,035 | p99 ≤ 2000 微秒 | 96.5% |
| 售罄 + AOF everysec，32 连接 | 188,536 | p99 ≤ 500 微秒 | 99.0% |
| 分布式锁，32 连接 | 尝试 197,135，成功 1,263 | p99 ≤ 500 微秒 | 98.5% |
| 单进程互斥锁，库存 20 万 | 6,039,966 | 只在这个进程里正确 | 不经过 Redis |
| 进程内售罄标记 | 31,693,833 | p99 ≤ 200 纳秒，出现过一次 241 毫秒的长尾 | 不经过 Redis |
| HTTP + 售罄标记，32 客户端 | 120,452 | p99 ≤ 1 毫秒 | 客户端和服务端挤在 4 个核上 |
| HTTP + 售罄标记，64 客户端 | 107,089 | p99 ≤ 2 毫秒 | 连接再加，QPS 下降 |
| HTTP + 每次都执行售罄 Lua | 66,092 | p99 ≤ 2 毫秒 | 服务端 16 条 Redis 连接 |

本地售罄标记，2 万个不同用户，库存 100，32 并发：

| | Redis 命令数 | 端到端 QPS | 卖出 |
| --- | --- | --- | --- |
| 每次都进 Redis | 60,203 | 169,825 | 100 |
| 第一次看到售罄后进程内拒绝 | 578 | 12,789,318 | 100 |

命令数大约是 1/104。标记只在 Lua 已经返回售罄之后置位，所以不会在还有库存时提前拒绝。多出来的命令是置位前已经在飞的请求。

固定窗口限流：20 个用户、每人上限 100、共 4000 次请求。结果是成功 20、重复 1980、限流 2000。限流放行之后仍然一人一单。窗口在测试里被钉死，避免跨秒。生产 key 要带 unix 秒。固定窗口在秒边界可以打到两倍额度，这是窗口算法本身的误差。

SQLite 单行 `UPDATE ... WHERE stock > 0`，8 线程，库存 500，全部跑完后库存是 0、成功正好 500：

| synchronous | 请求 QPS |
| --- | --- |
| OFF | 218,945 |
| NORMAL | 173,114 |
| FULL | 29,654 |

FULL 这一组只有 4000 次请求，另外两组是 8000 次。这个数字不能说成 MySQL。它没有 binlog，也没有网络。

横向扩展，售罄脚本：

| 部署 | QPS |
| --- | --- |
| 1 个进程，2 个 key，64MB | 195,007 |
| 1 个进程，2 个 key，32MB | 192,843 |
| 2 个进程，各 32MB | 326,011（两个进程 CPU 合计 192%） |

同一个进程里拆 key 没有加速。两个进程是 1.69 倍。

69.6 万个成功用户写在集合里时，`used_memory` 约 38MB，扣掉售罄场景大约 1.6MB 的基线，每人大约 52 字节。秒杀库存如果是几千，这个集合可以忽略。64MB 够用，真正的天花板是单线程，不是内存。

## 这些数字怎样用在 10 万、100 万、1000 万

先把点击和成交分开。典型秒杀库存远小于点击。5000 件库存按 13.9 万成功扣减/秒，决策本身只要大约 36 毫秒。后面的流量都是售罄流量。

应用服务器用这次测到的 HTTP 本地拒绝 **120,452 QPS / 4 核** 来除。这是 Go 标准库、本机回环、没有鉴权、没有 access log，而且压测客户端也占着这 4 个核。Spring Boot 会更低；客户端换到别的机器，服务端可能更高。表里的台数是这次实验的比值，不是生产容量承诺。

Redis 给出两列。规划列用官方单分片 10 万 QPS。实验列用本机售罄 19.5 万 QPS。典型秒杀在本地标记生效之后，Redis 不需要按点击 QPS 扩。下表的 Redis 列是「如果每个点击都打到 Redis」的对照，用来算省下来的分片。

| 点击 QPS | 应用服务器（按 12.0 万/台） | 每个点击都打 Redis，官方 10 万/分片 | 每个点击都打 Redis，实验 19.5 万/分片 | 本地标记生效后的 Redis |
| --- | --- | --- | --- | --- |
| 10 万 | 1 台 4 核 8G。再加 1 台做故障切换，这 1 台是可用性，不是压出来的 | 1 个 1GB 分片 | 1 个分片 | 1 个 1GB 分片 |
| 100 万 | 9 台 4 核 8G | 10 个分片 | 6 个分片 | 1 个分片，前提是所有实例转发进 Redis 的总量不超过一个分片 |
| 1000 万 | 84 台 4 核 8G | 100 个分片 | 52 个分片 | 仍然是 1 个分片，约束同上 |

10 万点击时，1 台应用加 1 个 Redis 在实验比值里就盖住了。100 万和 1000 万时，台数主要被 HTTP 吃掉，不是被 Lua 吃掉。

单个库存 key 不能靠加 Redis 分片变快。100 个分片接的是 100 个不同的 key。真的要把成功扣减做到 10 万以上，得把库存拆成多个桶（按用户取模），每个桶一个进程。这次只压了售罄读的双进程，1.69 倍，没有压成功路径的双进程。所以上表不把 1.69 套进成功扣减。

每个应用实例在标记生效前都会漏过一小段流量。实例一多，漏过的流量会叠到同一个分片上。每个实例要有自己的转发额度，所有实例加起来不超过一个分片的规划 QPS（按 10 万留出余量，可以收到 8 万）。这段额度控制这次没有做多进程实验。

落库不在这一章。胜出人数等于库存。5000 笔订单即使用这次 SQLite FULL 的速度，也是一两秒内的写入量。1000 万点击不能每点一次就写数据库：FULL 单行上限 2.97 万 QPS，1000 万是它的 337 倍。更大的 RDS 规格去不掉这一行上的锁。

## 钱

月费按 30 天、每天 24 小时。Redis 151.2 元来自官方算例。应用服务器 940 元/台来自社区转述的 c9i 4 核 8G 月价。

本地标记已经生效、库存只有一份的典型秒杀：

| 点击 QPS | 资源 | 目录价月费 |
| --- | --- | --- |
| 10 万 | 2 台 4 核 8G（1 台是备用）+ 1 个 Redis 1GB | 2×940 + 151.2 = **2031 元** |
| 100 万 | 9 台 4 核 8G + 1 个 Redis 1GB | 9×940 + 151.2 = **8611 元** |
| 1000 万 | 84 台 4 核 8G + 1 个 Redis 1GB | 84×940 + 151.2 = **79111 元** |

如果按「每个点击都打 Redis，并且热 key 真能拆到 N 个分片」去买，Redis 部分：

| 点击 QPS | 官方 10 万/分片的 Redis 月费 | 本地标记只留 1 个分片 | Redis 上少付 |
| --- | --- | --- | --- |
| 10 万 | 151 元 | 151 元 | 0。这个量级一个分片够用 |
| 100 万 | 1512 元 | 151 元 | **1361 元/月（90%）** |
| 1000 万 | 15120 元 | 151 元 | **14969 元/月（99%）** |

应用服务器也能少买一台数。同机测到 HTTP 本地拒绝 12.0 万 QPS，HTTP 里每次打 Redis 是 6.6 万 QPS。1000 万点击：

- 每次打 Redis：`ceil(10000000 / 66092) = 152` 台 × 940 = 142880 元
- 本地拒绝：84 台 × 940 = 78960 元
- 应用服务器少 **63920 元/月**
- 加上 Redis 少的 14969 元，合计大约 **7.9 万元/月**

这个差额有边界。6.6 万是客户端、服务端、Redis 挤在 4 个核上的结果。Redis 单独放机器之后，应用侧的 Redis 调用会变，差额会变。12.0 万也不是 Spring Boot 的数字。面试时要先说测量条件，再说钱。

数据库侧没有可比较的月费：单行在 SQLite FULL 上是 2.97 万 QPS，1000 万点击是 337 倍。继续升配买不到这一倍。省下的是一次无效的升配，不是一份精确的 RDS 报价。

分布式锁没有单独的云账单，它把成功扣减从 13.9 万压到 1263。要追上 Lua 的成功吞吐，大约要 110 条这样的串行队列。同一个 key 上做不到。

## 面试时可以主动讲的取舍

本地标记省的是 Redis 命令和分片账单。HTTP 框架本身还在，所以应用服务器不会变成原来的 1/104。1/104 是 Redis 命令数，1.8 倍是这次 HTTP 的端到端差距。两个数字都要报，只报 3170 万 QPS 会被追问。

连接不是越多越好。售罄脚本 16 连接 19.5 万 QPS、p99 ≤ 200 微秒；128 连接掉到 17.2 万，p99 ≤ 2 毫秒。单线程排队变长了。

AOF `everysec` 只惩罚写。成功路径少 13.4%，售罄读几乎不变。生产要开 AOF，容量按 11.9 万成功 QPS 这个已测数字留余量，不要用关了持久化的 13.9 万。

一人一单的集合只保存胜出用户，大小跟库存走，不跟点击 QPS 走。

旧锁脚本有语法错误。解锁必须比较 value，否则会删掉别人的锁。

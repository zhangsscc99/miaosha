## 30 秒版本

秒杀的库存是一个热 key。正确做法是用 Redis Lua 在一次往返里完成「是不是已经买过、还有没有库存、扣减、记下用户」。在这台 4 核虚拟机上，一个 64MB 上限的 Redis 进程把一个核打满之后：

- 成功扣减大约 **13.9 万 QPS**（16 条连接，p99 不超过 200 微秒）
- 售罄判断大约 **19.5 万 QPS**（16 条连接）
- 打开 AOF `everysec` 之后，成功路径降到 **11.9 万 QPS**（少 13.4%），售罄读路径没有变慢
- 同一把分布式锁的成功扣减只有 **1263 QPS**，大约是 Lua 的 1/110
- 应用侧先 GET 再 SET，100 件库存卖出了 **400** 件，库存最后还剩 74
- 进程内售罄标记把同一批 2 万个请求的 Redis 命令从 **60203** 降到 **578**，两轮都正好卖出 100 件
- 带上 HTTP 之后，本地直接拒绝大约 **12.0 万 QPS**，每个请求都打 Redis 大约 **6.6 万 QPS**。进程内原子读的 3170 万 QPS 不能当成接口容量

单分片有单线程上限。两个 key 放在同一个 Redis 里还是大约 19.5 万 QPS。拆成两个进程、内存合计仍是 64MB，售罄读到 **32.6 万 QPS**，是 1.69 倍，因为客户端和两个 Redis 抢 4 个核，没有线性到 2 倍。

第 3 章把成功扣减也拆开，对照是同一次跑出来的单进程 **14.2 万 QPS**（16 连接，p99 不超过 200 微秒，Redis CPU 100%）。同进程两个 key 是 14.3 万，1.006 倍。两个进程、同样 4 秒是 **24.5 万**，1.73 倍。两个 Redis 加客户端合计 350% CPU。AOF `everysec` 的双进程是 22.7 万，少 7.2%。20 万件卖完从 1.425 秒降到 0.745 秒。取模可以一人一单；流量打到一个桶上，另一个桶的 50 件会剩下。同一人同时打两个桶，100 件卖给了 50 个人。

第 4 章用 8 个进程测售罄标记。64000 次点击有标记时 Redis 评估 **225** 次，没有标记是 64000 次。售罄后再跑 2 秒，有标记 **128** 次，没有标记 **14.6 万 QPS**，只有 1 个进程时的 0.93 倍。本地额度合计大约每秒 8100，Redis CPU 从 99.5% 降到 **8.3%**，4 个进程和 8 个进程一样。限流放在 Redis 里仍是 **100% CPU**。1000 万点击的 Redis 还是 1 个分片，相对按点击买 100 个分片少 **14969 元/月**。

第 5 章换成商品详情。售罄可以本地拒绝，详情必须把页面交出去。正文是仓库里的静态页，**6785** 字节。一个 64MB Redis 上，16 连接 `GET` **162700** QPS，Redis CPU 85.5%；64 连接 **190962**，CPU 92.9%，没有打满。4 个进程是 **167192**，1.03 倍，p99 从不超过 1 毫秒变成不超过 5 毫秒。热 key 不加进程。512 个请求同时打空缓存：只做 SQLite 时三次回源是 **385、423、512**。把连接占住大约 20 毫秒、池大小 8 时，**512** 次全进数据库，整波 **2.62** 秒，回源 CPU **394.7%**。进程内 singleflight 收成 **4** 次，最大等待 35.7 毫秒。一把锁收成 **1** 次，但轮询了 4769 次，Redis 命令 **5795**。逻辑过期让 512 个人都拿到旧页面，p99 不超过 **10** 毫秒，回源 1 次，命令 **1026**。页面放进进程内存后，读者 p99 不超过 **5** 微秒，4 个进程各回源 1 次，这一波 Redis 命令是 **0**。不存在的商品不写占位，200 次全进 SQLite；写 `__NULL__` 并且 singleflight，回源 **1** 次，后面 4000 次 `GET` 是 0。锁没有过期时间时，8 个请求 **0** 次回源，详情仍然是空的。按点击去买 100 个分片少付的是 **14968.8 元/月**，那些分片不增加这一个 key 的 QPS。详情的字节还是要从应用服务器吐出去，所以不把第 1 章少买的应用服务器再算一遍。

第 6 章换成很多 key 一起过期。`GoodsKey` 的列表和详情都是 60 秒，`SETEX` 不抖动。2000 个 key 用同一个 TTL，一次 `EXISTS` 采样里 2000 个一起消失。TTL 铺开 2 秒后，一次采样最多消失 101 个。10 万个小 key 不访问，hz=10 大约 600 毫秒主动删完，最慢的一次 `PING` 是 1.5 毫秒；hz=100 大约 200 毫秒删完，这次的 `PING` 是 2.6 毫秒。没有把 Redis 打挂。

3200 个已经确认的未命中：不合并是 **3200** 次回源，进程内 singleflight 是 **800**，一个 key 的 singleflight 是 **4**，只有一个进程重建是 **200**。singleflight 收掉的是每个 key 上的并发，收不掉 key 的个数。4 个核打满时，100 毫秒桶是 185 到 210 次，大约每秒 1900 次。这是大约 2 毫秒 CPU 的回源，不是这次 10 微秒的 `SELECT`。10 万个这样的回源挤在 1 秒里要 53 台 4 核，摊在 60 秒 TTL 上是 1 台，少 **48880 元/月**。目录价仍是 940 元/台，不是 RDS。空缓存的第一波，抖动和固定 TTL 都是大约 200 次回源挤在一起。抖动把下一波的 100 毫秒桶从 178 压到 43，总次数没有变少。

第 2 章把胜出的那一次 `XADD` 放进同一段 Lua。16 条连接、一个核打满：

- 扣减加入队 **10.7 万 QPS**，p99 不超过 500 微秒。比第 1 章不加队列的 13.9 万少 23%，Redis CPU 99.3%
- 打开 AOF `everysec` 之后是 **9.2 万 QPS**，少 13.8%
- 5000 个胜出者，请求线程同步等 SQLite FULL 提交要 **376 毫秒**。改成入队就返回是 **62 毫秒**，大约 6.1 倍
- 消费者一批提交 100 行时，这 5000 行在用户返回后 **0.43 毫秒**内写完。一批一行时，库要再花 **564 毫秒**，因为只剩一个写者，速度是实测的 **9041 行/秒**
- 同一条消息重放一次，订单仍是 100 行。连续失败两次后第三次写成功。一直失败的 20 条进了死信，PEL 被清空
- 先 `DECR` 再 `XADD` 时，100 个胜出者丢掉 20 个，库存已经是 0，订单只有 80。现有控制器就是这两次调用
- 200 字节正文堆在 64MB 里，到 **25 万条**、`used_memory` 58.9MB 就到了门槛。5000 个胜出者大约 1.1MB

点击加到 1000 万 QPS，订单行数仍然等于库存。不需要为点击去买 Kafka。按帮助中心专业版高写版、地域组 1、峰值再留 30%，每个 200 字节的点击都进 Kafka 时，1000 万 QPS 对应 3000 MB/s 那一档，流量规格 **71,540 元/月**（不含磁盘）。胜出才入队的话，这条流在第 1 章那个 Redis 上，这项月费是 0。

第 7 章关的是已经胜出、却还没支付的订单。32 个连接对 2000 张单先 `HGET` 再 `INCR`，库存加到 **23094**，有序集合里的 2000 个成员还在。同一批改成 Lua，库存正好 **2000**。支付和关单同时抢 4000 张，付掉 2831、关掉 1169，库存等于关掉的张数。1000 个带 TTL 的键过期之后库存仍是 0，没有回调。5 万张到期单，1 个连接 **35911/秒**（Redis CPU 55.3%），16 个连接 **92119/秒**（CPU 99.5%，窗口 0.54 秒）。10 万张订单的有序集合是 **88.2 字节/成员**，状态哈希是 **50.5 字节/字段**。按代码里的 2 小时、每个点击都建一单并且谁都不付，1000 万点击/秒大约 **9985** 个 1GB 分片，目录价 **1,509,732 元/月**。只把胜出者放进队列仍是 1 个分片，少 **1,509,581 元/月**。9985 个分片没有跑起来。

第 8 章把 Kubernetes 的限额写成 cgroup 文件，没有跑容器运行时。售罄读不限额是 **186,247** QPS，Redis CPU 99.5%。`cpu.weight=1` 仍是 **181,632**。限额 2 核是 **177,662**，0 个周期被按住。限额 1 核是 **193,578**，11/40 个周期被擦到，一共 15.8 毫秒。2 核没有更快。500m、16 连接是 **98,251**（52.8%），40/40 个周期被按住，超过 10 毫秒的请求正好 **640** 个，等于 16×40。p99 仍不超过 200 微秒，最慢 **53.5** 毫秒。同样的 500m 改成 128 连接，QPS **93,318**，超过 10 毫秒的是 **5120**，p99 不超过 **50** 毫秒。周期改成 1 秒、仍是 0.5 核，QPS **96,041**，最慢 **499.8** 毫秒，慢请求只有 64 个。成功扣减不限额 **132,776**，2 核 **140,478**，500m **70,465**。两个 1 核限额的 Redis 挤在这台 4 核上，合计 **316,715**，是 1.70 倍。父 cgroup 只有 1 个核时，weight 39 和 10 的 12 秒 QPS 是 **105,470** 和 **86,031**，比是 1.23，不是 3.9；加起来 **191,501**，仍是一个核。Redis 和压测塞进同一个 1 核，QPS **69,140**。`maxmemory 8MiB` 时进程还在，返回 OOM 文本；`memory.max=32Mi` 比 Redis 的 64MiB 紧时，写到 116 个 256KB 的值，`memory.peak` 顶到 33,554,432，进程被杀掉，客户端只有连接重置。按每个点击都进 Redis、186,247/核，1000 万是 54 个核。每片独占一台 4 核是 50,760 元/月，每片一台 2 核是 12,690 元/月，少 **38,070 元/月**。本地标记生效时 Redis 仍是 1 片，少的是 **470 元/月**。27 台没有同时跑。

第 9 章把胜出者放进一个 Kafka 进程，堆 256MB，副本数 1。先提交位移再记账，200 条里有 20 条这个消费组不会再读到。不提交就退出，下一次再读到 200，用户仍是 200。1 个分区分给 2 个消费者是 1000 和 0；4 个分区是 500 和 500。Go 客户端把 broker 用到 **107.2%** CPU 时是 **1,387,572** 条/秒，客户端自己占 **201%**，4 个核没有打满。6 个分区是 1.09 倍。官方 Java 工具只有 **450,450** 条/秒，broker CPU **20%**。10 万条不压缩的日志是 **210.00** 字节/条，RSS 只多了 44KB。5000 条 ack 是 **5.1** 毫秒。按 138.8 万去除，1000 万点击都进日志是 8 个进程；只放胜出者仍是 1 个。重复载荷的 lz4 压到 5.37 字节/条，不能拿去报订单磁盘。

## 和现有代码的关系

`MiaoshaService.miaosha` 现在还是同步 RPC 减库存，减失败再 `setGoodsOver`。第 1 章把「减库存的决策」单独抽出来压测，对应两件原有想法：售罄标记，以及仓库里已有的 Lua 限流。旧的 `luaLockScript.lua` 把判断写进了 `redis.call` 的参数，还用了 `KEY` / `AVG`，脚本本身不能执行。这次用的解锁脚本是比较 value 再删除。

## 测试机，也就是「一小部分资源」

| 项目 | 实际使用 |
| --- | --- |
| 机器 | 4 vCPU，KVM 上的 Intel Xeon（family 6 model 207），内存 15GB。压测进程和 Redis 在同一台机器 |
| Redis | 7.0.15，一个进程，`maxmemory 64mb`，关掉 RDB。售罄场景 RSS 约 10MB，成功扣减场景 RSS 约 49MB |
| 横向对照 | 两个进程，各 32MB，合计仍是 64MB |
| 持久化对照 | 同一进程打开 `appendonly yes`、`appendfsync everysec` |

| 没测的 | MySQL / RDS、跨机器网络、Spring Boot、Redis 主从切换、Kubernetes |

延迟用直方图桶的上界：写成「p99 不超过 200 微秒」是桶的边界，真实值可以更小。本地原子读的 p99 落在 200 纳秒这个最小桶里，JSON 里的 `p50us` 用整数微秒会显示成 0。

Redis 在成功路径和售罄路径上都到了大约 99% CPU（单线程，所以是一个核）。瓶颈在 Redis，不在压测客户端没把请求发出去。本地回环的网络延迟被足够的并发挡住了，这个单核数字可以拿来估计「同机房、客户端连接数足够」时一个分片的上限。跨可用区、经过 Proxy、再加鉴权和日志，都会更低。容量规划同时放了阿里云文档里的单分片参考值 **10 万 QPS**，取更保守的那个。

价格口径，全部是目录价，不是账单：

- Redis 社区版 1GB 标准版，杭州按量 **0.21 元/小时 = 151.2 元/月**。来源是阿里云帮助中心《Redis 资源包介绍》里的算例。云原生分片的官方 QPS 参考值是 10 万，和规格大小无关。
- ECS 计算型 c9i：2 核 4G 约 470 元/月，4 核 8G 约 940 元/月，8 核 16G 约 1880 元/月，16 核 32G 约 3760 元/月。来源是阿里云开发者社区 2026 年规格文的转述，下单以控制台为准。应用服务器按 4 核 8G 这档估算，因为我们的 HTTP 压测就是 4 个核。

## 这些数字怎样用在 10 万、100 万、1000 万

先把点击和成交分开。典型秒杀库存远小于点击。5000 件库存按 13.9 万成功扣减/秒，决策本身只要大约 36 毫秒。后面的流量都是售罄流量。

应用服务器用这次测到的 HTTP 本地拒绝 **120,452 QPS / 4 核** 来除。这是 Go 标准库、本机回环、没有鉴权、没有 access log，而且压测客户端也占着这 4 个核。Spring Boot 会更低；客户端换到别的机器，服务端可能更高。表里的台数是这次实验的比值，不是生产容量承诺。

Redis 给出两列。规划列用官方单分片 10 万 QPS。实验列用本机售罄 19.5 万 QPS。典型秒杀在本地标记生效之后，Redis 不需要按点击 QPS 扩。下表的 Redis 列是「如果每个点击都打到 Redis」的对照，用来算省下来的分片。

| 点击 QPS | 应用服务器（按 12.0 万/台） | 每个点击都打 Redis，官方 10 万/分片 | 每个点击都打 Redis，实验 19.5 万/分片 | 本地标记生效后的 Redis |
| --- | --- | --- | --- | --- |
| 10 万 | 1 台 4 核 8G。再加 1 台做故障切换，这 1 台是可用性，不是压出来的 | 1 个 1GB 分片 | 1 个分片 | 1 个 1GB 分片 |
| 100 万 | 9 台 4 核 8G | 10 个分片 | 6 个分片 | 1 个分片，前提是所有实例转发进 Redis 的总量不超过一个分片 |
| 1000 万 | 84 台 4 核 8G | 100 个分片 | 52 个分片 | 仍然是 1 个分片，约束同上 |

10 万点击时，1 台应用加 1 个 Redis 在实验比值里就盖住了。100 万和 1000 万时，台数主要被 HTTP 吃掉，不是被 Lua 吃掉。

单个库存 key 不能靠加 Redis 分片变快。100 个分片接的是 100 个不同的 key。真的要把成功扣减做到单核以上，得把库存拆成多个桶（按用户取模），每个桶一个进程。售罄读的双进程是 1.69 倍。成功扣减的双进程在第 3 章，同一次对照是 1.73 倍，见下面的第 3 章。上表仍然是点击 QPS，不把 1.73 套进点击。

每个应用实例在标记生效前都会漏过一小段流量。第 4 章用 8 个进程测了：64000 次点击、有标记，Redis 评估 225 次；没有标记是 64000 次。售罄之后的 2 秒，8 个进程有标记是 128 次评估，没有标记是 292615 次、CPU 99.9%。本地额度把总和收在大约每秒 8100，4 个进程和 8 个进程一样。规划仍是官方 10 万的 80%，也就是所有实例加起来 8 万。限流如果先打到 Redis，2 秒里仍然是 342201 次评估、CPU 100%。细节在第 4 章。

落库不在这一章。胜出人数等于库存。5000 笔订单即使用这次 SQLite FULL 的速度，也是一两秒内的写入量。1000 万点击不能每点一次就写数据库：FULL 单行上限 2.97 万 QPS，1000 万是它的 337 倍。更大的 RDS 规格去不掉这一行上的锁。

## 面试时可以主动讲的取舍

本地标记省的是 Redis 命令和分片账单。HTTP 框架本身还在，所以应用服务器不会变成原来的 1/104。1/104 是 Redis 命令数，1.8 倍是这次 HTTP 的端到端差距。两个数字都要报，只报 3170 万 QPS 会被追问。

连接不是越多越好。售罄脚本 16 连接 19.5 万 QPS、p99 ≤ 200 微秒；128 连接掉到 17.2 万，p99 ≤ 2 毫秒。单线程排队变长了。

AOF `everysec` 只惩罚写。第 1 章成功路径少 13.4%，售罄读几乎不变。只做扣减决策时，容量按 11.9 万留余量。第 2 章把入队放进同一段脚本之后，AOF 下是 9.2 万，少 13.8%。生产路径要入队的话，用 9.2 万。

一人一单的集合只保存胜出用户，大小跟库存走，不跟点击 QPS 走。

旧锁脚本有语法错误。解锁必须比较 value，否则会删掉别人的锁。

## 第 2 章在测什么

现有 `MiaoshaController` 先扣 Redis，再发 RabbitMQ。`MQReceiver` 发现数据库没库存就 return，消息被确认，Redis 里那一次扣减没有订单。`miaosha_order` 有唯一键 `u_uid_gid`，接收端先查再插，重复投递撞键之后会靠异常重入队。

实测用的是 Redis Stream 消费组，不是 RabbitMQ 进程。语义对应手动 ACK：写进 SQLite 之后才 `XACK`，主键是 `(user_id, goods_id)`。失败的消息留在 PEL，`XAUTOCLAIM` 再领。连续 3 次失败改 `XADD` 到死信流再 ACK。

精确 `MAXLEN` 把 200 条还在 PEL 里的消息裁没了，认领时 Redis 回报删除 200 条，流里剩 10 条。压测里的 `MAXLEN ~ 10000` 只是为了让 64MB 装得下 3 秒的成功路径。生产上的胜出流按库存留内存，不靠裁剪丢消息。

## 队列和落库的数字

入队，3 秒窗口，Redis 单核打满：

| 场景 | QPS | p99 上界 |
| --- | --- | --- |
| Lua + XADD，16 连接 | 106,545 | 500 微秒 |
| 32 连接 | 112,341 | 1000 微秒 |
| AOF everysec，16 连接 | 91,819 | 500 微秒 |
| 纯 XADD，短字段 | 196,462 | 200 微秒 |
| 纯 XADD，加 200 字节正文 | 137,766 | 500 微秒 |

落库是 SQLite WAL，同一块虚拟盘。FULL 逐条 9041 行/秒，4 个消费者是 9293，没有线性提升。100 行一个事务是 171,582 行/秒，19 倍。这台机器的 `fsync` 很快，FULL 的 p99 才能不超过 500 微秒。拿去和 RDS 比的时候，9041 是上界。

5000 库存、4 个生产者，用户等待和订单可见是两个时间：

| | 用户等待 | 5000 行落库 | 说明 |
| --- | --- | --- | --- |
| 请求里同步提交 | 376 毫秒 | 376 毫秒 | 13,291 单/秒 |
| 异步，一批一行 | 62 毫秒 | 626 毫秒 | 人先走，一个写者后面慢慢补 |
| 异步，一批 100 行 | 65 毫秒 | 65.4 毫秒 | 落库比入队快，几乎同时完成 |

6.1 倍是用户等待。一批一行时库反而比同步更慢，因为同步有 4 条连接在提交。要既快回用户、又不把订单拖在队列里，靠的是批提交，不是多开消费者。

64MB、不裁剪、200 字节正文，写到 25 万条、58.9MB 停下。短字段 200 万条只到 37MB，每条 17.8 字节，外推到 64MB 大约 369 万条，外推没有再跑到写满。规划用 230 字节这一组。5000 人大约 1.1MB。一个进程按 13.8 万次/秒写 200 字节，大约 1.8 秒写到门槛，然后 `noeviction` 开始拒绝写。

## 点击 QPS 和订单 QPS

典型秒杀的队列长度等于库存。5000 人按 AOF 的 9.2 万/秒，入队大约 55 毫秒。10 万、100 万、1000 万点击都是这个数，因为售罄点击不进流。落库 1 个主库：逐条大约 0.55 秒，100 行一批大约 0.03 秒。应用服务器台数沿用第 1 章，这一章没有重测 HTTP。

库存如果真的有 100 万、1000 万，单核入队要 10.9 秒和 109 秒。那就要按用户拆桶、拆进程。成功扣减拆到两个进程的加速比在第 3 章，入队脚本没有再拆一次。100 万行用一批 100 的速度大约 5.8 秒，1 个主库仍然写得完。1000 万行要 59 个这样的 SQLite 写者，MySQL 更慢，这个 59 是乐观的。

每个点击都写一条 200 字节消息时，一个核的纯 XADD 是 13.8 万 QPS。10 万点击 1 个进程，100 万点击 8 个，1000 万点击 73 个。第 1 章两个进程只有 1.69 倍，73 是每个进程单独吃满一个核的下限。每个进程的 64MB 大约 1.8 秒写满。

## 消息集群的钱

Kafka 专业版（高写版）公共云地域组 1，业务写入取表上「3×N MB/s」里的 N，再按帮助中心说的留大约 30% 余量。只算流量规格，不含磁盘（SSD 100GB 目录价 100 元/月）。

| 点击都进 Kafka | 写流量，留 30% | 规格月费 | 只入队胜出者 |
| --- | --- | --- | --- |
| 10 万 QPS | 约 25 MB/s | 4,235 元（30 MB/s） | 0 |
| 100 万 QPS | 约 248 MB/s | 16,525 元（250 MB/s） | 0 |
| 1000 万 QPS | 约 2480 MB/s | 71,540 元（3000 MB/s） | 0 |

1000 万点击少买的是这 **71,540 元/月**。磁盘没算，账单只会更高。如果不用 Kafka、改用 73 个 Redis 1GB 来扛每个点击，73 × 151.2 = 11,038 元/月，还要接受每个分片大约 1.8 秒的堆积上限。这个方案没有采用。

RabbitMQ 的进程没跑。弹性 TPS 公开单价是 0.0005 元/TPS/分钟，企业版弹性最多 5 万，接不住每秒 1000 万次。包月档的单价在购买页，帮助中心没有列成表，这里不编一个月费。停新购的按量实例是 2 元/百万次 API。1000 万点击持续 10 秒、一发一收，大约 400 元；5000 个胜出者不到 0.02 元。那是一次活动的调用费。第 9 章补的是本机 Kafka 进程的速率和磁盘，不改这张托管价表。

## 第 3 章：成功扣减的两个进程

第 1 章的 1.69 倍是售罄读。成功路径要写已购集合，内存和 QPS 都要重测。Redis 7.0.15，jemalloc 5.2.1，和前两章不是同一份二进制，所以单进程对照用这一章自己的 **141786 QPS**。第 1 章那次是 138581，差在这个量级里。

| 做法 | QPS | 相对单进程 |
| --- | --- | --- |
| 一个进程，一个 key，16 连接 | 141,786 | 1 |
| 一个进程，两个 key，16 连接 | 142,597 | 1.006 |
| 两个进程各 64MB，32 连接，4 秒 | 244,922 | 1.73 |
| 同上，AOF everysec | 227,395 | 1.60，相对不开 AOF 的双进程少 7.2% |
| 两个进程各 32MB，合计 64MB，窗口 2 秒 | 254,713 | 1.80。集合更小，不能拿来代替 4 秒窗口 |
| 钉核，Redis 在 CPU 0 和 1，压测在 CPU 2 和 3 | 229,339 | 0.94 倍于不钉核的双进程 |

两个进程加客户端用了 350% CPU。每个 Redis 大约 93%。1.73 倍和售罄读的 1.69 倍是同一件事：4 个核不够把两个 Redis 都喂到 100%，再加一个客户端。钉核之后更慢，少 6.4%，最慢的一次从 9.5 毫秒变成 13.8 毫秒。绑核没有当成优化。

20 万件实测卖完：一个进程 1.425 秒，两个进程 0.745 秒，1.91 倍。5000 件按 141786 QPS 是 35 毫秒，不拆。按两组 `used_memory` 估算，这份二进制上每个胜出者大约 43.5 字节，再加 1.7MB 基线。64MB 大约记下 150 万人。第 1 章的 52 字节是另一份二进制，不要混进这张表。

正确性是小请求量，QPS 字段不能当容量：

- 取模，库存 50+50：成功 100，两个已购集合交集为 0
- 400 个用户全打到 0 号桶：成功 50，1 号桶剩 50
- 库存 10 和 90，流量对半：最后卖完。薄桶第一次售罄时厚桶还剩 67
- 同一人同时打两个桶：100 件，50 人，每人两件
- 搬走 50 件的中途停掉：50 件从两个进程里都消失
- 并发下 `GET` 再 `SET`：20 万库存的账变成 204598，多 4598
- Lua 取走再 `INCRBY`：卖出 4520，搬走 195480，合计仍是 200000

1 秒内做完的成功扣减，官方列仍是每分片 10 万 QPS。实验列用 14.2 万，前提是每个进程独占一个核，客户端不跟它抢。超过两个进程没跑。

| 1 秒内的成功扣减 | 官方列，1GB 分片 | 目录价 | 按 14.2 万外推 |
| --- | --- | --- | --- |
| 10 万 | 1 个 | 151 元/月 | 1 个进程，已经测到 |
| 100 万 | 10 个 | 1512 元/月 | 8 个进程，1210 元/月。外推 |
| 1000 万 | 100 个 | 15120 元/月 | 71 个进程，10735 元/月。外推 |

不拆桶就去买这 10 个或 100 个分片，流量还在一个槽上。空转的是 9 个和 99 个分片，目录价 **1361 元/月** 和 **14969 元/月**，成功 QPS 不加。拆成库存桶之后，同样的账单对应的是每个分片都在做成功扣减。官方 10 万和本机 14.2 万之间差 2 个、29 个分片，目录价差 302 元/月、4385 元/月。第二个进程在这台机器上只贡献了 0.73 倍，所以买的时候仍按 10 万留余量。

5000 件不参与这张表。一个分片 35 毫秒做完，第二个分片是每个月多 151.2 元。

## 第 4 章：多实例的售罄标记和准入额度

第 1 章的标记是一个进程。`MiaoshaController.localOverMap` 也是每个 JVM 一份，而且 `RedisLimitRateWithLUA.accquire()` 写在 Map 判断之前。第 4 章用操作系统进程把标记隔开，Redis 仍是一个 64MB 进程。

8 个进程、各 16 条连接、各 8000 次点击、库存 100：有标记 225 次评估、875 条命令；没有标记 64000 次评估、192200 条命令。多出来的 125 次售罄评估接近连接数，不接近点击数。同样 32 条连接，1 个进程 104 次评估，拆成 8 个进程 129 次，只多 25。4 个进程各 64 条连接，最慢 37.3 毫秒才看见售罄，售罄评估 172 次。突发收成 2 之后评估仍是 214，命令数几乎没少，最慢标记从 21.9 毫秒降到 5.6 毫秒。

库存已经是 0、再跑 2 秒：8 个进程有标记 128 次评估；没有标记 292615 次、146216 QPS、CPU 99.9%。相对 1 个进程的 157783 是 0.93 倍，不是 8 倍。这段脚本比第 1 章的售罄读多一次 `SISMEMBER`，不要写成 19.5 万。

库存 500 万、卖不完：1 个进程成功路径 141082 QPS、CPU 99.5%。4 个进程各 2000 次/秒是 8132 QPS、CPU 8.3%。8 个进程各 1000 次/秒是 8126 QPS、CPU 7.3%。Redis 看到的是总和。桶初始是满的，所以 3 秒大约是 `rate×3+burst`，不是刚好 `rate×3`。这两组的 p99 被客户端空转拖到 20 毫秒那一档，不拿来当 Redis 延迟。

有一个进程不守每秒 1000 的额度，2 秒打了 149272 次，是守约进程的 71 倍。本地额度不是集群强制。把窗口上限放进 Redis，放行只有 2000 次库存脚本，评估仍有 342201 次，CPU 100%。同样量级的拒绝放在进程内，评估 4099 次，CPU 2.5%。

不探测时，补上的 50 件一件卖不掉，阶段 2 的评估是 0。每 20 毫秒放行一个真实用户，500 毫秒里卖完，阶段 2 评估 162 次。只有这次探测成功才清标记。在途的成功请求不清。

1000 万点击的 Redis 仍是 1 个 1GB 分片，151.2 元/月。按点击买 100 个分片少付的还是 **14969 元/月**。按 84 台应用各买一个分片，少付 **12550 元/月**，因为 8 个进程没有把这个 key 做成 8 倍。应用台数不在这一章重测。

## 第 5 章：商品详情的缓存击穿

第 4 章的标记能把售罄点击挡在 Redis 外面，是因为答案是「没有了」。详情要把 6785 字节交出去。`GoodsKey.getGoodsDetail` 的 TTL 是 60 秒。v2 的 `detail2` 是 `GET`，未命中就查库、渲染、`SET`，中间没有单飞。v1 的 `detail2` 查完库甚至没有 `SET`。`StringUtils.isEmpty` 把空字符串当成未命中。

Redis 还是那个 64MB 的 7.0.15。回源是本机 SQLite 3.45.1 里的一行。慢路径在 `SELECT` 之后再占住连接做一段 CPU 运算，探针 20.06 毫秒，不是 sleep，也不是 MySQL。连接池 8。

命中时，2 秒窗口：

| 读法 | QPS | CPU | p99 上界 |
| --- | --- | --- | --- |
| 1 进程 16 连接 `GET` | 162700 | Redis 85.5%，客户端 217.9% | 1 毫秒 |
| 1 进程 64 连接 `GET` | 190962 | Redis 92.9%，客户端 225.4% | 2 毫秒 |
| 4 进程各 8 连接 `GET` | 167192 | Redis 84.9%，客户端 268.8% | 5 毫秒 |
| 1 进程，页面已经在内存里 | 6991525 | 客户端 394.4% | 1 微秒 |

64 连接只比 16 连接多 17.4%，Redis 没有到 100%，客户端还占着两个核以上。4 个进程是 1.03 倍。699 万次是同一块 6785 字节在 CPU 缓存里被反复抄，没有进网卡，不能拿去除点击 QPS。4 个这样的进程是 1656 万，2.37 倍，因为 1 个进程已经把 4 个核占满。

SQLite 单连接读这一行是 **42278** 次/秒，p99 不超过 50 微秒。8 连接是 **126683**，2.996 倍。这是上界。

512 个请求同时看见空缓存：

| 做法 | 回源 | 用户等到的延迟 |
| --- | --- | --- |
| 只做 SQL。连跑三次 | 385、423、512 | 墙钟 16 到 17 毫秒 |
| SQL 之后把连接占住约 20 毫秒，池 8 | 512 | p50 不超过 1.5 秒，最大 2.617 秒，回源 CPU 394.7% |
| 4 个进程各做 singleflight | 4 | 最大 35.7 毫秒。命令 520 |
| 一把 PX 5 秒的锁，其他人每 1 毫秒轮询 | 1 | 最大 35.3 毫秒。命令 5795，其中轮询 4769 |
| 逻辑过期，旧页面直接返回 | 1 | p99 不超过 10 毫秒，最大 30.9 毫秒。512 个人全是旧页面。命令 1026 |
| 旧页面在进程内存里 | 4 | 读者 p99 不超过 5 微秒。Redis 命令 0 |

锁把回源从 4 次收成 1 次，Redis 命令变成 singleflight 的 11.1 倍，等待没有变短。逻辑过期把等待从「大家都等那一次回源」变成「一个人去刷新」。本地缓存把这一波的 Redis 也拿掉了，回源仍是每个进程 1 次。

PX 只有 2 毫秒、回源要 20 毫秒时，128 个请求回源 **9** 次，不是 1，也不是 128。锁没有过期时间、持有者又不删除时，8 个请求 **0** 次回源，详情还是空的。

不存在的商品：200 个请求不写占位，200 次都进 SQLite。写入 `__NULL__` 但不合并，这一波是 41 次。加上 singleflight 是 1 次，随后 4000 次 `GET` 是 0。

10 万点击的详情，1 个分片按官方 10 万 QPS 盖得住，本机也到过 19.1 万，但那不是独享上限。100 万、1000 万如果按分片去买，买到的是 10 个和 100 个分片，这个 key 的 QPS 不加。少付 **1360.8 元/月** 和 **14968.8 元/月**。应用台数不在这一章改，因为正文比第 1 章的拒绝响应大，6785 × 120452 大约是 817 MB/s，这次没测 HTTP。1000 万点击的正文带宽是 67.85 GB/s，缓存省不掉。省掉的是失效那一秒的回源：1000 万次 `SELECT` 按 42278 次/秒要 236.5 秒；收成每个进程 1 次之后，84 台是 84 次，这个 84 没有跑。

## 第 6 章：很多 key 一起过期

第 5 章把一个详情收成每进程 1 次回源。`GoodsKey.getGoodsList` 和 `getGoodsDetail` 都是 60 秒，一批 `SETEX` 会在同一秒到期。2000 个 key 同一个 TTL，`EXISTS` 采样在 t=502 毫秒把 2000 个一起删掉。铺在 500 到 2500 毫秒后，一次采样最多消失 101 个。这是惰性删除：采样访问了它们。不访问的 10 万个小 key，hz=10 从到期到 `keyspace` 为 0 大约 600 毫秒，hz=100 大约 200 毫秒。两次 `PING` 最慢 1493 和 2619 微秒。每个小 key 大约 73.7 字节。

回源仍是 SQLite 加一段大约 2 毫秒的 CPU，池子默认 8。4 个核打满时 100 毫秒做 185 到 210 次。池 4 的槽内时间大约 2.0 毫秒，和探针对得上。不排队的池 8 是 2.7 到 3.3 毫秒，3200 次全部回源的那一组是 4.1 毫秒，桶都没有更高。不排队时池 8 的四次回源是 1200 到 1286，池 4 是 2982 到 3093。少进去的那些是客户端抢不到核，不是策略更正确。

先让 4 个进程确认 3200 次都未命中，再回源：不合并 **3200**，进程内 singleflight **800**，1 个 key 的 singleflight **4**，一个重建者 **200**。800 对 4 就是雪崩和击穿的差别。不排队时，1 个 key 只有 128 个请求赶在写入前冲进去，合并后是 4。200 个 key 的 singleflight 四次是 690 到 708，二次 `GET` 省了一点，省不到 200。

空缓存上，固定 700 毫秒和抖动的第一波都是大约 200 次。之后固定 TTL 的桶最高 178，抖动最高 43。总回源 800 对 865、600 对 681，抖动没有减少总次数。本地截止时间四个进程对齐时，4000 次 `GET` 落在同一个 50 毫秒桶；进程错开 200 毫秒后是 1000。Redis CPU 1.3%。这 4000 次不产生分片账单。

10 万个大约 2 毫秒的回源，1 秒做完要 53 台 4 核 8G，49820 元/月。按 60 秒摊开是 1 台，940 元/月，少 **48880 元/月**。100 万、1000 万少的是 **486920** 和 **4865440 元/月**。`SELECT` 只有大约 10 微秒时，这个差不成立。4 个进程各回源一次是重建者的 4 倍，10 万个 key 多出来的 158 台是除法。84 台没有跑。

## 第 8 章：cgroup 里的 CPU 限额和内存限额

没有 dockerd，没有 kubelet，没有镜像。工作负载 cgroup 只有 memory 控制器。父 cgroup 的 `cpu.max` 是 `max 100000`。脚本用 root 在父 cgroup 下建了目录，把 Redis 7.0.15 的 pid 放进去。`500m` 写成 `50000 100000`，`1` 写成 `100000 100000`，`2` 写成 `200000 100000`。250m 和 1000m 的 request 按 kubelet 的换算是 weight 10 和 39，这两个整数是我们写进去的。

售罄读，16 连接，4 秒。不限额 **186,247**，CPU 99.5%，p99 不超过 200 微秒。weight=1 仍是 **181,632**。2 核 **177,662**，0/40 被按住。1 核 **193,578**，11/40 被擦到，一共 15.8 毫秒。四次都在 17.8 万到 19.4 万，2 核不是最高的。

成功扣减：不限额 **132,776**，2 核 **140,478**（1.06 倍），500m **70,465**（53.1%）。预热也在扣库存，不变量是集合人数加剩余库存等于 500 万。不限额那次 668,290 人，`used_memory` 53.1 字节/人，cgroup 峰值 38,223,872，57.2 字节/人。

## 第 9 章：一个 256MB 堆的 Kafka

仓库里的 `MQSender` 发的是 RabbitMQ。RabbitMQ 和 RocketMQ 这次没有进程。跑起来的是 Kafka 4.2.2，broker 和 controller 在同一个进程，`-Xms256m -Xmx256m`，副本数 1，网络线程和 IO 线程各 2。启动脚本的默认堆是 1G，这里盖掉了。压测和 broker 在同一台 4 核机器上。没有 TLS，没有跨机器 RTT。

`MQReceiver.receive` 在库存小于等于 0 时 return，监听器没有手动确认，正常返回就会被自动确认。`receiveMiaoShaMessage` 先 `basicAck`（`multiple=true`）再插入。第 9 章用消费组位移做了这两件事的对应：200 条先提交、订单只记 180，同一个组再读是 **0**。200 条不提交就关，下一次再读 **200**，两次投递 400，用户仍是 200。幂等生产者开着时，100 个用户再写 20 条，日志是 **120**，订单是 **100**。它不去掉业务上的第二次发送。

1 个分区、2 个消费者，分配稳定后再写 1000 条：分配 **1+0**，条数 **1000+0**。4 个分区是 **2+2** 和 **500+500**。这组用了轮询分区器。吞吐组用的是粘性分区器。

Go 客户端 8 个 goroutine，200 字节，4 秒：

| --- | --- | --- | --- | --- |
| 1 分区，acks=1，linger 5 毫秒 | 1,295,750 | 不超过 20 毫秒 | 77.2% | 219.0% |
| 1 分区，acks=1，linger 0 | 1,387,572 | 不超过 50 毫秒 | 107.2% | 201.0% |
| 6 分区，acks=1，linger 5 毫秒 | 1,410,166 | 不超过 20 毫秒 | 52.5% | 233.4% |

## 还不能讲成已经做过的事

- 没测 MySQL、没测主从切换、没测跨机器 RTT
- 没测第三个 Redis 进程，也没测 Redis Cluster 的槽迁移。两个以上的进程数是除法
- 没跑第 9 个和第 84 个应用进程，没跑 1344 条连接。8 进程的漏量不能乘成 84 进程
- 没跑 RabbitMQ、RocketMQ 的进程。第 9 章跑了一个 Kafka 4.2.2 进程，副本数 1，没有跨机器。托管 Kafka 的钱仍是第 2 章的目录价。没有 dockerd，没有 kubelet，没有容器镜像。第 8 章写的是 `cpu.max`、`cpu.weight`、`memory.max`。工作负载 cgroup 仍然只有 memory 控制器，cpu 配额是 root 在父 cgroup 下建出来的。Kafka 的 RSS 采样到 507924 KB，没有放进 cgroup
- 第 5 章没测 MySQL，没测带 6785 字节正文的 HTTP，没把 699 万次本地拷贝当成接口 QPS。详情 `GET` 的 Redis CPU 到过 92.9%，没有到 100%，190962 不是独享分片的上限
- 快路径击穿三次是 385、423、512，不能单拿一次当稳定值。慢路径的 20 毫秒是 CPU 占住连接，不是 SQLite 的查询时间
- 没跑第 84 个详情进程。4 个进程各刷新 1 次，84 次是除法。很多 key 一起过期在第 6 章，测的是 200 到 10 万个 key，不是 84 台
- 没重测单进程 AOF，没重测 HTTP。双进程 AOF 的 7.2% 不要写成「AOF 总是这个比例」
- 固定窗口的跨秒双倍额度只做了说明，没有专门压边界。第 4 章的 Redis 窗口只有 2 秒，落在 60 秒里面，没有跨边界
- Stream 的 `MAXLEN ~` 只用于压测限内存。200 条未 ACK 消息被精确 MAXLEN 裁掉是实测，不能把它配进胜出流
